# 系统性调试协议 (Debugging Protocol)

本协议用于 **bug 修复 / 报错排查 / 行为异常** 类任务。P0 预检判定任务类型后路由至此，不走 P2"设计定稿"那条功能开发线。

核心区别：功能开发是"从需求推实现"，调试是"从现象推根因"。**未定位根因之前打的每一个补丁，大概率都是在给错误的地方打补丁。**

## 与功能开发流水线的关系

| 功能开发 | 调试 | 说明 |
|----------|------|------|
| P1 澄清 | D0 预检 + D1 复现 | 澄清的对象从"需求"换成"现象" |
| P2 设计定稿 | D2 假设 + D3 验证 | 方案对比换成"根因假设排序" |
| P3 任务清单 | D4 修复计划 | 通常 1-3 个原子任务 |
| P4 执行 | D4 修复 | 最小改动，不顺手重构 |
| P6 验证 | D5 回归验证 | 必须包含防复发的回归测试 |
| — | 连续 3 次失败 | 升级为架构级复盘（回 P2） |

清单仍落盘 `<任务目录>/<task-slug>/CHECKLIST.md`（任务目录按 SKILL.md"环境适配"确定），但按本协议的"调试模式"填写。

## 阶段详解

### D0 预检

1. 收集素材：完整报错信息（含堆栈）、复现步骤、期望行为 vs 实际行为、最近的相关改动（`git log` / 最近提交）。
2. 判定档位（同主流程三档），**并确定分支策略**（见下方"分支隔离策略"）。
3. 声明：任务类型（调试）、档位、分支，让用户可见。

### D1 复现 —— 第一门禁

- **稳定复现是调试的前提**。先构造最小复现路径：最短的步骤、最小的输入、最少的依赖。
- 复现结果记入清单（命令 + 关键输出），这就是后续的"对照组"。
- **门禁：无法稳定复现之前，禁止修改任何代码。**
- 无法复现时：收集更多证据（日志、环境差异、版本差异），问用户要原始现场；实在不能本地复现，记入假设登记并采用"基于证据推理 + 加防御性日志"路线，向用户说明局限。

### D2 假设 —— 根因候选排序

- 列出 **2-4 个候选根因假设**，按可能性排序。每个假设必须写清：
  - **依据**（什么现象指向它）；
  - **验证方法**（用什么最小代价的实验能证实/证伪）。
- 常见根因维度逐个扫：输入数据、边界条件、并发/时序、环境/配置/版本差异、状态残留、依赖方变更。
- 假设记入清单"假设登记"，与 P1 的假设登记共用格式。

### D3 验证

- 按可能性从高到低逐一验证，每次只验证一个假设（控制变量）。
- **多个独立假设可并行派发子代理分别验证**（派发模板见 `invocation.md` 3.4），主 agent 汇总结论。
- 验证手段按代价从低到高：读代码推理 → 加日志复跑 → 最小 demo 隔离复现 → 二分法定位（`git bisect` / 注释法）。
- **门禁：未锁定根因（假设被证实）之前，禁止写"修复代码"。** 允许的例外是防御性日志——它属于验证手段。
- 所有假设都被证伪 → 回 D2 扩大假设范围（查依赖源码 / 查官方 issue / 问用户要更多现场信息），不要硬猜。

### D4 修复

- **最小改动修复**：只修根因，不顺手重构、不扩大范围（范围守卫同样生效）。
- 修复前打回滚点（commit / 分支）。
- 顺手发现的其他问题记入清单"发现事项"，问过用户再动。
- 修复完成后立即更新清单状态。

### D5 回归验证 —— 完成前强制

1. **原复现用例必须通过**（D1 的对照组现在变成验证组）。
2. **写回归测试防复发**：把这个 bug 的触发条件固化成一条自动化测试（精简档至少手动验证步骤写进清单，标准/严格档必须落测试代码）。
3. 跑相关既有测试 + 构建 + lint，关键输出贴进清单"验证证据"。
4. 修复没有证据 = 没有修复。

## 连续失败升级规则

**连续 3 次修复失败 → 停止打补丁**，升级处理：

1. 回 D2 重新审视：是否所有假设都建立在同一个错误前提上？
2. 检查更深层：是不是架构/设计层面的缺陷，而非实现 bug？是 → 回 P2 做架构复盘。
3. 向用户汇报：已排除什么、当前卡在哪、建议的下一步（换思路 / 降级范围 / 引入更多现场信息）。

## 调试模式清单的填写差异

与标准 `CHECKLIST.md` 相比：

- "任务目标"改为：现象一句话 + 期望行为。
- "任务列表"按 D0-D5 填写。
- "假设登记"承载根因假设（含验证结论：证实/证伪）。
- "验证证据"必须包含：复现输出（修复前）+ 回归通过输出（修复后），两者缺一不可。
