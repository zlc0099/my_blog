# 追问澄清协议 (Clarification Protocol)

本协议用于 P1 阶段。目标：**把"我以为"变成"确认过"**，杜绝在模糊状态下产出代码。

## 一、先分类问题等级

| 等级 | 定义 | 处理 |
|------|------|------|
| **Blocking** | 不确认就无法动手（技术栈、数据来源、核心行为） | 必须问用户，未解决前禁止进入 P2 |
| **Important** | 影响方案选择，但有合理默认值 | 问用户；用户不回则采用默认值并记入假设登记 |
| **Minor** | 实现细节，可自行决定 | 自行决定，记入决策日志即可 |

只把 Blocking 与 Important 抛给用户，Minor 自己消化——**不要把所有细节都变成问题**。

## 二、必须覆盖的澄清维度

按维度逐一扫一遍，找出空缺项：

1. **目标**：这次要解决什么问题？成功的标准是什么？
2. **用户与场景**：谁用？在什么场景下用？频次如何？
3. **输入与输出**：数据从哪来、到哪去？格式是什么？
4. **技术约束**：技术栈、版本、框架偏好、必须兼容的既有系统。
5. **边界与异常**：空态、超大输入、并发、网络失败、权限不足时怎么办？
6. **验收标准 (DoD)**：什么样才算做完？谁来验收？
7. **性能与安全**：有无性能指标？有无鉴权、脱敏、合规要求？
8. **范围**：明确哪些**不做**。

## 三、提问方式

**好的提问**：具体、带选项、能推动决策。

> "登录态用 JWT 还是 Session？我倾向 JWT（无状态、方便横向扩展），但如果你们后端已有 Redis 会话体系，Session 会更省事。你们现在是哪种？"

**坏的提问**：笼统、开放式、无法决策。

> "你有什么需求？"

规则：

- 一次最多 **3-5 个**问题，按 Blocking → Important 排序。
- 每个问题尽量给出**推荐选项 + 理由**，降低用户决策成本。
- 存在多种合理解法时，形成 **2-3 套方案对比**（改动范围 / 复杂度 / 风险 / 可维护性），让用户拍板。
- 不要问能从代码或文档里查到的答案——先自己查。

## 四、不要问的情况

以下情况自行决定，不打扰用户：

- 项目已有惯例（看代码风格、看已有同类实现即可确定）。
- 有行业通行默认值（如 REST 用 JSON、时间用 UTC）。
- 属于实现细节，不影响对外行为。

这类决定记入 **决策日志**，事后可追溯。

## 五、假设登记 (Assumption Log)

凡是**无法确认又必须做决定**的，写进假设登记，格式：

```markdown
| # | 假设 | 依据 | 若假设错误的影响 |
|---|------|------|------------------|
| A1 | 用户已登录，token 由网关注入 | 现有 API 均从 header 取 userId | 需新增登录页，工作量 +1d |
```

清单落盘到 `CHECKLIST.md` 的"假设登记"小节。

## 六、何时算"澄清够了"（退出条件）

满足全部条件才可进入 P2：

- 所有 Blocking 级问题已由用户明确答复。
- Important 级问题要么有答复，要么有默认值 + 假设登记。
- 方案已收敛到 1 套（或已让用户在 2-3 套中选定）。
- 验收标准 (DoD) 已明确。
- 范围边界 (in-scope / out-of-scope) 已明确。

未满足 → 继续问。**宁可多问一轮，也不要返工一遍。**
