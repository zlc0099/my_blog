# Git 操作规范 (Git Protocol)

本规范贯穿 P0-P7，与 SKILL.md 的"分支隔离策略"配合使用：**隔离策略管"在哪儿干活"，本规范管"怎么提交、怎么收尾"。**

## 一、提交时机与粒度（与执行批次绑定）

- **开工前**：一个基线 commit（干净基线，即第一个回滚点）。
- **每批末**（1-3 个原子任务，测试转绿后）：commit 一次，message 对应本批内容。commit 本身就是回滚点，记入清单"回滚点"表。
- 严格档可细化到每个原子任务一个 commit。
- **禁止**把整个任务的改动攒成一个大 commit（标准/严格档）——回滚点失去意义。

## 二、Commit message 规范

- 采用 Conventional Commits 风格：`feat|fix|refactor|test|docs|chore: 简短描述`（修 bug 用 `fix:`）。
- 描述必须说清"改了什么 + 为什么"，**禁止** `update` / `fix` / `修改` 这类空 message。
- 可选 body：补充理由或关联 `<task-slug>`，方便从提交历史反查清单。

## 三、提交内容卫生

- **过程文档**（`CHECKLIST.md` / `DESIGN.md` / `HANDOVER.md`）：跟随项目既有约定；项目无约定时**默认不提交**（建议加入 `.gitignore`），避免流程文档污染仓库；团队需要留痕的可提交。
- **禁止提交**：密钥 / 凭证 / 大文件 / 与本任务无关的文件。
- 提交前必看 `git status`，**优先 `git add <具体文件>` 而非 `git add -A`**。

## 四、脏工作区处理（P0 预检必查）

`git status` 发现未提交改动时，**先问用户这是谁的改动**，再决定：

- 用户进行中的工作 → 不碰它，直接新建任务分支（改动会跟随）；或请用户先 stash。
- 疑似遗留垃圾 → 经用户确认后处理（提交 / stash / 丢弃）。

**红线：未经用户明确确认，不得处置用户的未提交改动**（尤其 `checkout --` / `restore` / `clean`）。

## 五、分支终局处理（P7）

任务完成且 P6 验证通过后，**向用户提供四个选项，由用户选择**：

1. **合并**回目标分支（建议 `--no-ff`，保留任务形状）。
2. **建 PR / MR**，交给团队评审流程。
3. **保留分支**，稍后处理。
4. **丢弃分支**（需用户确认后才 `git branch -D`）。

收尾动作：处理完切回目标分支、清理已合并的工作分支、更新清单"回滚点"表。

**验证未通过时不提供合并选项**——只给"保留并记录问题"或"丢弃"。

## 六、破坏性操作红线（绝对）

以下操作**默认禁止**，确需执行必须先向用户说明并获得明确同意，且声明"此操作不可逆"：

- `git push --force`、改写已推送的历史（对已推送 commit 用 `--amend` 同样算）。
- 丢弃用户的未提交改动（`checkout --` / `restore` / `clean -f`）。
- 违反档位策略直接在主分支上开发。
- 未经确认删除分支、清空 stash。
