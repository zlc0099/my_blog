# 调用与派发指南 (Invocation Guide)

本文档说明本 skill 如何被安装、触发，以及如何派发给其他 agent（含子代理）和跨对话续接。

## 一、安装：让 agent 能"看见"这个 skill

**通用要求**：安装目录内必须有 `SKILL.md`（文件名固定，不可改），整个 `fullstack-dev-workflow/` 文件夹原样放入即可，无任何平台专属依赖。

### 1.1 各平台安装位置

| 平台 | 用户级（全局生效） | 项目级（仅该项目） |
|------|--------------------|--------------------|
| **Claude Code** | `~/.claude/skills/fullstack-dev-workflow/` | `<项目根>/.claude/skills/fullstack-dev-workflow/` |
| **其他 harness** | 查其 skills / commands 目录约定，放入整个文件夹 | 同左，放项目内对应目录 |

三种安装方式：

1. **复制文件夹** —— 把 `fullstack-dev-workflow/` 整个复制到平台对应的技能目录。
2. **导入 zip** —— 若平台支持技能导入：把 `fullstack-dev-workflow/` 打包为 zip，从平台的技能管理界面上传。
3. **命令行**（等效于方式 1）：
   ```bash
   cp -r <技能目录>/fullstack-dev-workflow <平台用户级技能目录>/
   ```

### 1.2 通用兜底：任何平台都能用的"引用式安装"

如果目标平台没有技能目录机制（或你不想装），在项目根的提示文件（`CLAUDE.md` / `AGENTS.md` / 项目规则文件）里加一行：

> 所有开发任务遵循 `<技能目录绝对路径>/SKILL.md` 的流程执行。

效果等同：agent 读取项目上下文时就会看到并遵循。

### 1.3 平台专属字段说明

frontmatter 中 `disable` / `disable-model-invocation` 为可选扩展字段，不识别它们的平台会自动忽略（不影响加载）；`name` / `description` 是所有平台的通用契约，不要改名或删除。

安装后确认：平台对应的技能管理列表里能看到 `fullstack-dev-workflow`，且开关为**开启**。

**注意**：每个技能都会占用一部分上下文。不要囤积技能，`fullstack-dev-workflow` 属于高频流程型技能，值得常驻。

## 二、主 agent 如何调用（四种方式）

| 方式 | 怎么用 | 适用场景 |
|------|--------|----------|
| **自动触发** | 直接描述开发任务，不提技能名。例：「帮我做一个登录页」「这个接口报 500 帮我看看」 | 日常最常用。agent 读 `description` 命中关键词就自动加载 |
| **显式点名** | 在指令里写出技能名。例：「**用 fullstack-dev-workflow 流程**做这个需求」 | **推荐用于重要任务**，避免 agent 走野路子 |
| **斜杠命令** | 输入 `/fullstack-dev-workflow`，若技能出现在弹出列表里即可选中 | 最明确。列表里没有时退回显式点名 |
| **先查后装** | 问「有没有适合处理 XX 的技能？」 | 手上没有合适技能时 |

**建议**：日常用自动触发；一旦发现 agent 没走流程（该追问却直接写码、没写清单），立刻改成**显式点名**，并在后续对话保持点名习惯。

## 三、派发给其他 agent / 子代理（重要）

**子代理不会自动继承技能列表。** 只写"帮我写个接口"是不够的，必须在派发指令里明确点名，否则子代理会直接开干、跳过流程。

### 3.1 标准派发模板（推荐）

> 读取并遵循 `<技能目录绝对路径>/SKILL.md` 的流程（含 `references/` 下各协议），完成以下任务：
>
> **任务**：<一句话描述>
> **已知信息**：<技术栈、相关文件、约束>
> **交付要求**：按 skill 的 P0-P7 执行；开工前必须先澄清（有疑问先问我，不要假设）；任务清单落盘到 `<任务目录>/<slug>/CHECKLIST.md`；结束时更新清单并判断是否需要交接文档。

### 3.2 精简派发模板（任务很小）

> 用 `fullstack-dev-workflow` 的**精简档**：先澄清关键问题 → 写清单 → 执行 → 验证。清单落盘 `<任务目录>/<slug>/CHECKLIST.md`。

### 3.3 修 bug 派发模板（配合调试协议）

> 读取并遵循 `<技能目录绝对路径>/SKILL.md` 及其 `references/debugging-protocol.md`，按调试线执行：
>
> **现象**：<报错信息 / 异常行为，附堆栈与复现步骤>
> **期望行为**：<应该是什么样>
> **环境信息**：<技术栈、版本、相关文件路径>
> **交付要求**：先稳定复现再动手；列出根因假设并逐一验证（未定位根因不得写修复代码）；修复后必须提供"修复前复现输出 + 修复后回归通过输出"两组证据，写入 `<任务目录>/<slug>/CHECKLIST.md`。

用于并行验证多个根因假设时，为每个子代理指定**只验证一个假设**，并要求返回"证实/证伪 + 证据"。子代理结论仅作输入，**根因锁定与修复由主 agent 确认**。

### 3.4 派发时最容易漏的三件事

1. **没点名技能** → 子代理不知道有这个流程，直接裸写代码。
2. **没给绝对路径** → 子代理在别的 cwd 下找不到 skill 目录；派发时把模板里的 `<技能目录绝对路径>` 换成当前平台的实际安装全路径。
3. **没要求落盘清单** → 子代理只在脑子里"想"了流程，产出物没有痕迹，无法交接、无法复核。

## 四、跨对话续接

上一轮对话结束时，skill 会（在满足条件时）在任务目录下生成 `<任务目录>/<slug>/HANDOVER.md`。新对话开场白直接用下面这段：

> 接着上次的活儿继续。先读 `<任务目录>/<slug>/HANDOVER.md` 与 `CHECKLIST.md`，然后按文件里的"下一步"执行。有不明白的先问我。

新一轮 agent 的 P0 阶段会自动走"续接流程"：读交接文档 → 核对代码现状 → 从断点继续，不会重头再来。

## 五、多 agent 并行协作

当一个大任务拆出互不依赖的子任务时：

1. 主 agent 先在 P3 完成整体清单拆解，再按子任务派发子代理。
2. **每个子代理使用独立的 `<task-slug>`**，避免清单文件互相覆盖。
3. 每个子代理的派发指令里都带上 3.1 模板。
4. 子代理返回后，主 agent 负责汇总到主清单并做 P5 独立评审 + P6 验证——**不能把子代理的"我完成了"直接当成完成**。

## 六、排障

| 现象 | 原因 | 处理 |
|------|------|------|
| 技能列表里看不到 | 目录里没有 `SKILL.md`，或缺 `name` / `description` | 补齐 frontmatter 与文件名 |
| 能看到但不自动触发 | 技能被关闭，或 `disable-model-invocation: true` | 在技能管理页开启；把字段改为 `false` |
| 触发了但没走流程 | 指令太模糊，agent 认为任务太小 | 改用显式点名，并声明档位（如"用标准档"） |
| 子代理没走流程 | 派发指令没点名技能 | 用 3.1 的模板重发 |
| 改完 skill 不生效 | 技能已被加载进上下文 | 开新对话，或让 agent 重新读取 SKILL.md |
