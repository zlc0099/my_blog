# 测试质量闭环协议 (Test Quality Loop)

本协议贯穿 P3-P7，与 P4 的 TDD 配合使用。核心立场：**测试的价值不在"通过"，而在"能拦住问题"**。一个全绿但测不到边界的测试套件，等于没有测试。

## 闭环全景

```
P3 定标准（DoD 含测试要求）
  → P4 TDD 守质量（红-绿-重构 + 反模式自查）
  → P5 评审查测试（测试质量作为独立评审维度）
  → P6 验证留证据（测试输出 + 覆盖说明）
  → 缺陷回流（运行期发现的问题固化为回归测试）
  → P7 记缺口（遗留测试债务写入清单，供下轮排期）
```

任何一环发现测试缺口，都回流到下一轮任务的 DoD——这就是"闭环"的含义：**测试债务有台账，不靠记忆。**

## 一、P3：把测试写进完成定义

- 每个原子任务的"验证方式"必须是**可执行的测试命令或明确的手动检查步骤**，不允许写"看起来正常"。
- DoD 中必须包含：核心路径有测试覆盖、涉及业务逻辑的改动有对应断言。
- 档位要求：
  - **精简档**：至少为改动点补一条验证（手动步骤也须写清操作与预期）。
  - **标准档**：业务逻辑必须有自动化测试。
  - **严格档**：完整测试覆盖（单元 + 集成），关键异常路径逐条有测试。

## 二、P4：TDD 执行时的测试质量标准

红-绿-重构照旧，但每个测试写完自查四条：

1. **测行为，不测实现** —— 断言对外可观察的结果（返回值、状态变化、副作用），不断言内部调用细节。实现重构后测试不该大面积挂。
2. **结构清晰（AAA）** —— Arrange-Act-Assert 三段分明；一个测试只验证一个行为；测试名说清"什么条件下预期什么"。
3. **覆盖边界与异常** —— 每个功能至少覆盖：正常路径、边界值（空 / 极大 / 临界）、异常路径（非法输入 / 依赖失败 / 权限不足）。只测 happy path 的测试套件不合格。
4. **确定性** —— 测试必须可重复：时间、随机数、网络、文件系统等外部因素要么 mock，要么注入控制；不依赖执行顺序；不依赖共享可变状态。

## 三、常见反模式（P4 自查 + P5 评审对照）

| 反模式 | 表现 | 危害 |
|--------|------|------|
| 无断言测试 | 跑一遍不崩就算过 | 零防护价值，虚假安全感 |
| 恒真断言 | `assert result is not None` 这类弱断言 | 拦不住真正的回归 |
| 测实现细节 | mock 层层嵌套、断言内部函数被调用 | 一重构测试全挂，维护成本压垮测试意愿 |
| 快照滥用 | 大段输出直接快照比对 | 挂了不知道哪错，被人无脑更新快照 |
| 时序侥幸 | 靠 sleep 等异步结果 | 间歇性失败（flaky），比没有测试更糟 |
| 共享状态 | 测试间靠执行顺序传递状态 | 单跑过、全跑挂，无法并行 |
| 删测试过构建 | 改不动就跳过 / 删除失败的测试 | **绝对禁止**，发现即阻塞 |

## 四、P5：测试质量作为独立评审维度

独立评审从两阶段扩为**三阶段**：

1. 规格符合度（原有）。
2. 代码质量（原有）。
3. **测试质量（新增）**：对照第三节反模式清单逐条检查；核对边界与异常路径是否覆盖；确认没有"为过而测"的弱断言；确认没有测试被跳过或删除（`git diff` 里出现的 skip / 删除须逐条说明理由）。

评审发现测试质量问题与代码质量问题**同等阻塞**，修复后复核。

## 五、P6：验证证据的测试部分

验证证据中测试相关输出必须包含：

- 完整测试命令与结果摘要（通过数 / 失败数 / 跳过数——**跳过的须逐条给理由**）。
- 新增/修改测试的清单（哪些行为现在有防护了）。
- 标准/严格档：关键路径覆盖说明（哪些分支有测试、哪些没有及原因）。

**证据红线**：测试全绿但存在未解释的 skip，不算通过；靠删除测试转绿的，禁止宣布完成。

## 六、缺陷回流（闭环的关键一环）

任何阶段（P6 验证、用户反馈、后续任务）发现的新缺陷：

1. 修复前先写一条**能复现该缺陷的失败测试**（这是 TDD 在 bug 场景的形态）。
2. 修复让该测试转绿，测试永久保留。
3. 缺陷与对应的回归测试记录进清单"决策日志"或调试线"验证证据"，形成"问题 → 防护"的映射。

效果：**每一个被发现过的 bug，都变成一条永久防线**，同类问题不会二度漏网。

## 七、P7：测试债务台账

收尾时在清单"遗留问题"中显式记录：

- 未覆盖的路径及原因（时间限制 / 低风险 / 依赖外部服务难 mock）。
- 存在的 flaky 测试及处理建议。
- 建议的测试改进方向（如"下轮给支付模块补集成测试"）。

这些记录在续接任务（P0）时被读取，优先纳入新任务的 DoD——债务清账，而不是烂在账本里。
