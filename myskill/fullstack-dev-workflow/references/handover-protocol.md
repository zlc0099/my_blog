# 新对话判定与交接协议 (Handover Protocol)

本协议用于 P7 阶段，也用于 P0 的续接场景。

## 一、为什么需要它

对话越长，上下文越容易失真：早期的澄清结论、设计取舍、被否掉的方案会逐渐被稀释，模型开始"忘事"或"自信地编"。**在正确的时机开新对话 + 一份高质量交接文档**，比硬撑长对话更可靠。

## 二、何时该开启新对话

满足以下**任意 2 条**即建议开新对话（满足任意 1 条硬信号则必须开）：

**硬信号（触发即开）**

- 一个独立的里程碑已完成并验证通过，下一个里程碑是相对独立的新话题。
- 上下文已明显拥挤：出现明显的早期信息遗忘、需要反复重复已确认过的结论。
- 话题发生根本切换（如从"写后端接口"切到"排查部署环境"）。
- 当前任务清单已全部完成，即将开始一份**新的、无依赖的**任务清单。

**软信号（凑够 2 条即开）**

- 本次对话内已完成 3 个以上较大任务。
- 工具输出噪音累积很多（大量日志、长文件读取），稀释了关键信息。
- 出现了与主线无关的支线讨论并已解决。
- 距离上次"干净起点"已过去很长一段工作。

**不该开的情况**

- 任务正处在修 bug 的中途、状态难以描述清楚时。
- 还剩 1-2 个紧耦合的小任务就能收尾时。
- 交接文档写不清楚（说明本来就还没到断点）。

## 三、交接文档规范

**HANDOVER.md 不是 P7 专属**：从 P4 第一批起，每批结束按活文档协议（`living-docs-protocol.md` 第三节）刷新"当前进度"与"下一步"两节——这样即使对话非正常中断，断点损失也最多一批。P7 时只做最终终态化。

写到 `<任务目录>/<task-slug>/HANDOVER.md`（任务目录按 SKILL.md"环境适配"确定），模板见 `assets/templates/handover.md`。

**必备八要素**（缺一不可）：

1. **任务目标**：一句话说清要做什么、为什么做。
2. **当前进度**：已完成 / 进行中 / 未开始，对照清单标注。
3. **已改动文件**：路径 + 一句话说明改了什么。
4. **关键决策与理由**：为什么这么选，避免下一轮推翻重来。
5. **假设登记**：当前依赖的未验证假设。
6. **未决问题**：还悬着的问题，标注是否 Blocking。
7. **下一步**：具体到"改哪个文件、做什么、怎么验证"。
8. **必备上下文**：下一轮必须知道的环境 / 命令 / 账号 / 路径 / 已知坑。

## 四、新对话怎么开

交接文档写完后，在回复中明确给出**一段可直接复制的开场白**，例如：

> 接着上次的活儿继续。先读 `<任务目录>/user-auth/HANDOVER.md` 与 `CHECKLIST.md`，然后按文件里的"下一步"执行。有不明白的先问我。

## 五、续接流程（P0 使用）

当检测到 `HANDOVER.md` / `CHECKLIST.md` 已存在时（含上一次对话**非正常中断**的场景，额外注意见 `living-docs-protocol.md` 第六节）：

1. 先读 `HANDOVER.md`，掌握目标、进度、决策、下一步。
2. 再读 `CHECKLIST.md`，确认任务状态。
3. 核对"已改动文件"当前是否与文档描述一致（`git status` / `git diff`）。
4. 若文档与代码不符，以代码为准，并向用户说明差异。
5. 从"下一步"继续，不要重头再来；如需重复已完成的步骤，先说明为什么。
