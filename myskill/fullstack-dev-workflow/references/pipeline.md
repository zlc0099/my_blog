# 流水线详解与 superpowers 对应关系

本文档是 `SKILL.md` 流水线的详细展开，说明每个阶段的动作、产出物、门禁条件，以及它与 superpowers 原始技能的对应。

## 与 superpowers 的逐项对应

| 本 skill 阶段 | superpowers 对应技能 | 关系 |
|---------------|----------------------|------|
| P1 澄清 | `brainstorming` | 等同。苏格拉底式追问，产出澄清结论而非直接写代码 |
| P2 设计定稿 | `brainstorming` 的输出 + 设计文档 | 等同。方案对比 + 设计文档落盘 |
| P3 任务清单 | `writing-plans` | 等同。拆成 2-5 分钟原子任务，标注文件路径与验证命令 |
| P4 执行 | `executing-plans` + `test-driven-development` + `subagent-driven-development` | 合并。分批执行 + TDD + 并行子代理 |
| P5 独立评审 | `requesting-code-review` / `receiving-code-review` | 等同。独立视角两阶段评审 |
| P6 验证 | `verification-before-completion` | 等同。完成前必须给出真实证据 |
| P7 收尾与交接 | `finishing-a-development-branch` + `remembering-conversations` | 扩展。新增"新对话判定 + 交接文档" |
| bug 修复路由 | `systematic-debugging` + `root-cause-tracing` | 扩展。独立调试线 D0-D5（复现 → 假设 → 验证 → 修复 → 回归），含并行子代理假设验证，见 `debugging-protocol.md` |
| 分支隔离 | `using-git-worktrees` | 简化。按档位强制新分支，严格档建议 worktree |
| 测试质量闭环 | `test-driven-development` + `testing-anti-patterns` + `defense-in-depth` | 扩展。独立测试协议（质量标准 + 反模式清单 + 评审三阶段 + 缺陷回流 + 测试债务台账），见 `testing-protocol.md` |
| 全局自动触发 | `verification-before-completion` | 融入 P6 与"架构红线复盘" |

**核心继承原则**（来自 superpowers）：

- 流程型技能优先级高于实现型技能。先定义"怎么做"，再决定"用什么做"。
- 未澄清需求与设计之前，不允许写业务代码。
- 证据优先于声明。
- 系统性优于临时性，简单性优先。
- 连续 3 次修不好触发架构级复盘。

## 阶段详解

### P0 触发与预检

**动作**

1. 识别任务类型（功能开发 / bug 修复）、档位与分支策略，向用户声明。bug 类路由到 `debugging-protocol.md` 的 D0-D5。
2. 读取项目上下文：README、依赖清单、目录结构、git 状态。
3. 完成环境探测，确定任务目录（TASK_DIR）；检查其下是否已有清单 / 交接文档；有则走续接流程。
4. 明确 in-scope / out-of-scope。

**产出**：一段简短的"任务预检"说明（任务类型、档位、分支、技术栈、续接与否、边界）。
**门禁**：无。但预检信息必须让用户可见。

### P1 澄清

**动作**：按 `clarification-protocol.md` 追问。
**产出**：澄清结论 + 假设登记。
**门禁**：存在 Blocking 级未决问题 → 禁止进入 P2。

### P2 设计定稿

**动作**：输出 2-3 套方案对比，推荐一套并说明理由；定稿写入 `DESIGN.md`。
**产出**：`DESIGN.md`。
**门禁**：用户未确认设计 → 禁止写代码。

### P3 任务清单

**动作**：按 `task-checklist.md` 模板拆解原子任务。
**产出**：`CHECKLIST.md`。
**门禁**：清单未落盘 → 禁止进入 P4。

原子任务判据：

- 能在 2-5 分钟内完成。
- 只涉及一个明确的文件或一个明确的函数/组件。
- 有可执行的验证方式（测试命令、构建命令、手动检查步骤首条）。
- 不依赖同批次其他任务的结果（否则应拆成有先后关系的两个任务）。

### P4 执行

**动作**

- 分批执行，每批 1-3 个任务，批间回清单更新状态。
- 业务逻辑改动走 TDD 红-绿-重构。
- 独立任务并行子代理。
- 范围守卫 + 回滚点。

**产出**：代码改动 + 清单状态更新 + 回滚点记录。
**门禁**：无（但每批结束必须更新清单并刷新 HANDOVER——活文档纪律见 `living-docs-protocol.md`）。

### P5 独立评审

**动作**：独立视角两阶段审查（规格符合度 → 代码质量）。
**产出**：评审批注 + 修复记录。
**门禁**：P0/P1 级问题未修复 → 禁止进入 P6。

### P6 验证

**动作**：运行真实命令，收集证据；连续 3 次失败触发架构复盘。
**产出**：验证证据（命令 + 关键输出）。
**门禁**：无证据 → 禁止宣布完成。

### P7 收尾与交接

**动作**：终态化清单、写决策日志、判定新对话、必要时写 `HANDOVER.md`、有长期价值的结论写入长期记忆（按环境适配）。
**产出**：终态 `CHECKLIST.md`（+ 可选 `HANDOVER.md`）。
**门禁**：无。

## 失败与回退处理

| 情况 | 处理 |
|------|------|
| 澄清中发现需求本身不成立 | 回到用户，说明矛盾点，请其确认目标 |
| 设计中方案全部不可行 | 扩大调研范围（读依赖源码 / 查官方文档）后重新给方案 |
| 执行中修 3 次仍失败 | 停止打补丁，按 `debugging-protocol.md` 升级规则回 D2 / P2 复盘根因或架构假设 |
| 验证中暴露新的需求 | 记入清单"发现事项"，问用户是否纳入本次范围 |
| 评审发现设计层面的缺陷 | 回 P2 修订设计（**先改 DESIGN.md 再改代码**，修订理由记决策日志）并更新清单 |
| 评审发现测试质量问题 | 与代码质量问题同等阻塞，修复后复核；禁止靠删测试 / 加 skip 转绿 |
| 调试中所有根因假设都被证伪 | 回 D2 扩大假设范围，仍无果则向用户汇报已排除项与卡点 |
| 用户明确要求跳过流程 | 走用户紧急通道（SKILL.md）：最小执行，保留"不删测试转绿 + 事后验证"底线，豁免记决策日志 |
