这套提示词面向后台管理系统的整体排版与布局优化，不针对某个具体业务模块。它统一的是全局导航、页面标题、内容容器、列表/表单/详情/统计页的布局方式、表格与组件规范、状态反馈和响应式策略。

重点是信息密度、阅读效率、操作路径和组件一致性，而不是把后台做成营销页或堆砌装饰。菜单数量、页面类型、字段、列数和业务结构仍由项目实际需求决定。

## 适合什么场景

- 企业管理系统、运营后台、工单/审批/任务/设备/内容管理。
- 已有后台需要统一排版、减少页面之间的结构差异。
- 需要同时优化列表、表单、详情、统计和配置页的后台项目。
- 需要在桌面、平板和移动端保持可用性的数据密集型系统。

不适合营销官网、展示型落地页或没有真实业务数据却需要虚构统计的页面。

## 视觉构成

- **全局框架**：侧边导航 + 顶部栏 + 内容容器 + 全局反馈层，保持清晰的层级关系。
- **页面类型**：列表页突出筛选与表格，表单页突出分组与校验，详情页突出摘要与关联记录，统计页突出指标与趋势。
- **密度与对齐**：统一间距节奏、字号层级、表格行高、列对齐和操作区位置。
- **组件复用**：页面标题、筛选栏、表格工具栏、状态标签、分页、弹窗和抽屉保持统一行为。
- **状态完整**：加载、空数据、错误、权限不足、成功和失败都要有明确反馈。
- **响应式**：桌面优先，平板压缩辅助区，移动端调整导航、表格和表单，而不是整体缩小。

## 使用边界

- 不强行把列表、表单、详情和统计做成同一种卡片模板。
- 不删除现有菜单、权限规则、接口契约或业务功能。
- 不为每个字段增加无意义边框、阴影和装饰。
- 不虚构实时统计、成功状态、权限或接口响应。
- 表格、分页、筛选、弹窗和危险操作确认必须真实可用。
- 修改全局布局或公共组件后，要检查依赖页面是否回归。

## 完整提示词

````prompt
# Agent 通用提示词：后台管理系统 UI 排版与布局规范

## 一、任务目标

请基于当前项目，统一规划并优化后台管理系统的整体 UI 排版、页面布局、组件规范和交互体验。

本任务的核心是建立一套可复用、可扩展、符合实际业务的后台管理系统设计体系，使整个系统具备：

- 清晰的信息架构与导航层级。
- 统一的页面布局和视觉规范。
- 合理的数据表格、筛选表单和编辑表单。
- 一致的详情页、弹窗、抽屉和操作反馈。
- 良好的信息密度与阅读效率。
- 完整的桌面端、平板端和移动端适配策略。
- 统一的加载、空数据、异常、成功和失败状态。
- 易于维护、扩展和复用的前端组件结构。

不要只输出设计方案、静态原型或代码片段。应结合当前项目的技术栈和实际代码，完成必要的布局优化、组件实现和页面调整。

本提示词只规定通用布局原则，不限制具体业务、页面数量、菜单数量、组件数量或模块结构。

## 二、开发前的项目分析

开始修改代码之前，先检查当前项目。

1. 识别当前使用的前端框架、构建工具、UI 组件库、路由方案、状态管理和样式体系。
2. 检查现有后台布局、菜单结构、页面入口和公共组件。
3. 分析已有页面的业务类型，例如列表、详情、表单、统计、配置或流程管理。
4. 检查现有权限、登录、路由守卫、接口封装和数据请求逻辑。
5. 确认已有的设计规范、颜色变量、间距体系和公共样式。
6. 优先复用现有组件和依赖，不得为了统一视觉而无理由更换技术栈。
7. 未经授权，不得修改无关业务模块、数据库结构、接口契约或后端逻辑。
8. 对于现有功能，应在保持业务行为不变的前提下优化布局和交互。

完成分析后，根据项目实际情况确定需要修改的范围，不要机械地将所有页面强行改造成同一种结构。

## 三、整体布局架构

后台管理系统应建立统一的全局布局，通常由以下部分组成：

- 全局侧边导航。
- 顶部导航栏。
- 页面主体区域。
- 页面标题与操作区域。
- 页面内容容器。
- 必要的面包屑导航。
- 消息提示、弹窗、抽屉等全局交互层。

具体结构应根据项目现有设计和业务复杂度确定。

### 3.1 侧边导航

侧边导航用于组织系统功能和页面层级。

设计要求：

- 使用清晰的一级菜单与必要的二级菜单。
- 菜单名称应简洁、明确，符合业务语义。
- 当前路由对应的菜单必须具有明显的选中状态。
- 展开、收起和切换状态应保持一致。
- 图标应与菜单含义对应，避免随意混用不同风格的图标。
- 菜单数量较多时，应支持合理的分组和层级组织。
- 菜单过长时，应允许导航区域独立滚动。
- 侧边栏折叠后，应保留必要的图标提示和可访问性。
- 不得因为优化 UI 而删除原有菜单或修改原有权限规则。

宽度应根据实际导航内容确定，避免过窄导致菜单频繁换行，也不要过宽挤压主体区域。

如果项目已有成熟的导航布局，应优先在现有基础上优化，而不是重新实现一套重复的导航系统。

### 3.2 顶部导航栏

顶部导航栏主要承载全局级别的操作。

可根据项目需要包含：

- 侧边栏折叠按钮。
- 面包屑导航。
- 页面或系统标识。
- 全局搜索。
- 通知消息。
- 帮助入口。
- 用户头像与账户菜单。
- 主题切换或语言切换。
- 其他必要的全局操作。

要求：

- 高度适中，避免占用过多垂直空间。
- 元素应按功能分组排列。
- 用户信息和退出登录等操作应具有清晰的菜单层级。
- 不应将所有业务操作都堆积在顶部。
- 当视口较窄时，应合理隐藏次要入口或折叠为菜单。

### 3.3 主内容区域

主内容区域是后台系统的核心工作空间。

要求：

- 与导航栏保持清晰的布局关系。
- 具有统一的左右内边距和内容宽度规则。
- 根据页面内容合理分配可用空间。
- 避免页面内容紧贴屏幕边缘。
- 避免无意义的巨大留白。
- 避免固定高度导致内容被截断。
- 页面高度应优先适应内容。
- 表格等确实需要独立滚动的区域，可以单独控制滚动行为。

对于复杂的数据管理页面，应优先保证信息密度、内容对齐和操作效率。

### 3.4 页面标题区域

每个主要业务页面应有清晰的标题区域。

通常包括：

- 页面标题。
- 简短的页面说明（确有必要时）。
- 面包屑导航（根据层级和现有规范决定）。
- 主要操作按钮。
- 次要操作入口。

布局要求：

- 标题应具有明确的视觉层级。
- 主要操作应放在容易发现的位置。
- 次要操作应避免与主要操作争夺注意力。
- 页面说明不应重复标题表达的信息。
- 标题与下方内容之间应保持统一的间距。

如果页面很简单，可以使用紧凑标题区域；如果页面需要多个重要操作，可以采用标题与操作区左右分布的布局。

## 四、建立统一的页面布局类型

不同业务页面应根据任务类型选择合适的排版方式，而不是所有页面使用完全相同的模板。

### 4.1 数据列表页

适用于用户、订单、任务、设备、内容、工单、日志等数据管理场景。

推荐结构：

1. 页面标题与主要操作。
2. 筛选和搜索区域。
3. 可选的统计摘要区域。
4. 数据表格工具栏。
5. 数据表格。
6. 分页和数据量信息。

具体结构根据业务复杂度确定，不要求每个列表页都必须包含所有区域。

布局要求：

- 筛选条件应按照业务相关性分组。
- 常用筛选项优先展示。
- 不常用的筛选项可以放入展开区域。
- 搜索、重置和查询操作应具有清晰的行为。
- 新增、导入、导出等主要操作应放在容易发现的位置。
- 表格应优先保证关键字段可读。
- 操作列应保持合理宽度。
- 长文本应提供合适的换行、截断或详情查看方式。
- 分页、排序和筛选应具有一致的交互逻辑。
- 不要为每个字段添加无意义的边框和装饰。

### 4.2 数据表格

建立统一的数据表格规范。

应考虑：

- 表头与数据行的对齐。
- 列宽与内容长度。
- 行高和信息密度。
- 排序状态。
- 选中状态。
- 状态标签。
- 行内操作。
- 多选操作。
- 空数据状态。
- 加载状态。
- 请求失败状态。
- 分页。
- 横向滚动。
- 固定列或固定表头（确有必要时）。

具体要求：

1. 表头应容易识别，但不要使用过重的背景和边框。
2. 同类数据应保持一致的对齐方式。
3. 数字、金额、时间、状态等字段应采用统一格式。
4. 不应让每个单元格都充满按钮。
5. 高频操作可以直接展示，低频操作可以收纳到更多操作菜单中。
6. 删除等危险操作应有明确的确认机制。
7. 数据量较大时，应合理使用分页或项目现有的虚拟滚动方案。
8. 不得仅通过颜色区分重要状态，还应提供文字或其他辅助标识。
9. 在移动端无法完整展示表格时，应根据业务选择横向滚动、列优先级调整或适当的卡片式展示。

### 4.3 新增与编辑表单页

适用于创建、修改、配置和维护业务数据。

推荐结构：

- 页面标题和返回入口。
- 表单分组。
- 字段标签与输入控件。
- 必填与校验提示。
- 相关说明。
- 底部或顶部操作区。

布局要求：

- 相关字段应归入同一逻辑分组。
- 不要将所有字段堆在一个无分组的长表单中。
- 简单表单可以采用紧凑的单列或双列布局。
- 复杂表单应根据字段数量、依赖关系和阅读顺序决定分组方式。
- 标签、输入框、选择器和说明文字应保持对齐。
- 必填标识和校验错误应清晰。
- 只读字段与可编辑字段应具有明确区别。
- 对存在依赖关系的字段，应明确其联动逻辑。
- 保存、取消、重置等操作应具有一致的位置和行为。
- 离开存在未保存修改的页面时，应按项目需求处理确认逻辑。

表单字段的数量、分组数量和布局列数应根据实际业务决定，不要为了视觉统一强制所有表单使用相同列数。

### 4.4 详情页

适用于订单详情、用户详情、设备详情、工单详情、任务详情等场景。

应根据业务选择合适的布局，可以包含：

- 标题与核心状态。
- 关键业务操作。
- 核心信息摘要。
- 基础信息。
- 关联数据。
- 处理记录。
- 操作日志。
- 附件或图片。
- 时间线。
- 相关记录列表。

要求：

- 最重要的信息应优先展示。
- 不同类型的信息应进行合理分组。
- 长内容不应全部挤在同一行。
- 关联数据应具有清晰的跳转方式。
- 复杂详情可以使用标签页、分区或侧栏，但不要无意义地增加层级。
- 返回列表时，应尽可能保留合理的筛选和分页上下文。
- 详情页的操作必须遵循现有业务权限和状态规则。

### 4.5 统计与仪表盘页面

适用于运营数据、业务概览、任务监控和统计分析。

应根据实际数据选择：

- 核心指标。
- 趋势图表。
- 分类统计。
- 排名或分布。
- 最近活动。
- 关键业务列表。
- 时间范围筛选。

布局要求：

- 优先突出真正重要的指标。
- 图表应有明确的标题、单位、时间范围和必要的说明。
- 不要单纯为了丰富页面而堆叠大量指标卡。
- 不同图表之间应具有合理的视觉层级。
- 图表配色应统一且有可读性。
- 缺失数据时应展示明确的空状态。
- 不能使用虚构的实时数据冒充真实业务数据。
- 图表区域应根据可用宽度合理调整，不应发生文字遮挡或图例溢出。

### 4.6 配置与设置页面

适用于系统参数、个人偏好、业务规则和基础配置。

要求：

- 按配置主题进行分组。
- 清晰区分当前值、可编辑值和说明。
- 高风险配置应提供必要的确认。
- 保存后应提供明确反馈。
- 对影响范围较大的配置，应说明必要的业务影响。
- 不应让简单配置散落在多个没有关联的页面中。
- 配置项数量和层级应以真实业务需求为准。

## 五、设计系统与样式规范

### 5.1 整体视觉方向

后台管理系统应优先保证：

1. 清晰的信息层级。
2. 高效的数据阅读。
3. 统一的组件规范。
4. 合理的空间利用。
5. 可靠的操作反馈。
6. 易于长期维护的视觉体系。

不要为了追求所谓的高级感而降低可读性。

根据项目的品牌定位，可以采用简洁商务、现代科技、工业风、轻量化运营后台或其他适合的风格，但整个系统必须保持一致。

### 5.2 色彩规范

建立统一的颜色体系，包括：

- 品牌主色。
- 次要强调色。
- 页面背景色。
- 内容表面色。
- 主要文字色。
- 次要文字色。
- 边框色。
- 悬停色。
- 选中色。
- 成功色。
- 警告色。
- 错误色。
- 信息提示色。

色彩应通过统一的设计变量或主题配置进行管理。

状态颜色必须具有明确含义，并在整个系统中保持一致。

不要让每个页面自行选择颜色，也不要依赖大量高饱和色来区分普通内容。

### 5.3 字体与文字层级

统一以下文字规范：

- 页面主标题。
- 分区标题。
- 卡片标题。
- 表格表头。
- 表格正文。
- 表单标签。
- 辅助说明。
- 状态标签。
- 按钮文字。
- 时间、编号和统计数据。

要求：

- 中文优先使用清晰易读的字体。
- 正文不宜过小。
- 标题与正文之间应有明显层级差异。
- 长文本应具有合理的行高。
- 数字和时间格式应保持一致。
- 避免随意混用多种字体和过多字重。
- 不能只通过字体颜色表达字段是否重要或是否异常。

### 5.4 间距与尺寸

建立统一的间距体系，并合理应用于：

- 页面外边距。
- 页面标题与内容之间。
- 分区之间。
- 卡片内部。
- 表单字段之间。
- 表格单元格。
- 按钮组。
- 弹窗与抽屉。
- 工具栏。

整体原则是同类页面保持相近的空间节奏，不同复杂度的页面可以采用不同的密度。

不要机械地为所有区域设置相同的内边距。

### 5.5 圆角、边框与阴影

- 控制圆角种类和大小。
- 避免每个元素都使用大圆角。
- 普通内容区域以清晰的边界和合理的间距为主。
- 阴影应轻量且具有明确的层级意义。
- 弹窗、下拉菜单和浮层应具有合理的层级区分。
- 不要大量使用强烈的发光、渐变和装饰边框。

## 六、组件统一与复用

在现有技术栈允许的情况下，统一以下公共组件：

- 页面容器。
- 页面标题区。
- 面包屑。
- 筛选表单。
- 搜索栏。
- 表格工具栏。
- 数据表格。
- 分页。
- 状态标签。
- 表单字段。
- 表单分组。
- 弹窗。
- 抽屉。
- 确认对话框。
- 消息提示。
- 空状态。
- 加载状态。
- 错误状态。
- 时间线。
- 文件上传。
- 详情信息分组。

实施要求：

1. 优先复用现有组件库。
2. 对重复出现的布局进行合理抽象。
3. 不要为单个页面的特殊需求设计过度通用的复杂组件。
4. 不要为了组件复用而破坏不同业务页面的合理差异。
5. 公共组件的样式应保持统一。
6. 修改公共组件时，应检查其他使用该组件的页面，避免引入回归问题。
7. 对组件的默认行为、参数和交互状态进行必要的规范化。

## 七、交互与操作反馈

所有交互必须有真实、明确且符合业务语义的反馈。

### 常规交互

- 按钮点击应执行对应操作。
- 表格行操作应与当前数据关联。
- 查询和重置应具有明确的行为。
- 分页切换应正确更新展示数据。
- 排序和筛选应与数据逻辑一致。
- 弹窗和抽屉应支持正常关闭。
- 表单校验应在合适的时机触发。
- 保存成功和失败应有明确提示。
- 危险操作应有必要的确认步骤。

### 状态管理

针对真实存在的异步操作，合理提供：

- 加载状态。
- 禁用状态。
- 成功状态。
- 失败状态。
- 空数据状态。
- 网络异常状态。
- 权限不足状态。
- 操作结果反馈。

不要使用纯视觉交互代替实际业务逻辑。

如果后端接口暂时不可用，应保留清晰的接口边界，使用明确标识的演示数据或合理的空状态，不得伪造真实成功结果。

## 八、响应式适配

### 桌面端

- 保证侧边栏、顶部导航和内容区域比例合理。
- 充分利用可用宽度。
- 让复杂表格和多列表单具有良好的阅读体验。
- 避免内容区域过宽导致信息阅读困难。

### 平板端

- 根据可用宽度调整侧边栏。
- 合理压缩不重要的间距。
- 必要时将多列表单调整为单列或双列。
- 避免操作按钮互相挤压。

### 移动端

- 根据项目业务决定导航折叠、抽屉式导航或其他适配方式。
- 表格应采用适合小屏幕的展示策略。
- 表单应优先保证输入效率。
- 操作按钮应具有足够的触控面积。
- 弹窗、抽屉和下拉菜单不得超出屏幕。
- 避免固定宽度造成横向溢出。
- 不能简单地将桌面端整体缩小。

响应式规则应结合真实页面检查，而不是只添加媒体查询后就认为完成。

## 九、可访问性与易用性

- 使用语义正确的 HTML 元素。
- 保证键盘可以访问重要操作。
- 提供清晰的焦点状态。
- 输入控件具有明确的标签。
- 错误提示应能够被用户理解。
- 颜色对比度应满足基本可读性要求。
- 图标按钮应具有可理解的名称。
- 不应只通过颜色表达状态。
- 表单错误应尽可能指出具体字段及修复方法。
- 危险操作应清楚表达操作对象和影响。

## 十、工程约束

- 遵循当前项目已有的技术栈、路由和组件组织方式。
- 不要擅自更换框架、UI 组件库或状态管理方案。
- 不要随意修改后端接口契约、数据库结构和权限逻辑。
- 不要破坏已有业务功能。
- 不要删除未被明确要求修改的模块。
- 避免重复实现已有的公共能力。
- 避免全局 CSS 污染其他页面。
- 避免过度抽象和无必要的依赖。
- 不要只生成静态页面而忽略现有数据流。
- 不要将整个系统的所有页面强行套用同一套内容结构。

如果需要调整全局布局，应先明确影响范围，并验证依赖该布局的页面是否正常。

## 十一、执行流程

### 阶段一：分析

- 检查项目结构。
- 确认技术栈和现有设计体系。
- 梳理导航、页面类型和公共组件。
- 识别主要排版问题与重复实现。
- 明确允许修改的范围。

### 阶段二：规划

- 制定全局布局方案。
- 统一色彩、字体、间距和组件规范。
- 识别适合复用的公共布局。
- 按实际业务确定列表、表单、详情和统计页面的布局方式。
- 制定响应式策略。

### 阶段三：实施

- 优先优化全局布局。
- 建立或完善公共设计规范。
- 按页面类型优化排版。
- 统一公共组件和交互状态。
- 保持现有业务逻辑正常运行。
- 处理不同屏幕尺寸下的布局问题。

### 阶段四：验证

- 检查项目能否正常启动。
- 检查路由和导航是否正常。
- 检查表格、筛选、分页和表单行为。
- 检查弹窗、抽屉及危险操作确认。
- 检查权限和接口逻辑是否被意外改变。
- 检查常见屏幕尺寸下的布局。
- 检查控制台错误、样式冲突和资源加载问题。
- 修复本次修改引入的问题。

### 阶段五：交付

完成后说明：

- 修改了哪些布局和页面。
- 新增或复用了哪些公共组件。
- 统一了哪些视觉规范。
- 哪些交互已完成并经过验证。
- 是否存在尚未完成的功能。
- 是否需要额外的接口、配置或业务确认。

## 十二、最终验收标准

最终实现必须满足以下要求：

1. 整个后台具有统一、清晰的全局布局。
2. 页面标题、内容区域、操作区和导航层级明确。
3. 列表、表单、详情、统计等不同页面具有适合各自业务的布局。
4. 表格、表单、状态标签、弹窗和分页等组件表现一致。
5. 主要操作具有真实行为和明确反馈。
6. 加载、空数据、异常和错误状态得到合理处理。
7. 桌面端与移动端均不存在明显布局问题。
8. 不破坏原有业务逻辑、接口契约和权限规则。
9. 公共组件具有合理的复用性和可维护性。
10. 实际代码已经完成修改和检查，而不是仅提供建议。

最终目标是建立一套适用于当前项目的、统一而不僵化的后台管理系统排版体系。应以业务可用性为基础，以信息层级和操作效率为核心，以视觉一致性为保障，并在保持现有工程稳定性的前提下完成实际开发。
````
