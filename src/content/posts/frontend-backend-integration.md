前后端分开开发时，联调阶段最耗时间的往往不是「接口报错」，而是双方都以为接口是对的。

前端按文档传了 `pageSize`，后端实际只认 `size`；接口返回了统一包装 `{ code, data, message }`，前端却直接读 `data.list`；列表能查出来，但新增之后详情页读不到；未登录时返回 200 加一段错误文案，前端却当成成功数据渲染。这类问题单测和接口自测都不容易发现，只有把请求契约、业务状态和页面行为放在一起对，才会暴露。

这篇记录整理一遍我实际会走的联调顺序，最后附上完整的 Agent 提示词。

## 先确认真实契约，不要只信文档

开始改任何一边之前，先把三份东西对齐：

1. 前端页面实际发出的请求：URL、HTTP 方法、路径参数、查询参数、请求体、`Content-Type`、认证头。
2. 后端实际接收和处理的内容：Controller 映射、DTO 校验、Service 业务规则、统一响应结构、异常处理。
3. 文档或工单里写的接口约定。

三者不一致时，不要默认文档对，也不要默认代码对。先记录差异，再看业务预期和调用方，确定哪一边需要调整。涉及接口契约、数据库结构或权限规则的修改，先说明影响范围并确认，不能为了联调方便直接改掉。

## 接口清单至少记录这些

按业务模块整理，而不是按 Controller 数量罗列：

| 维度 | 要确认的内容 |
|---|---|
| 模块与用途 | 所属业务、前端调用位置、解决什么问题 |
| 请求 | 方法、路径、参数名、类型、必填、格式、分页字段 |
| 后端逻辑 | 校验、计算、状态变化、写入了哪些表 |
| 响应 | 包装结构、字段名、类型、空值、枚举、日期格式 |
| 权限 | 登录态、角色、数据归属、越权访问 |
| 异常 | 参数错误、记录不存在、状态冲突、重复提交、下游失败 |
| 状态 | 待分析、待确认、待联调、联调失败、已验证、暂缓 |

状态不是为了好看，而是为了知道哪些接口真的验证过、哪些只是「看起来能请求」。

## 联调时优先检查的七类问题

1. **请求不匹配**：URL、方法、参数名、类型、请求格式或 `Content-Type` 不一致。
2. **响应不匹配**：统一包装、DTO/VO 字段、空值、枚举、日期、分页结构不一致。
3. **业务逻辑问题**：接口能调通，但状态流转、数据持久化或关联记录不对。
4. **认证与权限问题**：Token 传递、登录状态、角色权限、数据归属或越权处理异常。
5. **异常处理问题**：参数校验、数据不存在、重复提交、状态冲突或下游异常时响应不符合约定。
6. **数据库问题**：查询结果、关联数据、事务、分页或写入后读取不一致。
7. **前端解析问题**：字段路径、错误处理、空数据分支和页面状态与后端真实返回不一致。

优先修复后端自身的问题；如果确认问题属于前端请求或展示逻辑，再给出前端修改建议，并分别记录根因，不要把所有问题都归到后端。

## 不要只测单个接口

一个接口返回 200，不代表业务闭环成立。至少要走一遍真实流程：

- 创建或提交 → 数据库真实写入 → 详情接口能读到 → 列表/统计/关联记录同步更新。
- 修改 → 允许改的字段变了，不允许改的字段没变 → 关联数据一致。
- 删除 → 逻辑删除或物理删除符合设计 → 已删除数据不能被正常接口访问。
- 失败/回滚 → 多步操作中途失败后，事务内的数据保持一致。
- 重复提交/并发 → 不产生重复记录、重复副作用或状态覆盖。
- 权限 → 未登录、无权限、跨数据范围访问都被正确拒绝。

测试要保留真实命令和结果；失败时继续定位根因，不能通过屏蔽异常、删除测试或放宽断言来制造通过。

## 什么才算联调完成

我会用下面几条判断，而不是「页面能打开」：

- 请求和响应契约一致，字段类型、空值、枚举、日期和分页都能被前端正确解析。
- 后端业务规则、状态流转和数据库结果符合预期，而不是只返回了成功状态。
- 认证和权限在真实调用中有效，前端隐藏按钮不能替代后端校验。
- 参数错误、无权限、数据不存在、重复提交和下游失败有合理响应。
- 核心业务流程经过真实测试，前后端都能完成预期交互。
- 未完成、待确认和被环境阻塞的项目有明确记录。

## 常见坑

- 只按文档联调，没有核对真实代码；文档和实现已经漂移。
- 只看 HTTP 200，不看业务码、`data` 结构和数据库结果。
- 分页参数名、页码从 0 还是 1 开始、总数计算不一致。
- 日期时区和格式不一致，前端显示与后端存储对不上。
- 枚举值在前后端各有一套映射，状态颜色对了但业务值错了。
- 只测正常路径，不测未登录、无权限、记录不存在和重复提交。
- 为了联调方便改接口契约或绕过校验，影响其他调用方。

## 使用方式

这份提示词适合在后端接口基本完成、前端开始接入或联调验收时使用。使用前准备好接口文档、前后端代码、测试环境、测试账号和核心业务流程；没有前端代码或测试环境时，可以完成契约核对，但不能声称已经完成端到端联调。

完整提示词放在文末，可以直接作为 Agent 的联调工作约束使用。

## 完整提示词

````prompt
# 前后端接口对接与联调 Agent 提示词

## 一、任务目标

请针对当前项目进行前后端接口对接检查与联调，确保前端页面、请求参数、后端接口、业务逻辑、数据库及响应数据之间形成完整闭环。

当前以**后端独立开发和接口适配为主**。优先修复后端自身的问题；只有确认问题属于前端请求或展示逻辑时，才提出对应修改建议。

开始前先阅读项目现有代码、开发工单、接口文档及相关配置，不得凭猜测修改接口。

## 二、执行流程

### 第一步：分析现有接口与调用关系

1. 阅读前端相关页面、API 请求封装、路由、状态管理及调用代码。
2. 阅读后端 Controller、Service、DTO、VO、实体、Mapper、统一响应结构及权限配置。
3. 对照现有接口文档、项目工单和数据库结构，梳理真实接口契约。
4. 检查请求方法、URL、路径参数、查询参数、请求体、响应字段、数据类型、分页结构、错误码、身份认证及权限要求。
5. 如果接口文档与实际代码不一致，记录差异并分析正确的业务预期，不要擅自认定其中一方必然正确。

### 第二步：建立接口对接清单

按业务模块整理接口清单，每个接口至少记录：

- 所属模块、业务功能及前端调用位置。
- HTTP 方法与接口路径。
- 请求参数、字段类型、必填规则及校验要求。
- 后端实际处理逻辑与数据库操作。
- 响应结构、字段含义及前端使用方式。
- 身份认证、权限和业务状态限制。
- 当前对接状态、问题描述及修复方案。

建议使用以下状态：`待分析`、`待确认`、`待联调`、`联调失败`、`已验证`、`暂缓处理`。

### 第三步：逐项检查并修复接口问题

重点排查以下问题：

1. **请求不匹配：** URL、HTTP 方法、参数名称、数据类型、Content-Type 或请求格式不一致。
2. **响应不匹配：** 统一响应包装、DTO/VO 字段、空值处理、枚举值、日期格式及分页结构不一致。
3. **业务逻辑问题：** 接口可以调用，但业务规则、状态流转、数据持久化或关联模块处理不正确。
4. **认证与权限问题：** Token 传递、登录状态、角色权限、数据归属及越权访问处理异常。
5. **异常处理问题：** 参数校验失败、数据不存在、重复提交、状态冲突及下游服务异常时，响应不符合约定。
6. **数据库问题：** 查询结果错误、关联数据缺失、事务不完整、分页不准确或写入后读取不一致。
7. **前端调用兼容问题：** 前端使用的字段、响应路径、错误处理方式与后端实际返回不一致。

优先修复后端自身的问题。若需要修改接口契约、数据库结构或影响其他模块的业务逻辑，先说明原因、影响范围和兼容方案，并向开发人员确认。

### 第四步：执行接口联调与业务闭环测试

按照实际业务流程逐项验证，不要只测试单个接口。

每个核心接口至少检查：

- 正常请求是否返回预期数据。
- 缺失参数、非法参数、边界值是否被正确处理。
- 未登录、无权限及数据不存在时是否正确响应。
- 新增、修改、删除、查询是否与数据库实际状态一致。
- 分页、排序、筛选及关联数据是否正确。
- 业务状态变更后，下游接口和相关页面能否正确获取新状态。
- 重复请求、异常中断及事务回滚是否符合业务要求。
- 前端能否正确解析响应并完成预期交互。

优先复用现有测试环境、测试账号和测试数据。涉及真实外部服务、不可逆操作或可能污染共享数据的测试，必须先确认执行条件。

### 第五步：回归验证并更新文档

每完成一个接口或一组强关联接口的修复：

1. 执行对应的接口测试和必要的业务闭环测试。
2. 检查相邻接口、共享 DTO/VO、统一响应封装及相关模块是否受到影响。
3. 更新接口清单和开发工单，记录修改文件、测试命令、真实结果及遗留问题。
4. 测试失败时继续定位根因，不得通过屏蔽异常、删除测试或降低断言来制造通过结果。

## 三、执行约束

- 不得为了方便联调而擅自更改既有接口契约。
- 不得随意修改与当前对接任务无关的前端页面或后端模块。
- 不得绕过权限校验、业务校验或数据库约束。
- 不得伪造接口返回、数据库结果或测试记录。
- 如果前后端均有问题，应分别记录根因和修复建议，不要将所有问题归因于后端。
- 如果缺少前端代码、接口文档、测试环境或必要凭据，应明确说明当前可验证范围及阻塞原因。
- 发现需求歧义时，先向开发人员确认预期行为，再实施存在风险的修改。

## 四、最终交付

完成后输出《前后端接口对接与联调报告》，建议保存到项目现有文档目录；若没有统一规范，可使用 `docs/integration/frontend-backend-integration-report.md`。

报告必须包含：

1. 项目接口现状与涉及的业务模块。
2. 接口清单及每个接口的联调状态。
3. 发现的问题、根因、影响范围及修复方案。
4. 已修改的文件、接口契约和业务逻辑。
5. 实际执行的测试、结果及失败原因。
6. 核心业务闭环验证结果。
7. 尚未解决的问题、待确认事项和下一步建议。

**最终验收标准：** 核心接口的请求与响应契约一致，业务逻辑和数据库行为符合预期，认证及权限有效，异常情况得到合理处理，相关业务流程经过真实验证，所有未完成事项均有明确记录。

未经开发人员明确授权，不得执行 Git 远程推送或其他会发布代码、影响外部环境的操作。
````
