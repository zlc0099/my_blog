这不是一份「帮我补几个单元测试」的提示词。

它要求 Agent 在写测试之前先读懂业务、接口、数据库结构和状态规则，再围绕真实业务流程建立测试矩阵，最后用可重复执行的测试代码、真实数据库变化和执行结果证明业务是否闭环。重点不是覆盖率数字，而是「正常路径、异常路径、数据一致性、后续查询」是否都得到了验证。

## 这份提示词解决什么问题

后端最容易出现的问题，往往不是接口报错，而是「接口返回成功，但业务没有真正完成」：

- 主表写入了，关联记录没生成。
- 状态改了，后续查询、统计或下游模块没有同步。
- 参数校验只在 Controller 做，Service 被直接调用时绕过。
- 多步操作中某一步失败，事务没有按预期回滚。
- 重复提交创建了重复数据，或者重复执行了不可重复的副作用。
- 用户只能看到自己的菜单，却可以通过替换 ID 访问别人的数据。
- 定时任务或消息消费失败后，业务永久停在「处理中」。
- 测试只断言 HTTP 200，没有验证数据库和业务结果。

这份提示词把这些检查点组织成一条可追溯的验证链：业务规则 → 接口/流程 → 测试用例 → 执行结果 → 缺陷与修复 → 最终结论。

## 什么时候使用

适合在以下场景使用：

- 一个业务模块刚开发完，准备提交测试或上线前验收。
- 修复了一个涉及状态、金额、权限或关联数据的 Bug，需要做回归验证。
- 重构 Service、Mapper、事务边界或消息处理逻辑，需要证明行为没有改变。
- 怀疑列表、详情、统计、关联记录之间存在数据不一致。
- 需要审查遗留代码的测试是否真的有效，而不只是「测试能跑」。
- 需要把一个跨多个接口、多个模块的业务流程串起来做端到端验证。
- 需要在交付前拿到一份包含失败证据、未覆盖范围和风险的测试报告。

它也适合让 Agent 帮你梳理一个陌生项目的接口清单和业务闭环，但前提是能提供代码、数据库结构和可运行的测试环境。

## 什么时候不适合

- 只做前端 UI、视觉或纯静态页面验证时，这份提示词过重。
- 没有可运行的测试环境、测试数据库或必要权限时，不能靠它得出「业务已通过」的结论。
- 需要在真实生产环境执行删除、并发写入、设备控制、支付或短信等破坏性/外部操作时，不应直接使用。
- 业务规则本身还没有确认时，不应让 Agent 自行编造预期结果；这类问题应列为待确认事项。
- 仅仅想生成几个示例测试代码、不打算执行时，也不适合使用完整流程。

## 使用前需要准备什么

为了让结果可验证，尽量提供：

- 后端技术栈、模块划分、启动方式和测试命令。
- 核心业务需求、状态定义、权限规则和异常处理约定。
- 数据库表结构、关联关系、约束和必要的测试数据。
- 接口清单或至少 Controller/Service 的入口范围。
- 可用的测试数据库或隔离环境，以及测试账号和角色。
- 外部依赖的处理方式：测试替身、沙箱、假服务或明确的可控环境。
- 本次允许修改的范围，以及明确不能改动的接口契约、权限或生产配置。

如果某些信息缺失，应在报告中明确列为假设或待确认项，而不是默默补全。

## 它会怎么工作

提示词会按以下顺序约束执行：

1. 先审查项目结构、接口、数据库、状态和现有测试。
2. 建立核心业务流程清单和业务闭环测试矩阵。
3. 分别设计单元、集成、API、端到端、安全、并发与异步测试。
4. 执行测试并保留真实结果，验证数据库和后续查询。
5. 对失败用例记录复现条件、预期结果、实际结果和影响。
6. 在授权范围内做最小修复，并补充防回归测试。
7. 输出覆盖情况、缺陷清单、未覆盖范围和最终结论。

它特别强调：不能删除失败用例、放宽断言、为了变绿修改业务规则，或者把未执行/被阻塞的测试写成通过。

## 如何判断输出是否合格

一份合格的交付至少要能回答：

- 核心业务有哪些，分别覆盖了哪些正常、异常和回退路径？
- 每个结论对应哪个测试用例、哪次执行结果、哪条业务规则？
- 数据库真实状态是否被验证，而不只是接口响应？
- 事务失败、重复请求、并发更新时数据是否仍然一致？
- 权限不足、数据越权、未登录访问是否被正确拒绝？
- 哪些测试没有执行、被环境阻塞或仍待业务确认？
- 最终结论是「通过」「有条件通过」「不通过」还是「无法判定」？

如果报告只有测试数量、覆盖率数字和「全部通过」，却无法追溯到具体业务结果，这份测试就不能算完成。

## 安全与边界

- 只在授权的测试环境执行；不连接生产数据库做破坏性测试。
- 不使用真实生产密钥，不向真实用户发送通知，不对真实设备或支付系统发请求。
- 不把真实账号、令牌、内部地址或敏感数据写入测试代码和报告。
- 生产代码修复应保持最小范围，接口契约、数据库结构和权限规则未经确认不得擅自修改。
- 外部依赖、异步任务和事务外副作用要单独验证清理与补偿，不能假设事务会自动回滚一切。

## 完整提示词

````prompt
# Agent 通用提示词：后端全链路严谨测试与业务闭环验证

## 一、任务目标

请对当前项目的后端进行一次系统性、严谨、可追溯的测试工作。

本次任务不是简单地补充几个单元测试，也不是只检查接口能否正常返回，而是需要从实际业务需求和现有代码出发，完整验证后端业务逻辑是否正确、业务流程是否闭环、数据状态是否一致、异常分支是否得到正确处理，以及各模块之间的协作是否可靠。

**核心目标：证明业务能够正确运行，而不是证明代码能够成功执行。**

必须重点验证：

1. 业务需求与实际实现是否一致。
2. 每个业务流程是否具备完整的开始、执行、结束及必要的后续处理。
3. 每个接口的正常路径、异常路径、边界条件是否正确。
4. 数据库新增、修改、删除、关联、状态流转是否符合业务规则。
5. 多接口、多模块之间的数据传递是否正确。
6. 事务、并发、重复请求和失败回滚是否可靠。
7. 登录认证、角色权限、数据权限及操作权限是否有效。
8. 定时任务、消息处理、异步任务等后台逻辑是否正确。
9. 业务操作完成后，相关列表、详情、统计、关联记录是否保持一致。
10. 已有自动化测试是否真正验证了业务行为，而不是仅覆盖代码执行路径。

测试应尽可能覆盖完整的业务链路，并通过真实断言验证执行结果。

最终交付必须包含可重复执行的测试代码、测试执行结果、业务闭环覆盖情况、缺陷清单及必要的修复验证记录。

---

## 二、最高优先级执行原则

### 2.1 先理解业务，再编写测试

开始测试前，必须先分析项目中的业务定义和实际实现。

重点检查：

- 需求文档及业务流程文档。
- 数据库表结构、字段含义、关联关系和约束。
- Controller、Service、Mapper 及相关实现。
- DTO、VO、实体类及统一响应结构。
- 状态枚举、业务常量和状态转换规则。
- 事务边界和异常处理机制。
- 登录认证、角色权限和数据权限。
- 定时任务、消息队列、异步处理及外部接口。
- 已有测试代码、测试配置和测试数据。
- 实际存在的跨模块调用与业务依赖。

不要只根据方法名推测业务含义。应结合代码、数据库结构、调用关系和现有文档进行交叉确认。

对于文档与代码存在冲突的情况，应明确记录冲突，不得擅自选择一种解释后直接判定另一种实现错误。

### 2.2 不得为了通过测试而掩盖缺陷

严禁以下行为：

- 删除失败的测试用例。
- 将严格断言改成宽松断言。
- 将预期失败的业务操作改成预期成功。
- 为了通过测试而跳过真实业务逻辑。
- 使用 Mock 完全替代本应验证的核心业务实现。
- 修改生产代码使测试表面通过，却破坏原有业务规则。
- 捕获异常后忽略，导致测试误判成功。
- 仅验证 HTTP 状态码，不验证业务结果。
- 使用硬编码的预期值掩盖真实计算错误。
- 将测试未执行、执行失败或环境异常报告为测试通过。
- 使用不真实的测试数据证明业务流程已经闭环。

如果发现缺陷，应先保留失败证据，再分析原因，最后在授权范围内修复并重新执行测试。

### 2.3 严格区分测试类型

根据验证目标选择合适的测试方式：

- 单元测试：验证独立业务逻辑、规则、计算和状态转换。
- 集成测试：验证 Service、Mapper、数据库、事务和组件协作。
- API 测试：验证真实 HTTP 接口、请求参数、响应结构和业务行为。
- 端到端业务测试：验证多个接口组合形成的完整业务流程。
- 安全测试：验证认证、权限、数据隔离和非法访问。
- 并发与可靠性测试：验证重复提交、并发更新、幂等性和事务一致性。

核心业务不能全部依靠 Mock 测试。必须根据项目实际架构选择真实组件和真实数据库环境验证关键链路。

## 三、第一阶段：项目与业务全面审查

在编写测试之前，先形成清晰的项目分析结果。

### 3.1 项目结构分析

识别：

- 后端技术栈与版本。
- 构建工具和模块划分。
- 接口入口与路由。
- 业务服务层。
- 数据访问层。
- 数据传输对象。
- 统一响应结构。
- 全局异常处理。
- 安全认证与授权机制。
- 数据库类型及迁移方案。
- 测试框架与现有测试基础设施。

如果项目采用 Spring Boot、MyBatis-Plus、MySQL 等技术，应沿用项目实际配置，不能为了测试方便擅自更换技术栈。

### 3.2 接口清单梳理

尽可能整理所有与业务相关的接口，至少记录：

| 字段 | 说明 |
|---|---|
| 模块 | 所属业务模块 |
| 接口 | HTTP 方法与路径 |
| 业务用途 | 接口实际解决的问题 |
| 权限要求 | 允许访问的角色或条件 |
| 前置条件 | 执行前必须满足的业务状态 |
| 输入参数 | 必填项、选填项及合法范围 |
| 核心逻辑 | 关键校验、计算和状态变化 |
| 数据影响 | 可能读写的表及关联数据 |
| 后置条件 | 操作完成后应满足的条件 |
| 异常场景 | 参数错误、状态冲突、权限不足等 |
| 关联流程 | 前置接口、后续接口和依赖模块 |

不要只根据 Controller 数量确定测试范围。一个接口可能承载多个业务分支，同一个业务流程也可能跨越多个 Controller 和 Service。

### 3.3 数据库与业务关系分析

重点检查：

- 主键和外键关系。
- 唯一性约束。
- 非空约束。
- 默认值。
- 逻辑删除规则。
- 业务状态字段。
- 关联记录。
- 历史记录和审计字段。
- 创建时间、更新时间及操作人。
- 事务涉及的多张表。
- 数据清理和归档规则。

需要明确每个核心业务操作会影响哪些数据，以及这些数据之间必须满足什么约束。

### 3.4 输出业务流程图

针对核心业务，以流程图或有序步骤描述真实业务链路。

例如：

创建业务记录 → 参数校验 → 数据持久化 → 执行业务操作 → 更新状态 → 生成关联记录 → 查询结果 → 完成业务闭环。

上述流程仅为结构示例，不能直接套用到所有项目。

必须根据真实代码与业务文档确定实际步骤，标记：

- 正常路径。
- 可选路径。
- 异常路径。
- 回退路径。
- 重试路径。
- 终止路径。
- 需要人工处理的分支。

如果无法确认某个业务规则，应将其列为待确认事项，而不是编造预期结果。

## 四、第二阶段：建立业务闭环测试矩阵

这是本次任务的核心。

必须以业务流程为测试组织单位，而不是只按 Controller 或 Service 方法罗列测试。

### 4.1 业务闭环定义

一个业务闭环至少应明确：

1. 业务如何开始。
2. 哪些前置条件必须满足。
3. 哪些接口和服务参与执行。
4. 哪些数据需要新增或更新。
5. 哪些状态允许转换。
6. 操作失败时应该如何处理。
7. 操作完成后如何查询和确认结果。
8. 后续业务能否正确使用该结果。
9. 是否存在关联记录、审计记录或统计数据需要同步。
10. 流程是否可以重复执行、取消、回退或终止。

并非所有业务都需要取消、回退或重试。只测试真实存在或明确要求支持的行为。

### 4.2 每条核心流程必须覆盖的场景

针对每条核心业务链路，至少评估以下场景：

- 正常完成。
- 缺少必需参数。
- 参数格式错误。
- 参数超出允许范围。
- 引用的数据不存在。
- 引用的数据已经删除。
- 当前业务状态不允许执行。
- 当前用户没有操作权限。
- 重复执行相同请求。
- 中途某个数据库操作失败。
- 事务内某个步骤发生异常。
- 后续接口读取结果。
- 关联记录是否正确生成。
- 状态、数量和统计结果是否一致。
- 流程结束后是否还允许非法操作。
- 并发操作是否会产生冲突。

上述项目应根据具体业务逐项判断适用性。对于不适用的场景，应说明原因，而不是为了凑测试数量强行制造用例。

### 4.3 业务闭环测试矩阵

请为每条核心流程建立可追踪的矩阵。

| 测试维度 | 验证内容 |
|---|---|
| 前置条件 | 数据、权限和状态是否满足要求 |
| 正常执行 | 完整流程能否按预期完成 |
| 状态流转 | 是否只允许合法的状态变化 |
| 数据持久化 | 新增、更新和关联数据是否正确 |
| 后续查询 | 列表、详情及相关接口能否读取正确结果 |
| 失败处理 | 失败后是否保留一致的数据状态 |
| 事务回滚 | 事务范围内的操作是否按预期回滚 |
| 重复请求 | 是否重复创建记录或重复执行副作用 |
| 并发执行 | 是否出现丢失更新或状态覆盖 |
| 权限控制 | 非法用户是否被正确拒绝 |
| 完成条件 | 是否满足业务真正完成的定义 |
| 可追溯性 | 操作人、时间及必要的审计信息是否正确 |

每个测试用例都必须能够关联到具体业务规则、接口、测试数据和验证结果。

## 五、第三阶段：接口级严谨测试

对实际存在的接口进行系统测试。

### 5.1 请求参数验证

覆盖：

- 正常参数。
- 缺失参数。
- 空字符串。
- 空值。
- 非法格式。
- 超长字符串。
- 超出范围的数值。
- 非法枚举值。
- 不存在的关联 ID。
- 重复的唯一字段。
- 非法日期和时间范围。
- 不符合业务约束的参数组合。

重点检查参数校验是否真正生效，以及错误响应是否符合项目的统一响应规范。

不要只验证请求失败，还要确认失败原因正确，且没有产生不应该发生的数据修改。

### 5.2 响应结构验证

如果项目使用统一的 Result、DTO、VO 等结构，应检查：

- 响应格式是否一致。
- 业务状态码是否符合约定。
- 消息字段是否合理。
- 数据字段是否符合接口约定。
- 分页信息是否正确。
- VO 是否包含正确的业务展示字段。
- 是否意外暴露密码、令牌、内部密钥或不应公开的字段。
- 成功与失败响应是否具有清晰的区分。

不要只断言响应不为空。应检查关键字段的实际值和业务含义。

### 5.3 HTTP 与业务状态码

分别验证：

- 正常成功。
- 参数错误。
- 未认证。
- 无权限。
- 资源不存在。
- 业务状态冲突。
- 请求频率或并发限制（如果项目支持）。
- 服务内部异常。
- 外部依赖失败。

实际 HTTP 状态码与业务错误码应遵循项目现有约定和接口契约，不要未经确认就强行修改成另一套规范。

---

## 六、第四阶段：数据库与事务测试

必须验证真实数据变化，而不是只看接口响应。

### 6.1 新增操作

验证：

- 记录是否真实写入数据库。
- 关键字段是否正确。
- 默认值是否正确。
- 创建人、创建时间等字段是否符合约定。
- 唯一约束是否生效。
- 关联记录是否正确建立。
- 是否意外创建重复记录。

### 6.2 修改操作

验证：

- 目标记录是否正确。
- 允许修改的字段是否更新。
- 不允许修改的字段是否保持不变。
- 更新时间和操作人是否正确。
- 关联数据是否同步更新。
- 不存在的记录是否被正确处理。
- 非法状态下是否拒绝修改。

### 6.3 删除操作

验证：

- 物理删除或逻辑删除是否符合设计。
- 关联数据是否按规则保留、更新或删除。
- 已删除数据是否还能通过不应允许的接口访问。
- 重复删除是否产生错误副作用。
- 删除后相关列表、统计和关联查询是否正确。

不得因为测试方便而忽略项目实际使用的逻辑删除机制。

### 6.4 事务一致性

重点测试涉及多步操作的业务：

- 所有步骤成功时，数据完整提交。
- 中间步骤失败时，事务范围内的数据按预期回滚。
- 事务外部的副作用是否有正确的补偿或重试机制。
- 异常是否被错误捕获，导致事务未按预期回滚。
- 事务传播行为是否符合实际设计。
- 并发请求是否可能导致重复数据或状态不一致。

注意：数据库事务不能自动回滚已经发送的外部 HTTP 请求、消息或文件写入。对于这些操作，应检查项目是否使用事务消息、可靠事件、补偿或其他一致性方案，并按实际机制设计测试。

### 6.5 数据一致性检查

在关键流程执行前后，比较数据库中相关记录的变化。

检查：

- 主记录与关联记录。
- 业务状态与操作记录。
- 明细数据与汇总数据。
- 当前状态与历史状态。
- 统计结果与明细记录。
- 逻辑删除标记与查询结果。
- 关联数量与实际关联数据。

对于数量、金额、面积、时长、百分比等计算，应根据真实业务规则验证精度、舍入和边界行为。

---

## 七、第五阶段：状态机与业务规则测试

如果业务存在状态流转，必须建立明确的状态转换测试。

### 7.1 状态转换矩阵

针对每种核心业务状态，梳理：

- 当前状态。
- 允许执行的操作。
- 允许转换到的目标状态。
- 不允许执行的操作。
- 操作所需的权限。
- 操作完成后的数据库变化。
- 失败后的预期结果。

例如，业务可能存在“待处理 → 处理中 → 已完成”的状态变化，但这只是示意。实际状态必须以项目中的枚举、文档和业务实现为准。

### 7.2 非法状态测试

必须验证：

- 已完成的业务是否还能被重复完成。
- 已取消的业务是否还能继续处理。
- 尚未满足前置条件时是否允许进入下一阶段。
- 状态已变化后，旧请求是否会错误覆盖新状态。
- 非法状态值是否会导致不可预期的逻辑执行。
- 状态修改失败后，相关数据是否仍然一致。

不能仅仅因为接口返回成功，就判定状态流转正确。

### 7.3 状态流转的副作用

如果状态变化会触发以下行为，应分别验证：

- 生成后续任务。
- 创建关联记录。
- 发送消息。
- 记录操作日志。
- 更新统计数据。
- 触发通知。
- 释放或占用资源。
- 调用其他业务模块。

必须验证这些行为是否只在正确的条件下发生，以及是否会因为重复请求而重复执行。

---

## 八、第六阶段：跨模块完整业务链路测试

对存在模块依赖的系统，必须测试真实的跨模块调用链。

例如，若项目涉及任务创建、工单派发、处理记录、结果审核和统计汇总，应根据实际业务串联相关模块，验证完整链路。

测试必须覆盖：

1. 上游模块能否创建正确的业务数据。
2. 下游模块能否接收到正确的关联信息。
3. 上游和下游的数据标识是否一致。
4. 关联记录是否建立正确。
5. 状态是否按照业务规则推进。
6. 上游失败时，下游是否被错误触发。
7. 下游失败时，是否需要回滚、重试或补偿。
8. 流程完成后，查询接口是否返回正确结果。
9. 列表、详情和统计页面依赖的数据是否一致。
10. 是否存在数据重复、丢失或无法继续处理的中间状态。

不要只分别测试各个模块的接口，还必须验证它们组合起来是否能完成实际业务。

如果一个流程需要多个接口才能完成，应提供一组能够从初始数据开始、最终验证业务结果的集成测试或端到端测试。

---

## 九、第七阶段：权限与安全测试

根据项目实际认证和授权机制，验证：

### 身份认证

- 未登录访问受保护接口。
- 使用有效身份访问。
- 使用无效、过期或失效凭据访问。
- 退出登录后的访问行为。
- 不同认证状态下的接口表现。

### 功能权限

- 有权限的用户能否执行操作。
- 无权限的用户是否被拒绝。
- 仅有查询权限的用户是否无法执行修改。
- 仅有部分模块权限的用户是否无法越权访问其他模块。
- 隐藏菜单后，直接调用接口是否仍受到后端权限控制。

### 数据权限

如果项目存在数据范围控制，应测试：

- 用户是否只能访问授权范围内的数据。
- 修改、删除时是否会检查目标记录的数据归属。
- 是否能通过替换 ID 访问其他用户或其他组织的数据。
- 列表、详情、导出和统计是否使用一致的数据权限规则。

### 输入与敏感信息

根据实际接口检查：

- SQL 注入风险。
- 非法输入和边界输入。
- 敏感字段是否泄露。
- 错误堆栈是否被直接返回给普通用户。
- 文件上传类型、大小和访问权限（如果存在）。
- 导出接口是否绕过数据权限。
- 重复请求或并发请求是否可能造成业务滥用。

安全测试应以非破坏性方式执行，不得在未授权的真实生产环境中进行破坏性操作。

---

## 十、第八阶段：并发、幂等与可靠性测试

对于涉及订单、任务、工单、设备、告警、审批或资源分配的业务，应判断是否需要并发和幂等性测试。

### 10.1 幂等性

对于业务上应当幂等的操作，验证同一请求重复执行后：

- 不会重复创建业务记录。
- 不会重复生成下游任务。
- 不会重复扣减或增加资源。
- 不会重复执行不可重复的副作用。
- 返回结果符合接口契约。

并非所有 POST 请求都必须天然幂等。应根据业务约定和接口设计判断，不能擅自要求所有接口具有相同的重复请求行为。

### 10.2 并发状态更新

模拟合理的并发场景，例如：

- 两个用户同时处理同一条任务。
- 多个请求同时修改同一业务记录。
- 同一告警被重复确认。
- 同一资源被多个请求同时占用。
- 并发请求触发重复创建。

检查是否存在：

- 丢失更新。
- 重复记录。
- 状态覆盖。
- 超额分配。
- 重复执行副作用。
- 数据库死锁或长时间锁等待。

根据项目实际使用乐观锁、悲观锁、唯一约束或其他并发控制方式验证结果。

### 10.3 超时与失败重试

如果项目存在外部接口、消息队列或异步任务，应检查：

- 依赖服务超时。
- 外部服务返回失败。
- 消息消费失败。
- 重试是否有合理次数和间隔。
- 重试是否造成重复副作用。
- 重试耗尽后是否存在明确的失败记录。
- 任务是否可能永久停留在处理中状态。

只测试项目实际支持的可靠性机制，不要假定系统已经实现了重试、补偿或死信队列。

---

## 十一、第九阶段：定时任务与异步业务测试

如果项目存在定时任务、消息队列、异步执行或后台调度，应验证：

- 触发条件是否正确。
- 任务执行逻辑是否正确。
- 任务是否会重复运行。
- 多实例环境下是否可能重复执行。
- 执行失败后是否能够记录错误。
- 重试和补偿是否符合业务规则。
- 异步执行完成后，数据状态是否正确更新。
- 任务执行与主业务之间是否存在竞态条件。
- 任务结束后是否能够通过正常查询接口读取结果。

对于时间相关逻辑，优先采用可控时钟、可注入时间源或合理的测试时间配置，避免测试依赖真实等待时间。

不要为了测试方便修改生产环境的定时任务频率或实际业务时间规则。

---

## 十二、第十阶段：测试数据与环境管理

测试必须具有可重复性和可隔离性。

### 测试数据

- 为每个测试场景准备明确的数据前置条件。
- 尽可能使用独立的测试数据。
- 不依赖测试执行顺序。
- 不依赖开发者本机数据库中的偶然数据。
- 避免使用可能与现有数据冲突的固定业务编号。
- 对时间、随机数和外部依赖采用可控的测试方式。
- 重要测试应记录初始状态、执行操作和预期结果。

### 数据清理

- 优先使用独立测试数据库。
- 对支持事务回滚的测试合理使用事务隔离。
- 对事务外副作用进行独立清理。
- 清理逻辑不能误删非测试数据。
- 不得未经授权连接生产数据库执行测试。
- 不得使用真实生产数据进行未经批准的破坏性操作。

注意：使用测试事务不代表所有操作都会自动回滚，尤其是异步任务、独立线程、独立事务和外部副作用。应根据实际执行机制处理清理。

### 环境要求

测试配置应与生产配置合理隔离。

- 不使用真实生产密钥。
- 不向真实用户发送测试通知。
- 不对真实设备执行控制命令。
- 不向真实支付、短信或其他外部服务发送非预期请求。
- 对不可避免的外部依赖，应使用可控的测试替身或专用测试环境。
- 对核心数据库集成测试，优先使用与生产数据库类型及关键行为一致的测试环境。

---

## 十三、第十一阶段：现有测试质量审查

如果项目已经存在测试代码，不能只运行测试，还应检查测试本身是否有效。

重点排查：

- 断言是否真正验证业务结果。
- 是否只检查 HTTP 200 或响应不为空。
- 是否大量使用 Mock 绕过核心业务逻辑。
- 是否存在没有断言的测试。
- 是否存在无条件通过的测试。
- 是否通过捕获异常隐藏失败。
- 是否使用错误的预期值。
- 是否存在依赖执行顺序的测试。
- 是否存在测试数据污染。
- 是否覆盖关键异常分支。
- 是否覆盖数据库事务与状态变化。
- 是否覆盖完整业务链路。
- 是否存在被忽略或禁用但未说明原因的测试。

必要时补充或重写测试，但不得通过降低测试质量来获得绿色结果。

---

## 十四、第十二阶段：缺陷发现、修复与回归

发现问题后，按照以下流程处理。

### 14.1 缺陷记录

每个缺陷至少记录：

- 缺陷编号。
- 所属模块。
- 关联接口或业务流程。
- 问题描述。
- 复现前置条件。
- 复现步骤。
- 实际结果。
- 预期结果及其依据。
- 影响的数据或业务状态。
- 严重程度。
- 初步原因。
- 对应测试用例。

### 14.2 缺陷分类

建议按照影响程度分类：

- **严重：** 可能导致业务数据损坏、越权操作、重复执行关键业务、事务不一致或重大业务流程中断。
- **高：** 核心流程无法完成、关键状态错误、重要数据丢失或业务结果明显错误。
- **中：** 部分功能异常、特定条件下结果不正确或重要异常处理不完整。
- **低：** 非核心问题、提示信息不一致或影响较小的边界缺陷。

分类应依据实际业务影响，而不是仅依据异常堆栈或代码位置。

### 14.3 修复要求

- 优先定位真实原因。
- 最小化修改范围。
- 不得为了修复测试而改变未经确认的业务规则。
- 不得随意修改数据库结构或公共接口契约。
- 对涉及多个模块的问题，评估关联影响。
- 修复后必须重新运行对应测试。
- 还应运行相关回归测试，确认没有破坏其他业务。

如果需要修改生产代码，应说明修改原因、影响范围及验证结果。

如果没有得到明确授权，不要擅自进行高风险数据库迁移、大规模重构或真实外部系统操作。

---

## 十五、第十三阶段：测试覆盖与完成度评估

不要只使用代码覆盖率作为测试质量的唯一标准。

应同时评估以下维度：

### 业务覆盖率

- 核心业务流程覆盖情况。
- 业务规则覆盖情况。
- 状态转换覆盖情况。
- 异常与回退流程覆盖情况。
- 跨模块链路覆盖情况。
- 关键副作用覆盖情况。

### 接口覆盖率

- 已识别接口总数。
- 已执行接口数量。
- 已通过接口数量。
- 执行失败数量。
- 尚未执行数量。
- 被阻塞数量及原因。

### 代码覆盖率

如果项目已配置覆盖率工具，合理统计：

- 行覆盖率。
- 分支覆盖率。
- 必要时统计关键模块的方法覆盖情况。

覆盖率数字必须来自真实测试报告，不能凭估计填写。

### 业务闭环完成度

对每条核心流程给出明确状态：

- 已完整验证。
- 部分验证。
- 验证失败。
- 被环境或依赖阻塞。
- 尚未验证。
- 存在待确认的业务规则。

只有当正常流程、关键异常分支、状态与数据一致性以及后续结果均得到足够验证时，才可以认定该流程已完成闭环测试。

如果存在关键步骤无法验证，不得将整个流程标记为完全通过。

---

## 十六、测试执行策略

请按照以下顺序逐步执行，避免一开始就运行大量难以定位问题的测试。

### 第一轮：基础验证

- 编译与构建。
- 现有单元测试。
- 参数校验测试。
- 核心业务规则测试。
- 状态转换测试。

### 第二轮：集成验证

- 数据库集成测试。
- Mapper 查询与更新测试。
- 事务回滚测试。
- 统一响应与异常处理测试。
- 认证与权限测试。

### 第三轮：完整业务闭环

- 从真实业务入口开始执行。
- 按实际流程调用各接口。
- 验证中间状态与数据库记录。
- 验证失败路径。
- 验证最终状态。
- 使用后续查询接口确认结果。
- 检查关联模块和统计结果。

### 第四轮：可靠性与边界测试

- 重复请求。
- 并发状态更新。
- 数据边界。
- 依赖服务异常。
- 定时任务和异步任务。
- 数据隔离与清理。

### 第五轮：回归验证

- 重新执行失败用例。
- 执行相关模块测试。
- 执行核心业务链路测试。
- 执行必要的全量测试。
- 汇总真实结果与剩余风险。

每轮测试都应记录执行命令、执行环境、测试数量、通过数量、失败数量、跳过数量和关键失败原因。

不得将没有执行的测试写成已通过。

---

## 十七、测试实现规范

根据项目现有技术栈选择合适的测试框架和实现方式。

如果项目使用 Spring Boot、MyBatis-Plus、MySQL 等技术，应优先沿用项目已有测试基础设施。

### 单元测试

适用于：

- 业务规则。
- 参数校验。
- 状态转换判断。
- 数据计算。
- 分支逻辑。
- 异常映射。

单元测试应具有明确的输入、执行过程和结果断言。

### 集成测试

适用于：

- Service 与 Mapper 协作。
- 真实 SQL 执行。
- 数据库约束。
- 事务行为。
- 多表数据一致性。
- 真实业务组件协作。

测试完成后，必须输出一份结构清晰、可追溯的报告。

- 通过数量。
- 失败数量。
- 跳过数量。
- 被阻塞数量。

### 8. 未覆盖范围

- 未确认的业务规则。
- 尚未修复的问题。
- 仍然存在的风险。

### 9. 最终结论

最终结论必须区分：

- **通过：** 有实际测试证据支持，相关业务和数据结果符合预期。
- **有条件通过：** 核心功能已验证，但仍有明确的非关键问题或覆盖缺口。
- **不通过：** 存在关键业务错误、数据不一致、安全问题或核心闭环失败。
- **无法判定：** 由于环境、权限、外部依赖或业务规则缺失，无法得出可靠结论。

只有实际执行并取得证据的测试，才允许纳入通过统计。
````
