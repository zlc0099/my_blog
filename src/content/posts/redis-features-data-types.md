很多人对 Redis 的印象停留在 `GET` / `SET`，再进一步就是「缓存」。但 Redis 真正有用的地方，是它把常用数据结构放在内存里，并提供原子操作、过期、持久化、复制和集群能力。把它只当缓存，会浪费一半能力；把它当数据库，又会踩另一批坑。

这篇是我对 Redis 的整理：先看它提供什么，再看每种数据类型适合什么，最后回答实际使用中最容易混淆的问题。

## 它到底是什么

Redis 是一个**内存数据结构服务器**，不是简单的 key-value 存储。key 是字符串，value 可以是字符串、哈希、列表、集合、有序集合、位图、流等结构，每个结构都有一组原子命令。

几个基本事实：

- 命令执行是单线程的，所以单条命令天然原子，不需要在命令内部加锁。
- 数据主要放在内存里，持久化用于重启恢复和备份，不是「绝不丢数据」的保证。
- 6.0 之后支持 I/O 多线程，但**命令执行仍然是单线程**；多线程只分担网络读写。
- 它适合高频读写、简单查询、计数、去重、排行榜、会话、锁和轻量消息；不适合复杂关联查询、大 value、海量冷数据和强事务场景。

理解这一点之后，后面的选型基本都围绕两个问题：**这份数据丢了能不能恢复？读写的瓶颈到底在内存、网络还是命令本身？**

## 核心功能

| 功能 | 作用 | 关键点 |
|---|---|---|
| 丰富的数据结构 | 用结构表达业务，而不是把对象序列化成一个字符串 | 选错类型会导致大 key 和多次往返 |
| 过期时间 | 给 key 设置 TTL，到期自动删除 | 过期是惰性 + 定期清理，不保证精确到秒 |
| 内存淘汰 | 达到 `maxmemory` 后按策略淘汰 | 策略选错会误删非缓存数据 |
| 持久化 | RDB 快照、AOF 日志、混合持久化 | 持久化不等于主从同步 |
| 复制 | 主从复制，读扩展和故障备份 | 复制是异步的，故障切换可能丢写 |
| 哨兵 | 监控主节点并自动故障转移 | 只解决高可用，不解决分片 |
| 集群 | 数据分片 + 故障转移 | 多 key 操作受槽位限制 |
| 事务与 Lua | 批量执行、原子脚本 | 事务不支持回滚，Lua 会阻塞其他命令 |
| 管道 | 一次网络往返发送多条命令 | 减少 RTT，但不保证原子 |
| Pub/Sub | 发布订阅，即时广播 | 不持久化，离线消息收不到 |
| Stream | 追加日志、消费组、ACK | 更接近真正的消息队列 |

## 数据类型

| 类型 | 特点 | 典型场景 | 注意 |
|---|---|---|---|
| String | 二进制安全，最大 512MB | 缓存对象、计数器、分布式锁、位图基础 | 大字符串就是大 key |
| Hash | 字段-值结构，小 hash 很省内存 | 对象属性、购物车、配置 | 7.4 起才有字段级过期命令 |
| List | 双向链表式结构，两端操作快 | 队列、栈、最新列表 | 中间插入慢，不适合当可靠队列 |
| Set | 无序去重集合 | 标签、关注、共同好友、抽奖 | 大集合的交并差会阻塞 |
| ZSet | 带 score 的有序集合，跳表实现 | 排行榜、延时队列、滑动窗口限流 | score 是 double，注意精度 |
| Bitmap | 用位表示状态，底层是 String | 签到、活跃用户、布尔标记 | 偏移量很大时会分配大量内存 |
| HyperLogLog | 基数估算，固定约 12KB | UV 统计、独立访客估算 | 有约 0.81% 误差，拿不到原始成员 |
| GEO | 地理位置，底层用 ZSet 存 geohash | 附近的人、门店距离 | 精度和范围要按业务选 |
| Stream | 追加日志 + 消费组 + ACK | 轻量消息队列、事件流 | 至少一次投递，消费端要幂等 |

### String

最基础也最常用。除了缓存 JSON、计数器，还可以用 `SET key value NX PX 30000` 做分布式锁，用 `INCR` 做原子自增，用 `SETBIT` / `GETBIT` 做位图。

```bash
SET user:42:name "zlc"
INCR article:1001:views
SET lock:order:42 "uuid-xxx" NX PX 30000
```

`INCR` 的原子性只在单条命令内成立；先 `GET` 再 `SET` 不是原子操作，并发下会丢更新，需要 `INCR`、Lua 或 `WATCH`。

### Hash

把一个对象的多个字段放在同一个 key 下，比给每个字段单独建 key 更省内存，也方便一次取出。

```bash
HSET user:42 name "zlc" role "backend" level 3
HGETALL user:42
HINCRBY user:42 level 1
```

字段很多、访问模式又总是整对象读写时，Hash 不一定比 String 存 JSON 更合适；要按读写粒度选。Redis 7.4 之后支持 `HEXPIRE` 等字段级过期命令，但老版本仍然只能给整个 key 设 TTL。

### List

适合「最新 N 条」「简单队列」这类两端操作的场景：

```bash
LPUSH feed:42 "post:1001"
LRANGE feed:42 0 9
BRPOP queue:email 5
```

`LPUSH` + `BRPOP` 可以写一个阻塞队列，但它没有 ACK 和消费组，消费者崩溃后消息可能丢。需要可靠消费时用 Stream 或专业消息队列。

### Set

用于去重和集合运算：

```bash
SADD article:1001:tags java spring redis
SINTER user:42:follow user:43:follow
SADD lottery:2026 1001 1002 1003
```

`SINTER`、`SUNION`、`SDIFF` 在大集合上开销不小，别在高峰期的核心链路上直接对百万级集合做交并差；可以预先算好结果或拆小集合。

### ZSet

每个成员带一个 score，按 score 排序，底层是跳表 + 字典。排行榜、延时队列、滑动窗口限流都靠它：

```bash
ZADD rank:2026 9800 "player:42"
ZREVRANGE rank:2026 0 9 WITHSCORES
ZADD delay:order 1767225600000 "order:1001"
ZRANGEBYSCORE delay:order 0 1767225600000 LIMIT 0 10
```

延时队列用 ZSet 存「到期时间戳」，消费者轮询 `ZRANGEBYSCORE` 取到期任务；要处理重复消费和任务取消。score 是浮点数，做时间戳时注意精度和时区。

### Bitmap

用位表示布尔状态，底层还是 String：

```bash
SETBIT sign:2026:10:27 42 1
BITCOUNT sign:2026:10:27
BITOP AND active:week sign:day1 sign:day2 sign:day3
```

签到、活跃用户、权限位都适合。偏移量越大占用的内存越多，不要把稀疏的随机 ID 直接当偏移量。

### HyperLogLog

做基数估算，不保存原始元素，固定约 12KB：

```bash
PFADD uv:2026-10-27 user:42 user:43
PFCOUNT uv:2026-10-27
PFMERGE uv:month uv:2026-10-27 uv:2026-10-26
```

适合 UV 这种「只要数量、不要名单」的统计，标准误差约 0.81%。需要精确值或需要知道具体是谁，就不要用它。

### GEO

把经纬度写进去，按半径或矩形范围查询：

```bash
GEOADD shop:location 114.305 30.593 "shop:1"
GEOSEARCH shop:location FROMLONLAT 114.30 30.59 BYRADIUS 5 km ASC
```

底层是 ZSet + geohash，适合门店、附近的人；精度和范围要按业务定，别拿它做精确的行政区划判断。

### Stream

Redis 的追加日志结构，支持消费组和 ACK，适合轻量事件流：

```bash
XADD stream:order * orderId 1001 status PAID
XGROUP CREATE stream:order g1 0 MKSTREAM
XREADGROUP GROUP g1 c1 COUNT 10 BLOCK 5000 STREAMS stream:order ">"
XACK stream:order g1 1767225600000-0
```

它是至少一次投递，消费者处理失败可以用 `XPENDING` + `XCLAIM` 重新领取；消费端仍然要做幂等。Stream 比 List 可靠，但比 Kafka / RocketMQ 轻量，别拿它硬扛大规模消息场景。

## 缓存怎么用

最常见的模式是 Cache-Aside：

1. 读请求先查缓存，命中直接返回。
2. 未命中查数据库，回填缓存并设置 TTL。
3. 写请求先更新数据库，再删除缓存（不是更新缓存）。
4. TTL 作为最终兜底，防止脏数据永久存在。

### 穿透、击穿、雪崩

| 问题 | 现象 | 常用处理 |
|---|---|---|
| 缓存穿透 | 查询根本不存在的数据，请求每次都落到数据库 | 空值缓存、布隆过滤器、参数校验 |
| 缓存击穿 | 某个热点 key 过期，瞬间大量请求打到数据库 | 互斥重建、逻辑过期、热点 key 不过期 + 异步刷新 |
| 缓存雪崩 | 大量 key 同时过期，或 Redis 整体不可用 | TTL 加随机值、多级缓存、限流熔断、集群高可用 |

这三个词经常被混用：穿透是「数据不存在」，击穿是「单个热点失效」，雪崩是「大面积同时失效」。

### 一致性

缓存和数据库之间没有免费的强一致。常见顺序是「更新数据库 → 删除缓存」，再配合延迟双删或订阅 binlog 异步删除。延迟双删也不是绝对可靠：延迟时间难估、删除失败要重试、并发读写仍有窗口。

如果业务不能接受短暂不一致，要么接受更高成本（锁、串行化、事务消息），要么重新审视这块数据是否真的需要缓存。**缓存是加速层，不是事实来源。**

## 分布式锁

最基础的写法是一条命令完成加锁：

```bash
SET lock:order:42 "uuid-xxx" NX PX 30000
```

`NX` 保证只有不存在时才设置，`PX` 保证原子地设置过期时间。不要拆成 `SETNX` + `EXPIRE`，两条命令之间宕机会留下永远不过期的锁。

释放锁必须校验 value，防止删掉别人的锁，用 Lua 保证比较和删除原子：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

业务执行时间不确定时，需要看门狗续期（Redisson 的 watchdog 就是做这件事），但续期只能解决「业务没结束」，解决不了「进程暂停后锁已过期，别人已经拿到锁」。对安全性要求高的场景，还要加 fencing token，让下游只接受版本号更大的写入。

Redlock 在多实例上加锁，但仍有争议：时钟漂移、GC 暂停、网络延迟都可能让锁在临界区失效。单实例主从切换也可能丢锁。**Redis 锁适合防重复、防并发写，不适合承担强一致的唯一屏障。**

## 限流、排行榜与延时任务

- **固定窗口限流**：`INCR rate:user:42`，第一次设置过期时间；简单，但窗口边界会突刺。
- **滑动窗口**：ZSet 存请求时间戳，按 score 范围删除旧记录并计数；精确但内存成本高。
- **令牌桶**：用 Lua 把「取令牌 + 补充令牌 + 判断」写成原子脚本。
- **排行榜**：ZSet 的 `ZINCRBY` / `ZREVRANGE`，按天分 key，避免单个 key 无限增长。
- **延时任务**：ZSet + 定时轮询，适合小规模；规模大时用专业调度或消息队列的延时消息。

## 持久化与高可用

### RDB 与 AOF

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| RDB | 定时生成全量快照 | 文件小、恢复快 | 两次快照之间宕机会丢数据；fork 有内存开销 |
| AOF | 追加写命令日志 | 丢数据窗口小 | 文件更大、恢复更慢、需要重写 |
| 混合 | RDB 头 + AOF 增量 | 恢复速度和数据安全兼顾 | 配置和运维更复杂 |

`appendfsync everysec` 是最常用折中，极端情况下仍可能丢约 1 秒数据；`always` 更安全但性能代价高。AOF 重写通过 fork 子进程完成，内存和磁盘要留余量。

如果 Redis 只是缓存，持久化可以按需关闭；如果承载会话、锁、队列或幂等记录，至少要开 AOF，并考虑主从和备份。**不要把唯一数据放在一个没有持久化、没有副本的 Redis 里。**

### 哨兵与集群

- **主从复制**：异步复制，读请求可以分散到从节点；主节点故障时需要人工或哨兵切换。
- **哨兵**：监控、通知、自动故障转移、告诉客户端新主节点地址；不负责分片。
- **Cluster**：16384 个槽分片到多个主节点，每个主节点可带从节点；客户端按槽路由，遇到 `MOVED` 重定向，迁移过程中可能遇到 `ASK`。

Cluster 的约束要提前知道：

- 多 key 命令、事务、Lua 脚本涉及的 key 必须在同一个槽。
- 需要同槽时用 hash tag，例如 `order:{42}:info` 和 `order:{42}:items`。
- 跨槽的聚合、事务、分布式锁不能想当然地写。
- 至少 3 个主节点起步，生产还要考虑副本和故障转移。

## 常见疑惑

**1. Redis 单线程为什么还快？**

主要是内存操作、避免锁竞争、命令简单，加上 I/O 多路复用。快不等于可以随便用：一个大 key 或一条慢命令（`KEYS`、大集合交并差、长 Lua）会阻塞后面所有请求。

**2. Redis 6 之后的多线程是怎么回事？**

多线程处理的是网络读写和部分后台任务，命令执行仍是单线程。所以「多线程了就不会阻塞」是误解，慢命令照样会卡住整个实例。

**3. Redis 事务支持回滚吗？**

不支持。`MULTI` 后的命令会排队，`EXEC` 时顺序执行；如果某条命令运行时出错，前面已经执行的命令不会回滚。`WATCH` 提供的是乐观锁，不是数据库事务。

**4. 事务、Lua、管道怎么选？**

管道只是减少网络往返，不保证原子；事务能保证一批命令连续执行，但不回滚、不能读中间结果；Lua 在服务端原子执行，适合「读-判断-写」的组合。Lua 不能太长，否则阻塞其他请求。

**5. 更新数据时为什么删缓存而不是更新缓存？**

并发更新时，两个请求的写缓存顺序可能和数据库提交顺序相反；而且很多更新根本不会被马上读取，更新缓存是无效计算。删除后等下次读取回填更简单。删除仍可能失败，所以需要重试、延迟双删或订阅 binlog。

**6. 缓存和数据库能做到强一致吗？**

很难，通常只能做到最终一致。强一致需要锁、串行化或分布式事务，代价高。先判断业务能接受多长的不一致窗口，再决定是否值得。

**7. 为什么分布式锁要用 SET NX PX，而不是 SETNX + EXPIRE？**

两条命令不是原子的，加锁后、设置过期前进程崩溃，锁就永远不会释放。`SET key value NX PX ttl` 把两个动作合成一条命令。

**8. 锁过期了业务还没执行完怎么办？**

看门狗续期可以降低概率，但不能消除风险。业务要幂等，关键写操作加 fencing token；不要把「锁没过期」当成绝对安全。

**9. Redlock 可靠吗？**

它在多个独立实例上加锁，但时钟漂移、GC 停顿和网络延迟都可能破坏安全性，学界和工业界都有争议。强一致场景更适合用带 fencing token 的方案或 etcd / ZooKeeper 这类共识系统。

**10. 大 key 怎么发现和处理？**

大 value、几十万元素的集合都算大 key。用 `redis-cli --bigkeys`、`MEMORY USAGE`、`SCAN` 抽样发现；处理时拆分 key、压缩 value、删大 key 用 `UNLINK` 异步释放，别用 `KEYS *` 扫全库。

**11. 热 key 怎么处理？**

本地缓存、读副本、key 拆分、集群分散、入口限流都可以组合使用。先确认是真的热 key（监控 + 采样），再决定是缓存到本地还是拆分，不要凭感觉优化。

**12. 过期 key 为什么没有立刻释放内存？**

Redis 用惰性删除加定期采样，过期不等于立刻回收；达到 `maxmemory` 时还会触发淘汰。TTL 是逻辑过期时间，不是精确的内存回收时刻。

**13. Redis Cluster 为什么是 16384 个槽？**

槽位数量影响心跳包大小和迁移粒度。16384 是官方在规模和开销之间的选择；节点规模特别大时还要考虑槽分布和迁移成本。

**14. Redis 能当数据库用吗？**

不建议作为唯一事实来源。它没有通用查询能力，持久化和复制是异步的，内存淘汰还可能删数据。缓存、会话、锁、排行榜、轻量消息这些场景更合适；真要当主存储，必须接受它的边界并做好持久化、副本和备份。

## 小结

Redis 的核心不是「快」，而是**在内存里提供一组带原子操作的数据结构**。选型时先确定数据角色：

- 只是加速读：按缓存设计，关注穿透、击穿、雪崩和一致性。
- 需要跨请求共享状态：考虑会话、锁、限流，注意 TTL 和续期。
- 需要消息和事件：优先专业消息队列，轻量场景再用 Stream。
- 需要持久数据：Redis 只能作为辅助，不能替代数据库。

把数据类型、过期策略、持久化和集群约束放在一起看，很多「Redis 又出问题了」其实是使用方式和数据角色不匹配。
