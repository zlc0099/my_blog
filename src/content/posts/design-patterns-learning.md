设计模式很容易学成两种极端：一种是背下 23 个名字和 UML 图，另一种是觉得它全是面试八股，实际写代码根本用不上。

我的理解在中间：设计模式是对反复出现的结构问题的命名。它最大的价值不是让你多写几个接口，而是让团队在讨论“这里要不要加一层”“这个变化点放在哪”时，有共同的词汇。

用得好，它能让代码在变化来临时少改一点；用得不好，它就是一层又一层没有必要的抽象。

## 先记住三条原则

在看具体模式之前，先把几条原则放在前面，因为它们比模式本身更重要。

**封装变化。** 找出会变的部分，把它隔离出来。支付方式会变、折扣规则会变、通知渠道会变，这些是模式真正要处理的地方。不会变的部分，不一定需要抽象。

**组合优于继承。** 继承会把子类和父类绑死，父类一改，所有子类都受影响。组合更灵活，可以在运行时替换行为，也更容易测试。

**依赖抽象，而不是依赖细节。** 高层业务不应该直接依赖某个具体实现。Spring 的依赖注入、面向接口编程，本质上都是在做这件事。

再加一条：**简单优先。** 如果一段 if-else 现在只有两个分支，而且短期不会变，先让它保持简单。模式应该服务于变化点，不是服务于“看起来更架构”。

SOLID 五条原则也可以放在这个框架里理解：单一职责关注“一个类为什么变”，开闭原则关注“新增变化时改哪里”，里氏替换关注“子类能不能替代父类”，接口隔离关注“别让实现方依赖用不到的方法”，依赖倒置关注“高层和低层都依赖抽象”。它们不是五条口号，最终都落到“变化来时，代码要改在哪”。

## 23 个模式怎么分类

| 类别 | 关注点 | 常见模式 |
|---|---|---|
| 创建型 | 对象怎么创建，创建逻辑和使⽤逻辑怎么分开 | 单例、工厂方法、抽象工厂、建造者、原型 |
| 结构型 | 类和对象怎么组合成更大的结构 | 适配器、桥接、组合、装饰器、外观、享元、代理 |
| 行为型 | 对象之间怎么分工、通信、分配职责 | 责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者 |

不用一上来就把 23 个都背完。实际业务里高频的其实就那么几个：策略、工厂、建造者、单例、代理、装饰器、模板方法、责任链、观察者、状态。剩下的知道意图，用到时再查就够了。

## 几个常用模式

### 策略：把会变的算法抽出来

```java
public interface DiscountPolicy {
    BigDecimal discount(BigDecimal amount);
}

@Service
public class VipDiscountPolicy implements DiscountPolicy {
    public BigDecimal discount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.9"));
    }
}
```

策略适合“同一件事有多种算法，运行时选一种”的场景，比如支付方式、折扣规则、导出格式、风控规则。它把 if-else 里的每个分支变成一个可替换的实现。

但不要为了两个固定分支就建一套策略体系。策略的代价是类变多、调用链变长。只有当分支会持续增加，或者每个分支的逻辑已经复杂到值得独立测试时，它才划算。

### 工厂：把创建逻辑收起来

工厂方法关注“创建哪个产品”，抽象工厂关注“创建一整个产品族”。业务代码里更常见的是简单工厂或 Spring 容器本身：调用方只依赖接口，具体实现由工厂或容器给出。

```java
public interface Notifier {
    String type();
    void send(String message);
}

@Component
public class NotifierFactory {
    private final Map<String, Notifier> notifiers;

    public NotifierFactory(List<Notifier> notifiers) {
        this.notifiers = notifiers.stream()
            .collect(Collectors.toMap(Notifier::type, Function.identity()));
    }

    public Notifier get(String type) {
        return notifiers.get(type);
    }
}
```

工厂适合创建逻辑复杂、需要集中管理、或者要隐藏具体实现的场景。如果一个对象只是 `new` 一下、没有分支，不需要为了“模式”再包一层工厂。

### 建造者：把复杂对象的构造过程拆开

```java
Order order = Order.builder()
    .userId("user-1")
    .items(items)
    .coupon(coupon)
    .build();
```

建造者适合参数多、可选参数多、需要分步构造、或者希望对象不可变的场景。它比一长串构造参数可读，也比先 `new` 再一堆 setter 更安全。

但建造者不是所有对象的标配。参数只有两三个、构造逻辑简单时，直接构造更清楚。Lombok 的 `@Builder` 很好用，但也要注意它不会自动帮你做业务校验，`build()` 里该检查的边界还是要检查。

### 单例：一个实例，不是全局变量

单例保证一个类只有一个实例，并提供访问点。Java 里常见写法有枚举、静态内部类、双重检查锁。

```java
public enum ConfigRegistry {
    INSTANCE;

    private final Map<String, String> config = new ConcurrentHashMap<>();

    public String get(String key) {
        return config.get(key);
    }
}
```

枚举单例能防反射和序列化破坏，写法也简单。双重检查锁则必须给实例字段加 `volatile`，否则可能读到“引用已经赋值、对象还没初始化完”的状态。

在 Spring 里，单例 Bean 的“单例”是每个容器一个，不是整个 JVM 一个。不要把单例当成全局可变状态的借口；如果一个单例里塞满可变的业务数据，它很快就会变成测试和并发问题的源头。

### 代理、装饰器、适配器：都是“包一层”，但目的不同

| 模式 | 目的 | 典型场景 |
|---|---|---|
| 代理 | 控制对对象的访问 | 权限、延迟加载、远程调用、AOP |
| 装饰器 | 在不改原对象的情况下增加行为 | 缓冲、日志、重试、加密 |
| 适配器 | 转换接口，让不兼容的类一起工作 | 老系统接口、第三方 SDK |
| 外观 | 简化子系统调用 | 给复杂模块提供统一入口 |
| 桥接 | 分离抽象和实现两个维度 | 多平台、多渲染方式 |

代理和装饰器都实现同一个接口，区别在意图：代理是“访问控制”，装饰器是“功能叠加”。Spring AOP 用的是代理；给 `InputStream` 套 `BufferedInputStream` 是装饰器；把旧支付接口包成新接口，是适配器。

### 模板方法：固定骨架，留出钩子

```java
public abstract class ImportTemplate {
    public final void execute() {
        parse();
        validate();
        save();
        afterSave();
    }

    protected abstract void parse();
    protected abstract void validate();
    protected abstract void save();
    protected void afterSave() {
    }
}
```

模板方法适合流程步骤固定、个别步骤变化的场景，比如导入、导出、审批、初始化。父类控制顺序，子类实现细节。

它的代价是继承耦合：子类被父类的骨架绑住，父类改顺序会影响所有子类。如果变化维度不止一个，组合和策略通常比继承更灵活。

### 责任链：让请求沿着处理者传下去

责任链适合校验、审批、过滤器、拦截器这类“多个处理者按顺序处理同一个请求”的场景。每个处理者决定自己处理、继续传递，还是直接中断。

Spring 的 `HandlerInterceptor`、Servlet 的 `FilterChain` 都是责任链思想。用的时候要注意顺序和终止条件：链太长会难排查，处理者之间共享状态也容易出错。

### 观察者：一个变化，多个响应

观察者定义一对多依赖：主题状态变化时，所有观察者收到通知。Spring 的 `ApplicationEventPublisher` 和 `@EventListener` 就是进程内观察者。

它适合解耦“订单创建后要发通知、加积分、写审计”这类副作用，但要知道它的边界：默认是进程内、同步的，事务回滚和异常会影响其他监听器；跨服务、需要可靠投递时，应该用消息队列和 outbox，而不是进程内事件。

### 状态：把状态和状态迁移收进对象

状态模式适合订单、工单、审批单这类有明确状态和迁移规则的业务。每个状态负责自己能处理的动作，以及下一步转到哪个状态。

它和策略的区别是：策略通常由外部选择算法，状态则由对象内部根据动作和当前状态决定迁移。状态多了以后，用状态机或状态表往往比一堆状态类更清楚。

## Spring 里其实到处都是模式

- `BeanFactory` / `FactoryBean`：工厂
- 单例 Bean：单例（容器级）
- AOP：代理
- `JdbcTemplate`：模板方法
- `ApplicationEvent`：观察者
- `HandlerInterceptor` / `FilterChain`：责任链
- `Resource`、`Converter`：适配器和策略
- `@Transactional`：代理 + 模板方法的组合

但框架用模式，不代表业务代码也要把每一层都写成模式。Spring 的存在本来就是帮你处理对象创建、依赖装配、代理和事务这些横切问题；业务代码更重要的是把领域逻辑写清楚。

## 什么时候不要用

- **变化点还没出现**：只有一个实现、一个分支，先写简单代码。等第二个、第三个变化出现再抽象，通常比一开始就设计一套体系更稳。
- **用模式替代领域建模**：如果业务概念本身没想清楚，套再多策略和工厂也只是把混乱藏进类名里。
- **为了模式而模式**：每个类都加接口、每个接口都加工厂、每个工厂都加配置，最后阅读成本远大于收益。
- **用单例保存全局状态**：单例会变成隐式依赖，测试难隔离，并发问题也难查。
- **用继承复用代码**：继承应该是“is-a”的关系，不是“我想少写几行”。组合通常更安全。

模式的价值在于降低变化时的修改成本，不是增加类图的美观度。一个模式如果让代码更难读、更难测，那它大概率用错了。

## 常见答疑

**1. 23 种设计模式都要背吗？**

不需要。知道三类分别解决什么问题，记住常用的十来个的意图和边界，剩下的用到时查。面试会问，但工作里更重要的是判断“这里该不该抽象”。

**2. 设计模式是不是过时了？**

没有，但形式在变。Lambda、函数式接口、依赖注入和框架已经吃掉了很多模板代码。比如策略、命令、观察者可以用函数或事件替代，但“把变化隔离出来”的意图没有变。

**3. 策略和 if-else 怎么选？**

分支少、稳定、逻辑短，if-else 更直接。分支持续增加、每个分支都需要独立测试、或者要在运行时选择，策略更合适。不要为了消灭 if-else 而制造一堆类。

**4. 工厂和建造者有什么区别？**

工厂解决“创建哪个对象”，建造者解决“怎么一步一步构造一个复杂对象”。工厂通常返回成品；建造者关注构造过程和参数组合。

**5. 单例和静态方法怎么选？**

静态方法简单，但难替换、难 mock，也不容易管理生命周期。单例可以通过依赖注入替换实现，适合需要状态、配置或测试隔离的场景。Spring 里优先用容器管理的单例 Bean。

**6. 双重检查锁为什么需要 volatile？**

防止指令重排导致另一个线程看到“引用不为空、对象还没初始化完”的实例，同时保证可见性。

**7. 代理和装饰器怎么区分？**

看意图。代理控制访问，客户端通常不知道背后有代理；装饰器增加行为，客户端可以一层层叠加。两者结构像，目的不同。

**8. 模板方法和策略怎么选？**

流程骨架固定、只有个别步骤变化，用模板方法；整个算法需要替换、或者有多个变化维度，用策略/组合。模板方法依赖继承，策略依赖组合。

**9. 责任链和装饰器有什么区别？**

装饰器通常会继续调用被包装对象，强调功能叠加；责任链可以把请求传给下一个处理者，也可以直接终止，强调“谁来处理”。

**10. 观察者能替代消息队列吗？**

不能。观察者通常是进程内、同步的，应用重启或事务回滚时事件可能丢失；消息队列解决的是跨进程、可靠投递和削峰。两者解决的问题不同。

**11. 状态和策略怎么区分？**

策略是“选一种算法”，状态是“对象在某个状态下能做什么，以及怎么迁移到下一个状态”。状态模式里，状态自己通常知道下一步；策略通常由外部选择。

**12. 为什么 Spring 里到处都是设计模式？**

框架要解决对象创建、依赖装配、代理、事务、事件这些通用问题，所以会用工厂、代理、模板方法、观察者等模式。业务代码不必复制框架的复杂度。

**13. 怎么避免过度设计？**

先写能工作的简单版本，标出可能变化的地方；等变化真的出现，再引入抽象。每次加一层都问：它解决了哪个具体变化？如果没有答案，就先不加。

**14. 怎么在现有代码里识别设计模式？**

看意图和对象关系，不要只看类名。一个 `XxxManager` 可能是外观，也可能是上帝类；一个接口加多个实现可能是策略，也可能只是普通多态。模式是描述结构的词汇，不是命名的装饰。

## 小结

设计模式最值得带走的是三件事：

- 找到变化点，把它隔离；
- 优先组合和依赖抽象，而不是继承和硬编码；
- 在简单和灵活之间做取舍，别为了模式而模式。

模式不是代码的目标，能让代码在需求变化时少疼一点，才是。
