工具用得越多，越容易把“能生成代码”误认为“能推进任务”。真正影响效率的不是模型回答得多快，而是它能否稳定拿到上下文、按流程验证，并在出错时收敛。这篇记录我目前的分工方式，不涉及具体版本评分。

## 先按任务类型分，而不是按工具排名

我把日常开发任务粗略分成三类：

- **深度重构**：跨多个文件、需要理解调用链和历史约定。
- **全栈联动**：前端页面、接口、数据模型一起改，强调工作区一致性。
- **快速试验**：先看视觉和交互效果，允许代码暂时粗糙。

三类任务对上下文长度、工具调用能力和反馈速度的要求不同，用一个工具包打天下反而会增加返工。

## Claude Code：终端里的长上下文工作台

适合：跨文件重构、方案复核、问题排查。

我更愿意把它放在终端里处理“需要读完一圈代码再动手”的任务。它可以看到仓库结构、运行命令、读日志，适合把证据链串起来。

一次典型的使用方式是先让它只做分析：

```text 排查任务
请先不要改代码。
1. 定位列表接口的完整调用链；
2. 找出状态判断散落在哪些文件；
3. 列出可以合并到 Service 的规则；
4. 给出回归清单。
```

确认分析成立后，再让它按文件逐个修改。这样做的原因是：一次性生成大范围 diff 很难复核，先看判断再看改动，成本更低。

它的弱点是反馈循环相对慢。对于纯视觉微调，等待一次完整分析并不划算。

## Qoder：工作区里的全栈实现

适合：从需求拆解到页面、接口一起落地。

Qoder 的优势在于工作区上下文完整。当前端组件和后端接口需要同时调整时，不需要反复把约定贴进对话。它更适合执行结构化的任务清单，比如：

1. 新增一个查询接口。
2. 补充 DTO 与校验。
3. 在页面接入筛选条件。
4. 补空状态与错误提示。
5. 跑构建并修复类型错误。

这种任务链的价值是“一致性”：接口字段、页面状态和验收标准在同一个上下文里收敛。

我通常会把范围写得很窄，避免它顺手重构无关模块。任务越具体，产出越可控。

## Trae：快速试界面

适合：样式探索、组件草稿、移动端断点调整。

视觉想法需要尽快看到结果。Trae 更适合先在现有页面里做一个可交互的草稿，再决定是否保留。例如调整列表的悬停状态、验证某个非对称网格在平板上的表现。

这个阶段我会刻意降低要求：

- 先不追求组件抽象。
- 先不接入真实数据，用少量静态数据验证布局。
- 先不写复杂动效，确认信息层级。

确认方向后，再把结构化的部分交给更擅长全栈联动的工具。

## 一个简单的对比

| 维度 | Claude Code | Qoder | Trae |
| --- | --- | --- | --- |
| 主要场景 | 深度重构、排障 | 全栈实现 | 前端试验 |
| 上下文获取 | 终端与仓库 | 工作区 | 当前编辑区 |
| 适合的粒度 | 跨文件任务 | 功能链路 | 单个界面 |
| 主要风险 | 反馈偏慢 | 范围容易扩大 | 代码容易临时化 |
| 我的验收重点 | 判断是否有证据 | 接口与页面是否一致 | 视觉与状态是否可用 |

这张表描述的是我的使用方式，不是工具能力上限。同一个工具在不同项目里可能扮演不同角色。

## Token 消耗的控制方式

无论用哪个 Agent，我会坚持几条约束：

1. **先澄清再执行**：需求模糊时先问问题，避免生成大量无效代码。
2. **范围写清楚**：明确本次做什么、不做什么，减少无关文件扫描。
3. **小步验证**：每完成一个原子任务就跑一次构建或测试，而不是最后一次性验收。
4. **保留证据**：命令输出、错误日志和浏览器结果要能回看，而不是只保留一句“已完成”。

这些约束比“换一个更强的模型”更能控制成本。Token 账本记录的不应该只是数字，还应该包含任务类型和结果，否则无法判断哪些消耗是值得的。

## 目前的分工

```text 工作流
需求澄清        → 人工 + Claude Code 分析
数据模型 / 接口 → Qoder 实现
页面骨架 / 视觉 → Trae 试验
跨文件重构      → Claude Code 复核
最终验收        → 人工执行构建与浏览器检查
```

这套分工还会调整。重要的不是固定工具，而是让每一步都有明确的输入、产物和验证方式。

> Agent 可以加速执行，但不能替代对结果的判断。能说清楚“为什么这样改”，才算真正完成。
