重复流程如果只存在于聊天记录里，就永远需要重新解释。Skill 的价值不是把提示词写长，而是把一套可重复的工作方式固定下来：什么时候触发、按什么顺序做、产出什么、如何判断做完。

## Skill 与普通提示词的区别

普通提示词解决一次对话，Skill 解决一类任务。一个可维护的 Skill 至少应该包含：

- **触发条件**：什么情况下加载，什么情况下不加载。
- **工作流**：每一步的输入、动作、产物和验证方式。
- **边界**：哪些事情不做，避免范围失控。
- **失败处理**：信息不足、验证失败或环境不满足时怎么办。
- **自检清单**：交付前逐项确认，而不是凭感觉判断完成。

如果一段提示词只是“请帮我写一个页面”，它不是 Skill；如果它规定了设计 Token 来源、状态覆盖范围、响应式断点和验收命令，它才开始具备 Skill 的形态。

## 最小结构

一个兼容多个 Agent 的 Skill 可以只用 Markdown 描述：

```yaml SKILL.md
---
name: frontend-ui-design
description: 前端 UI 美化与设计规范。当用户显式要求按设计规范实现页面时加载。
---

# Frontend UI Design

## 适用场景
- 新页面、组件库、落地页
- 已有页面的视觉重构

## 工作流
1. 提取风格关键词与品牌色。
2. 建立 Design Token，禁止魔法数字。
3. 选择布局与断点，说明移动端策略。
4. 实现组件与交互状态。
5. 按可访问性与响应式清单自检。

## 不做什么
- 不引入新的 UI 框架。
- 不为装饰牺牲正文可读性。
- 不虚构没有提供的品牌素材。
```

关键在 `description`：它决定 Agent 何时加载技能。写得含糊，技能要么永远不触发，要么在不相关任务里频繁出现。

## 触发条件要写成可判断的句子

不好的写法：

```text
描述：帮助前端开发。
```

好的写法：

```text
描述：当任务涉及页面/组件的视觉实现、响应式布局或设计规范落地时加载；
仅讨论接口数据结构、不涉及界面时不要加载。
```

前者听起来宽泛，后者给出了明确的正反例。对自动触发的 Skill 来说，description 就是路由规则。

## 把流程拆成可验证的阶段

以全栈开发为例，我把它拆成六段：

| 阶段 | 产物 | 验证方式 |
| --- | --- | --- |
| 澄清 | 问题清单与默认假设 | 用户确认或明确标注 |
| 设计 | 数据模型、接口契约、页面状态 | 能覆盖主链路与异常 |
| 清单 | 原子任务列表 | 每项可独立验证 |
| 实现 | 代码与自测结果 | 构建、类型检查、单元测试 |
| 复核 | 改动范围与回归清单 | 从调用方重新阅读 |
| 验收 | 命令输出、浏览器结果 | 有证据再宣布完成 |

每一段都要有产物。没有产物的步骤，通常只是“思考了一下”，下次无法复用。

## 失败与回退

Skill 不应该假设环境永远满足。需要提前写清楚：

- 必要命令不存在时，先报告缺失项，不擅自安装全局依赖。
- 测试失败时，保留失败输出，不通过跳过测试来“完成”任务。
- 信息不足时，先提出最多几个关键问题，而不是自行编造约束。
- 需要修改共享环境或推送远端时，先征求确认。

这些规则能显著降低 Agent 在自动化流程里的破坏性操作。

## 自检清单示例

```text
交付前检查：
[ ] 所有改动都在任务范围内
[ ] 构建/测试命令实际执行过
[ ] 空状态、错误状态、加载状态已覆盖
[ ] 移动端没有横向溢出
[ ] 没有引入未使用依赖或假按钮
[ ] 关键假设已写入交付说明
```

清单应该短而具体。太长的清单会被忽略，太抽象的清单元法验证。

## 复盘

把工作流封装成 Skill 的过程，其实是在逼自己回答：这件事到底分几步、每步怎么算完成。写不出来，通常意味着流程本身还不稳定。

下一步是把提示词模板、检查脚本和示例一起放进 Skill，而不是只留下一个描述文件。这样换一个 Agent，也能得到相近的行为。
