## 这个 Skill 是什么

Frontend Design Simplifier 是我自己写的一个前端页面简化与设计审查 Skill。

它扮演的是产品设计师、UI/UX 设计师和前端体验审查者，不是单纯的“帮我把页面变好看”。它先理解产品、用户和页面任务，再判断哪些设计有价值、哪些只是模板习惯。

核心原则只有一句：**删除没有价值的设计，保留有价值的设计。**

“去 AI 味”不等于一律极简、白底、无装饰，也不是把所有页面都改成同一个模板。品牌个性、内容密度和必要的视觉氛围都可以保留，前提是它们确实服务于产品和用户。

## AI 味通常从哪里来

它把常见问题分成四类。

**模板化视觉**：默认紫色或蓝紫渐变、没有理由的玻璃拟态、光斑、发光边框、网格纹理；所有页面都是 Hero + 统计卡片 + 功能卡片；图标和 emoji 风格不统一。

**结构臃肿**：简单信息被拆成大量卡片，卡片里继续嵌套卡片；标题、统计和图表重复展示同一件事；顶部堆一堆欢迎区、介绍区、统计区和快捷入口；为了填满空间加入没有实际价值的模块。

**视觉失衡**：留白过多或过少；标题过大、字阶过多、字重混乱；圆角、阴影、边框和间距没有统一规则；所有元素都在强调，反而没有重点；低对比度、小字号或过多浅灰文字。

**交互问题**：主操作不突出，次要操作反而抢眼；同一操作有多个入口；悬浮、缩放、弹跳和滚动动画没有实际用途；为了极简把必要操作藏进多层菜单；表单、表格和筛选器过度装饰，降低效率。

## 先理解页面，再决定布局

它不会先问“你想要什么风格”，而是先确认：

- 产品类型和目标用户是谁；
- 这个页面最核心的任务是什么；
- 信息优先级和主要操作是什么；
- 用户最常走的路径是什么；
- 品牌和视觉资产有哪些约束；
- 技术栈、组件库和现有设计 Token 是什么。

已有上下文里写清楚的内容不会重复问。只有真正影响页面结构的问题才会追问。

## 页面诊断：P0–P3

审查时会把问题分级，而不是把所有“不顺眼”都当成必须改：

| 级别 | 含义 |
| --- | --- |
| P0 | 阻断核心任务，或存在严重可访问性、功能问题 |
| P1 | 明显影响理解、效率或视觉秩序 |
| P2 | 冗余、装饰过度或一致性问题 |
| P3 | 纯风格偏好，不应强制修改 |

这个分级很重要。否则“简化”很容易变成个人审美清洗，把有品牌价值但自己不喜欢的东西全部删掉。

## 结构精简：不要用极简掩盖信息缺失

结构精简不是把内容删空，而是：

- 删除重复信息和纯装饰模块；
- 合并表达同一件事的标题、统计和图表；
- 减少没有意义的容器嵌套；
- 让主操作出现在用户自然寻找的位置；
- 根据任务选择侧栏、标签页、筛选、表格或详情面板；
- 保留空、加载、错误、成功和确认状态。

如果删掉一个模块会让用户完不成任务，那它就不该被删。极简不是目的，清晰才是。

## 视觉简化：先定角色，再调样式

它会先确定颜色、字体和间距的角色，再动具体样式：

- **颜色**：区分背景、内容表面、主文字、次文字、边框、品牌色和状态色；颜色要有语义，不为装饰增加多组近似色。
- **字体**：建立有限层级，比如页面标题、区块标题、正文、辅助说明、标签和元信息；不为每个组件创造新字号。
- **间距**：使用统一尺度，保证区块、组件和文本节奏一致。
- **圆角与阴影**：按品牌和产品类型决定，不是所有元素都要大圆角或阴影；优先用间距、分隔线和背景层级组织内容。
- **动效**：只用于反馈、状态变化、导航和帮助理解，不为装饰而漂浮、弹跳或呼吸。

同时会检查文字对比度、键盘焦点和响应式，避免“看起来简洁，实际更难用”。

## 交互与响应式

视觉之外，它还会看操作效率：

- 主操作是否明确，危险操作是否和普通操作区分；
- 表格是否便于扫描、筛选和分页；
- 表单是否说明必填、格式和错误原因；
- 小屏是否还能完成核心任务；
- 状态是否只靠颜色传达；
- 空、加载、错误和成功状态是否完整。

## 不同产品，不同减法

它不会拿同一套标准套所有页面：

| 产品类型 | 优化重点 |
| --- | --- |
| 中后台 | 信息密度、表格、筛选和操作效率；不要把每个字段都做成卡片 |
| 博客 / 内容网站 | 阅读体验、排版、内容宽度和标题层级；让文章和作品成为主体 |
| 品牌官网 / 游戏官网 | 保留品牌识别、氛围和叙事；大图、纹理和动效可以存在，但不能套用 SaaS 仪表盘结构 |
| 音乐 / 评分 / 社区 | 突出封面、作品信息、评分、评论和用户关系；避免每条内容都被厚卡片包裹 |
| 数据大屏 | 保留必要指标，控制重复表达，明确单位、时间范围、图例和来源；不要把所有数字都做成发光效果 |

## 两个例子

**中后台仪表盘**：常见问题是顶部欢迎语占很大空间，统计卡片展示无关数字，卡片里继续嵌套图表卡片，渐变和阴影比数据更抢眼。改造时会把高频操作和关键筛选放到用户自然寻找的位置，只保留支持决策的指标，用分组或紧凑表格表达关联数据，而不是继续加卡片。

**个人博客**：常见问题是首页同时出现巨大欢迎区、个人统计、技能卡片、项目卡片和重复自我介绍，所有内容都被圆角容器包住。改造时会让文章列表或个人介绍成为主体，控制内容宽度和阅读行长，用排版、留白和少量品牌元素建立个性，同时保留分类、搜索和归档入口。

## 改代码时的边界

用户要求直接改代码时，它会先检查项目结构、组件库和相关页面，说明准备改什么、哪些业务行为保持不变，然后分页面实施。

它优先复用现有组件和设计 Token，不无故引入依赖，也不做无关重构。改完会检查交互、路由、权限、数据绑定和响应式，并按环境能力运行 lint、typecheck、测试或构建，最后区分“实际验证过”和“没有验证”的内容。

如果用户只是要求审查，它不会擅自改代码。

## 怎么使用

只做审查：

```text
用 frontend-design-simplifier 审查当前页面。
先给 P0–P3 问题清单、删除/合并/保留/简化建议，不要改代码。
```

直接精简：

```text
按 frontend-design-simplifier 精简 <页面>。
可以调整布局、视觉和交互，但保留所有字段、状态、权限、路由和接口，不做无关重构。
```

新页面前置约束：

```text
开发 <页面> 前，先用 frontend-design-simplifier 输出页面目标、信息层级、页面结构、视觉方向、设计 Token 和应避免的模板化套路。
```

设计决策时，它会依次问五个问题：

1. 这个元素是否帮助用户完成任务或理解信息？
2. 它是否和其他内容重复？
3. 去掉它是否会损害理解、品牌或操作？
4. 有没有更简单的表达？
5. 它是否符合产品自己的视觉语言？

有价值就保留；表达过度就简化；重复或纯装饰就删除；价值不明则标记讨论，不擅自删除业务内容。

## 输出与检查

新页面设计前会给出页面目标、信息层级、页面结构、视觉方向、设计 Token、关键组件、交互、响应式规则和应避免的套路。

现有页面审查会给出总体判断、P0–P3 问题、删除/合并/保留/简化清单、建议结构、业务影响和验证清单。

直接改完代码后，会说明改了哪些页面和组件、删掉或合并了什么、哪些业务逻辑保持不变、实际测试结果和未验证风险。

最后还会过一遍检查项：核心任务是否清晰、是否还有无意义欢迎区和统计卡片、是否有重复信息和不必要嵌套、颜色和字号是否有统一规则、主次操作是否明确、各类状态是否完整、桌面和窄屏是否可用、品牌个性是否还在、有没有擅自删除业务功能。

## 边界与禁止事项

- 不把所有页面改成同一种极简模板。
- 不默认紫色渐变、玻璃拟态、发光边框和大圆角卡片。
- 不为“高级感”增加无意义留白。
- 不为“简洁”删除必要功能、字段、状态、权限或路由。
- 不把个人审美偏好说成客观错误。
- 不擅自更换品牌风格。
- 不未检查项目就大规模替换组件库。
- 不声称执行了没有实际运行的测试或构建。

它也不是万能审美裁判。它更擅长发现结构冗余、视觉失焦和交互低效；涉及品牌战略或视觉创意时，最终判断仍然应该由人来做。
