## 调用方式（通用适配）

- **手动调用**：本技能不依赖自动触发。普通「写个接口」类请求不会自动加载；当你显式引用本技能（如 `/backend-workflow`、"按 backend-workflow 流程做"、"用后端工作流"）时，Agent 读取 SKILL.md 并按其执行。
- **跨 Agent 兼容**：只依赖 Markdown、相对路径引用和通用工程命令，不绑定特定平台 API。支持 SKILL.md 的 Agent 可直接识别；不支持的 Agent 可将 SKILL.md 与 references/templates 作为上下文注入。
- **引用规则**：`references/...` 与 `templates/...` 都相对于 SKILL.md 所在目录，按需读取。

## 这个 Skill 是什么

它是一套面向后端和软件项目的**带门禁工作流**，不是代码模板，也不是架构方案。

它约束的是 Agent 的工作方式：先读懂需求并复述确认，再建立可追踪的任务文档，按优先级小步实现和测试，交付前检查敏感信息与 Git 授权，最后用真实证据汇报。它不替开发人员决定业务规则，也不允许在需求模糊时直接大规模写代码。

如果只用一句话概括：**把「凭感觉直接写」变成「先确认、再计划、分阶段验证、最后诚实交付」。**

## 它解决什么问题

Agent 写后端时常见的风险，通常不是不会写 CRUD，而是流程失控：

- **需求理解错**：只看了半段需求就开始写，做出来的不是开发人员要的。
- **没有计划**：一次改很多模块，缺少优先级、依赖和验收标准。
- **假完成**：代码写了但没跑测试，或者只跑了不相关的测试。
- **测试变绿靠改测试**：删失败用例、放宽断言、跳过关键路径。
- **敏感信息与 Git 越界**：把密钥写进代码，或未经确认就提交、推送、发布。
- **无法续接**：中断后不知道做到哪、改了什么、还剩什么风险。

这套 Skill 用阶段、门禁、任务文档和证据报告逐项约束这些风险。

## 核心结构：5 个阶段 + 5 道门禁

| 阶段 | 主要工作 | 对应门禁 |
|---|---|---|
| 1. 需求发现 | 读需求、上传文件、代码、测试和 Git 状态；复述理解 | **Gate A：理解确认** |
| 2. 任务文档 | 建/更新模块化开发任务文档，列优先级、依赖和验收标准 | **Gate B：计划确认** |
| 3. 分阶段实现 | 只做最高优先级的未阻塞任务，小步修改并测试 | **Gate C：阶段验证** |
| 4. 敏感信息与 Git | 检查密钥、凭据、变更范围和远端操作授权 | **Gate D：敏感操作确认** |
| 5. 最终验证与交付 | 跑真实测试、核对任务文档、输出诚实的交付报告 | **Gate E：交付报告** |

门禁不是形式：Gate A/B 未确认前不进入大规模实现；Gate C 没有测试证据不能标记完成；Gate D 没有明确授权不提交/推送；Gate E 不能把未执行测试写成通过。

## 五个阶段具体做什么

### 阶段一：发现需求并确认理解

Agent 会先读开发人员的请求、上传的需求/设计/表结构/截图/日志，以及现有仓库结构、技术栈、入口、相关模块、测试和 Git 状态。

然后给出简短的理解摘要，至少包括：

- 这次要改什么、什么不能改；
- 核心业务流程和预期结果；
- 假设、风险和未解决问题；
- 可能受影响的模块。

即使需求看起来清楚，也要请开发人员确认或纠正。只有涉及设计、数据、安全、API 或范围的关键歧义才需要追问，不应让开发人员重复已经提供的材料。

### 阶段二：建立开发任务文档

默认创建或更新 `docs/project/development-task.md`，如果仓库已有文档位置则跟随现有约定。文档通常包含：

- 项目背景、目标、范围、非目标、用户和角色；
- 已确认的技术栈与版本，建议项单独标记；
- 架构、模块职责、现有代码约束和编码约定；
- 核心实体、关系、API 契约和校验规则；
- 端到端业务流、状态流转、异常、权限、事务和幂等性；
- 按模块拆分的可验证小任务；
- P0–P3 优先级、依赖、风险、影响范围与验收标准；
- 测试策略、测试数据和环境假设；
- 待确认问题与已确认决策。

拆分原则是每个任务都能独立实现、独立测试、独立验收；任务太大就继续拆。

### 阶段三：分阶段实现并测试

默认选择最高优先级且依赖已满足的任务，不静默跳过前置依赖，也不把无关改动混进同一批。

执行时：

- 先重读需求和相关代码，再做最小的完整改动；
- 跟随现有架构和编码约定，除非已批准的计划明确要求变更；
- 不顺手重构无关模块、升级依赖或改表结构；
- 每批修改后测试正常、非法输入、边界、异常、权限、持久化、事务、重复请求和上下游集成；
- 测试失败先定位原因，不通过删测试或放宽断言变绿；
- 更新任务文档的状态、改动文件、执行命令和真实结果。

任务状态包括：`待确认`、`待开始`、`进行中`、`待验证`、`已完成`、`受阻`、`暂缓`。写了代码不等于完成，必须满足验收标准并有验证证据。

### 阶段四：敏感信息与 Git 检查

交付前会扫描改动文件和配置中的潜在密钥，包括 API Key、访问令牌、密码、私钥、连接串、签名密钥和日志中的凭据。

发现风险时：

- 不在报告中打印完整密钥，只说明位置、类型和风险；
- 询问开发人员再决定删除、替换、轮换或改配置；
- 优先使用环境变量或项目已有密钥管理方式；
- 示例配置只放占位符，不放真实凭据。

Git 方面会检查 `git status`、暂存区、diff、忽略文件和提交范围，确认生成文件、本地数据、日志和密钥没被误带进去。**本地只读检查可以做；提交、推送、发布、创建远端分支或上传内容，必须得到明确确认。** 同意改代码不等于同意推送。

### 阶段五：最终验证与交付

Agent 会运行当前环境可用的测试和质量检查，核对核心业务流、API 兼容性、数据库迁移、配置和相邻模块回归风险，并让任务文档与实际实现保持一致。

最终报告包括：

- 实际完成了什么；
- 影响了哪些模块和文件；
- 跑了哪些测试、真实结果如何；
- 敏感信息和 Git 检查结果；
- 未完成项、限制和风险；
- 文档与产物位置、下一步建议。

未执行的测试会明确标注原因，理论检查不会被包装成执行结果；关键验收未满足时只能给部分完成报告。

## 五道门禁的意义

- **Gate A（理解）**：先证明理解一致，再谈方案。
- **Gate B（计划）**：范围、任务拆分、优先级和验收标准确认后才大规模动手。
- **Gate C（阶段验证）**：每个阶段都有测试证据，或明确因何受阻。
- **Gate D（敏感操作）**：密钥变更和远端 Git 操作需要单独确认。
- **Gate E（交付）**：报告必须反映真实代码和测试状态。

这五道门禁是它区别于普通「帮我写代码」提示词的核心。

## 测试要求

测试策略会按项目技术栈裁剪，优先覆盖：

- 单元测试：业务规则、计算、校验、状态判断和异常分支。
- API/集成测试：请求校验、响应契约、认证授权、持久化和事务。
- 数据库测试：约束、迁移、回滚、并发更新、分页和查询正确性。
- 业务流测试：跨模块完整旅程、状态变化和失败路径。
- 回归测试：相邻模块和原有行为。
- 静态检查：格式化、lint、类型检查、编译、依赖和安全扫描（若项目已有且安全）。

每个接口或业务操作会结合场景检查正常、缺失/非法/超长字段、边界、未授权、记录不存在、状态冲突、重复提交、事务回滚、并发、下游失败、分页、日志脱敏和状态码。

证据规则是：记录实际执行的命令和结果，区分代码审查与实际测试；环境、凭据、依赖或外部服务不可用时说明限制，不把未运行的负载、安全或端到端测试写成通过。

## 文档与模板

技能目录内包含：

- `SKILL.md`：五阶段工作流、原则、门禁和交付要求。
- `references/workflow-gates.md`：Gate A–E 的详细检查点和范围变更规则。
- `references/testing-and-quality.md`：测试分层、覆盖清单、证据和完成标准。
- `templates/development-task.md`：项目任务文档模板，含范围、技术栈、业务流、任务表、测试计划和风险。
- `templates/phase-report.md`：单阶段报告模板。
- `templates/final-delivery.md`：最终交付报告模板，含真实测试结果、敏感信息和 Git 状态。

完整源码入口在文章顶部，指向 GitHub 的 `myskill/backend-workflow-skill/`。

## 适合什么场景

- 从零开始的后端项目，需要先确认需求、范围和任务拆分。
- 实现一个功能、重构一个模块或协调跨模块改动。
- 涉及数据、安全、支付、权限或其他高风险变更。
- 需要一份可续接、可交接的开发任务文档。
- 希望 Agent 在交付前跑测试、查密钥、确认 Git 操作，而不是直接宣布完成。
- 需要把需求分析、实现、测试、性能和缺陷修复串成有顺序的阶段链。

## 不太适合的场景

- 只读代码、解释概念或回答一个很小的技术问题。
- 单行文案修改且开发人员明确要求走最简流程。
- 项目已有更严格、更具体的工程流程；此时应把它作为补充，而不是强行覆盖。
- 无法访问仓库、测试命令或必要环境；这种情况下可以完成分析和计划，但不能声称已完成验证。
- 希望 Agent 完全不确认、直接大规模自动改代码；这与 Skill 的门禁设计相反。

## 怎么使用

最直接的方式：

```text
用 backend-workflow 流程帮我实现 <功能>。
范围：<相关模块/接口>；不要改：<无关模块/接口契约>。
测试命令：<已有命令>。
```

Agent 应先做 Gate A 理解确认，再给出任务拆分和计划（Gate B）；确认后按阶段实现，每批更新任务文档和验证结果。涉及提交或推送时，需要单独明确授权。

如果已有任务文档或交接文件，可以直接指向它，让 Agent 先读再续接，避免从头重复分析。

## 与其他后端提示词文章的关系

- **初期需求分析与项目工单**：更详细的业务需求梳理工具；这个 Skill 负责把确认后的需求放进完整开发流程。
- **Spring Boot 功能实现**：具体写代码的提示词；这个 Skill 负责范围、顺序、测试和交付门禁。
- **全链路严谨测试 / 性能测试 / 缺陷分批修复**：更深入的阶段工具；这个 Skill 规定它们在什么时机使用、如何确认和如何回滚。

它不是替代这些提示词，而是把它们串成一条可确认、可验证、可续接的工作流。

## 预期结果

使用后应该得到：

- 一份明确的 in-scope / out-of-scope 理解和确认记录；
- 一份可执行、可追踪的开发任务文档；
- 小步、可回归的实现，而不是一次性大改；
- 真实测试结果与阶段报告；
- 敏感信息和 Git 操作的明确边界；
- 一份不夸大、不隐瞒的最终交付说明。

## 边界与限制

- 它描述 Agent 应有的行为，不能在平台层面强制执行权限或拦截命令。
- 它是流程约束，不替开发人员确认业务规则、技术选型或验收标准。
- 某些平台不会自动加载 Skill；需要显式调用，或把不可协商的规则补充到项目的 `AGENTS.md` 等指令文件中。
- 它不保证每个项目都适合同一套测试范围；应按项目技术栈和风险裁剪。
- 开发人员明确要求跳过流程时可以精简，但不应用删测试、改断言或伪造结果来换取「完成」。
