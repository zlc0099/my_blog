我用 Agent 做全栈项目之后，最大的变化不是“写代码变快了”，而是我更像一个 tech lead 了：定边界、拆任务、给上下文、验结果。Agent 负责动手，但方向、范围和“什么算完成”仍然得我来定。

这篇不比较工具，也不讲怎么安装 Skill，只讲一个实际问题：**怎么把全栈项目合理地交给 Agent，而不是被它带着跑。**

## 先把它当成一个没有上下文的工程师

Agent 的能力不差，但它不知道你的项目昨天发生了什么，不知道哪个接口是历史包袱，不知道哪个目录不能碰。它会把“看起来合理”的东西写得很顺，包括不存在的接口、编造的字段和多余的抽象。

所以沟通的核心不是“把话说得客气”，而是把三件事说清楚：

- **现状**：项目是什么、用什么栈、怎么跑、哪些地方不能动。
- **目标**：这次只做什么，做到什么程度算完成。
- **验收**：用什么命令、什么页面、什么数据证明它真的做完了。

缺了任何一项，Agent 都会自己补。它补出来的东西，往往就是你要返工的地方。

## 开工前，先给它一张地图

我现在会在项目根目录放一份简短的协作说明，叫 `AGENTS.md` 或 `CLAUDE.md` 都行。不用写成论文，能回答下面这些问题就够：

```md
## 项目
Vue 3 + Vite 前端，Spring Boot + MySQL 后端。

## 常用命令
- 前端：npm run dev / npm run build
- 后端：mvn test / mvn spring-boot:run
- 数据库迁移：见 docs/migration.md

## 约定
- API 统一返回 { code, message, data }
- 错误码在 docs/error-codes.md
- 页面必须处理加载、空、错误状态
- 不新增依赖前先询问
- 不修改 legacy/ 目录
- 不打印或提交任何密钥

## 当前状态
- 订单模块正在开发，接口契约见 docs/order-api.md
- 已知问题：列表分页在第二页会重复
```

这份文件的价值是“减少重复解释”。每次新开对话，Agent 先读它，比你重新贴一遍项目背景可靠得多。它也应该随着项目更新，不要把过期信息一直留在里面。

## 一个任务，一个可验收的纵向切片

全栈项目最容易犯的错，是让 Agent “先把后端写完，再写前端”。等前后端碰头时，字段对不上、状态没处理、接口返回结构和页面预期不一致，返工量比一开始就纵向打通更大。

我现在更愿意按**纵向切片**拆任务：一个用户故事，从数据库到页面完整走通。

比如“订单列表”这个任务，可以拆成：

1. 确认订单表结构和分页查询；
2. 写 Repository / Service / Controller；
3. 定义前端 API 类型和请求函数；
4. 做列表页，包括加载、空、错误状态；
5. 用真实数据联调；
6. 跑测试和构建，交验收证据。

这一个切片做完、验完、提交，再开下一个。不要一次性丢给 Agent “把订单模块做完”，那不是一个任务，是一个季度目标。

任务要小到你能在合理时间内 review 完。太大，Agent 容易跑偏；太小，又会把时间耗在反复启动上。我的经验是：一个任务最好只对应一个可演示的结果。

## 提示词按这六段写

我不太用很长的“角色扮演”提示词，更常用一个固定的任务包：

```text
【背景】
这是一个 Vue 3 + Spring Boot 项目，订单模块已有订单表和基础 Controller。
相关文件：src/views/OrderList.vue、src/api/order.ts、OrderController.java。

【目标】
实现订单列表页，支持分页和按状态筛选，使用真实接口。

【范围】
只修改上述三个文件和对应的测试文件。
不要改订单表结构，不要新增依赖，不要动其他模块。

【约束】
沿用现有 API 封装和设计 Token；接口返回结构见 docs/order-api.md。
页面必须有加载、空数据、错误和重试状态，移动端不能横向滚动。

【验收】
- 打开 /orders 能看到真实接口数据
- 切换状态和页码时请求参数正确
- npm run build 通过
- 后端相关测试通过
- 汇报修改文件、执行过的命令和未验证项

【先别写代码】
先复述你的理解，列出计划修改的文件、风险和需要我确认的问题。
```

这六段里，最容易被忽略的是“范围”和“验收”。不写范围，Agent 会顺手重构；不写验收，它会觉得“代码写完了”就是完成。

## 先计划，再动手

除了很小的修改，我现在都会让 Agent 先出计划：

- 它理解的任务是什么；
- 准备改哪些文件；
- 有没有需要先确认的接口、字段或业务规则；
- 打算怎么验证。

这一步能提前暴露很多问题。比如它准备“顺便把订单服务重构成策略模式”，你就能在它动手前拦住；它准备“先 mock 一下接口”，你就能要求它先读真实契约。

计划不需要很长，但要有文件路径和验证方式。确认之后再做，比写完再发现方向错了便宜得多。

## 全栈的顺序：契约、数据、后端、前端、联调

一个比较稳的顺序是：

1. **先定契约**：接口路径、请求参数、响应结构、错误码、分页格式、日期格式。
2. **再动数据**：表结构、迁移脚本、索引；不要让 Agent 直接改生产库。
3. **后端实现**：Controller 只做参数校验和编排，业务放在 Service，数据访问放在 Repository。
4. **前端接真实接口**：先写 API 类型和请求函数，再做页面，不要先堆一版假数据再“以后替换”。
5. **联调与回归**：真实数据、异常分支、空状态、权限、移动端，一起验。

契约最好落到文档或类型里，而不是只在对话里说一遍。Agent 很擅长根据一个明确的 DTO 推导前后端代码，也很擅长在没有契约时自己发明字段。

## 验收要证据，不要“已完成”

Agent 说“已完成”时，我通常会追问四件事：

- 改了哪些文件？有没有超出范围？
- 执行了哪些命令？构建和测试结果是什么？
- 有没有实际打开页面/调用接口？看到了什么？
- 哪些是验证过的，哪些还没验证？

如果它只给了一段总结，没有命令输出、没有测试结果、没有页面反馈，我会把它当成“代码写完了”，而不是“任务完成了”。

Review 的时候重点看：

- 有没有无关文件被改；
- 有没有偷偷新增依赖；
- 有没有删除或跳过测试；
- 有没有把异常吞掉、用默认值掩盖错误；
- 有没有把 Mock 数据伪装成真实接口；
- 有没有为了“通过”而改断言、改配置。

这些比代码风格更值得先看。

## 卡住的时候，别让它反复猜

Agent 卡住时，最常见的表现是开始“到处改”：换个写法、加个日志、重构一下、再试一次。这个时候继续让它自由发挥，通常只会扩大 diff。

我现在的做法是：

1. 给它最小复现：哪个页面、哪个接口、什么输入、期望什么、实际什么。
2. 给它关键日志或堆栈，不要贴整个仓库。
3. 要求它先给假设，再给最小修复方案，不要直接大改。
4. 修完加一个回归测试或验证步骤。
5. 如果两三轮还在打转，就停下来，缩小范围，或者自己接手。

Agent 适合在明确边界内快速试错，不适合在没有反馈的情况下无限猜。

## 多 Agent 并行：先分地盘

多个 Agent 同时写一个项目，最容易出的不是“能力问题”，是冲突：两个人改同一个文件、一个人改了接口另一个人不知道、最后合并出一堆隐性 bug。

我现在会先分地盘：

- 按模块或目录拆，不按“前端/后端”粗暴拆到会互相依赖的文件；
- 先冻结接口契约，再让前后端并行；
- 一个文件同一时间只有一个 owner；
- 用独立分支或 worktree，不要让多个 Agent 在同一个工作区里同时改；
- 最后留一个集成者跑构建、测试和联调，而不是让每个 Agent 各自宣布完成。

Agent 可以用来做研究、review、写测试、查日志，但不建议让多个 Agent 同时改同一块核心代码。

## 上下文会过期，交接要写下来

长对话到后面，Agent 会忘掉前面的决定，或者把旧方案和新方案混在一起。这个时候继续聊，往往越聊越乱。

我会在阶段结束时写一个简短交接：

```md
## 已完成
- 订单列表接口和页面
- 分页、状态筛选、空/错误状态

## 关键决定
- 分页参数用 page/size，响应结构沿用现有 PageResult
- 状态枚举以后端为准，前端不自定义

## 未完成
- 导出功能
- 第二页重复数据的问题还没修

## 下一步
- 先复现第二页重复，再决定是 SQL 还是前端去重
```

新开对话时把这份交接和项目说明一起给 Agent，比让它继承一整段混乱的历史更可靠。

## 安全边界

这几条我会写死：

- 不把 `.env`、密钥、令牌贴进对话；
- 不执行来源不明的脚本；
- 数据库迁移、删除数据、部署、推送远程前先确认；
- 不让 Agent 直接操作生产环境；
- 命令执行前看一眼，尤其是 `rm`、`drop`、`reset --hard`、`push --force` 这类。

Agent 可以很快，但破坏性操作也很快。权限给得越大，越需要边界。

## 我踩过的坑

- 只说“做个订单模块”，没给验收，最后页面能打开但接口是假的。
- 没写“不要动其他模块”，Agent 顺手重构了公共组件，回归了一下午。
- 让 Agent 先写前端假数据，后面换真接口时字段全对不上。
- 长对话里它忘了之前定过的分页格式，自己发明了一套。
- 它说“测试通过”，但实际只跑了构建，没有跑测试。
- 为了让它“通过”，它把失败断言改掉了；从此我 review 必看测试 diff。

这些坑的共同点不是 Agent 不聪明，而是我没有把“现状、边界、验收”说清楚。

## 小结

跟 Agent 做全栈项目，比较合理的方式是：

- 给它一张项目地图，而不是每次重新口述；
- 按纵向切片拆任务，一次交付一个可演示结果；
- 契约先行，真实数据优先，Mock 必须显式；
- 先计划再动手，范围写清楚；
- 验收要命令、输出和页面证据，不接受一句“已完成”；
- 长任务写交接，多 Agent 先分地盘；
- 安全边界和破坏性操作始终由人确认。

Agent 的上限，很大程度取决于你给它的上下文、边界和验收标准。你越像一个清楚的 tech lead，它越像一个靠谱的工程师。
