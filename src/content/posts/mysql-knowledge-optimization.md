MySQL 很容易给人一种「会用」的错觉：增删改查都能写，建表加字段也没问题。但真正出问题时，往往卡在更下面一层——为什么这个索引没走、为什么事务里读到了不该读的数据、为什么加个字段就把表锁住了、为什么数据量一上来接口就慢。

这篇笔记把这些东西串起来：先看一条 SQL 是怎么执行的，再看索引、事务、日志这些底层机制，然后落到优化顺序，最后集中回答开发中最常见的疑惑。

## 一条 SQL 是怎么执行的

一条查询大致经过四层：

| 层 | 做什么 | 出问题时常见表现 |
|---|---|---|
| 连接层 | 建立连接、认证、权限检查、连接池管理 | 连接数打满、连接泄漏 |
| 解析与预处理 | 词法语法分析、检查表列是否存在 | 语法错误、表名写错 |
| 优化器 | 决定用哪个索引、join 顺序、是否改写 | 选错索引、执行计划回退 |
| 执行器 | 按执行计划调用存储引擎取数据 | 扫描行数过多、回表过多 |

存储引擎层才是真正读写数据的地方。InnoDB 是默认引擎，支持事务、行锁、MVCC、崩溃恢复；MyISAM 不支持事务，基本只适合只读或历史归档场景。现在新项目默认用 InnoDB 就够了。

理解这条链路的意义在于：**SQL 慢，可能慢在优化器选错路，也可能慢在执行器扫了太多行，还可能慢在连接层排队。** 不同层的问题，解法完全不同。

## InnoDB 是怎么存数据的

### 页、行和 B+Tree

InnoDB 以**页**为单位读写磁盘，默认一页 16KB。数据行存在页里，页组成 B+Tree。

聚簇索引（主键索引）的叶子节点直接存整行数据；二级索引的叶子节点存的是「索引列 + 主键值」。所以通过二级索引查完整行时，要先查到主键，再回聚簇索引取数据，这个过程叫**回表**。

一张表只能有一个聚簇索引。如果没定义主键，InnoDB 会选第一个非空唯一索引；都没有，就生成一个隐藏的 6 字节 row id。所以建表时**最好显式定义主键**，而且主键要短、有序、不频繁变更。

### 为什么是 B+Tree

| 结构 | 问题 |
|---|---|
| 二叉搜索树 | 数据量大时树太高，磁盘 I/O 次数多 |
| 红黑树 | 同样太高，不适合磁盘 |
| 哈希 | 只支持等值查询，不支持范围和排序 |
| B-Tree | 非叶子节点也存数据，同样大小能放的 key 更少 |
| B+Tree | 非叶子只存 key 和指针，叶子成链表，范围查询和排序友好 |

B+Tree 的关键优势是**矮胖**：一个 16KB 的页能放几百个 key，三层左右就能覆盖千万级数据。查一次通常只需 2 到 4 次页读取，而且非叶子节点常驻内存，实际磁盘 I/O 更少。

### Buffer Pool

InnoDB 不会每次都读磁盘，而是把页缓存到 **Buffer Pool**。读先看内存，写先改内存页并标记为脏页，再由后台线程刷盘。

Buffer Pool 的 LRU 不是简单的「最近最少使用」，而是分成 young 和 old 两块，新页先插入 midpoint，避免全表扫描把热点数据冲掉。这个设计解释了一个现象：**一次大查询可能让缓存命中率骤降，进而拖慢整个实例。**

## 索引

### 索引的类型和选择

| 类型 | 说明 | 场景 |
|---|---|---|
| 主键索引 | 聚簇索引，叶子存整行 | 每张表都该有 |
| 唯一索引 | 保证列值唯一 | 业务唯一约束 |
| 普通索引 | 加速查询，不保证唯一 | 大多数过滤字段 |
| 联合索引 | 多列组成一个索引 | 多条件查询、排序 |
| 前缀索引 | 只索引字符串前 N 个字符 | 长字符串，节省空间 |
| 全文索引 | 分词检索 | 简单文本搜索，复杂场景用 ES |

索引不是越多越好。每个索引都要占空间，都会拖慢写入，都会增加优化器的选择成本。判断标准只有一个：**这个索引服务哪条查询，它的收益是否大于写入和维护成本。**

### 联合索引与最左前缀

联合索引 `(a, b, c)` 相当于按 a、再按 b、再按 c 排序。它能支持：

- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c = ?`
- `WHERE a = ? AND b > ?`（a 等值，b 范围）
- `WHERE a = ? ORDER BY b`

不能高效支持：

- `WHERE b = ?`（缺少最左列）
- `WHERE b = ? AND c = ?`
- `WHERE a = ? AND c = ?`（c 用不上索引定位，只能靠 a 过滤后再判断）

这里有个常见误区：`WHERE a = 1 AND c = 3` 并不是完全用不上索引，而是**只能用 a 做索引定位**，c 只能在回表后过滤。如果查询列都在索引里，c 还能通过索引下推在索引层过滤，但依然不能像等值列那样缩小扫描范围。

所以联合索引的列顺序要围绕查询来定：**等值条件在前，范围条件在后，排序字段尽量跟索引顺序一致。**

### 覆盖索引

如果一条查询需要的列全部在索引里，就不需要回表，这叫覆盖索引。`EXPLAIN` 的 `Extra` 出现 `Using index` 就是覆盖索引生效。

```sql
-- 只需要 id、status、created_at
ALTER TABLE bid
  ADD INDEX idx_tenant_status_created (tenant_id, status, created_at);
```

覆盖索引能显著减少随机 I/O，但代价是索引变宽。把 `SELECT *` 改成只查需要的列，很多时候比加索引更划算。

### 索引什么时候会失效

- 列上用了函数或表达式，比如 `WHERE DATE(created_at) = '2026-10-01'`。
- 隐式类型转换，比如字符串列和数字比较。
- 前导模糊匹配，`LIKE '%keyword'`。
- `OR` 连接的某一侧没有索引。
- 不满足最左前缀。
- 数据区分度太低，优化器判断全表扫描更便宜。
- 统计信息过期，优化器估算错误。

最后两条经常被忽略：**索引没失效，只是优化器主动没选它。** 这种情况要先 `ANALYZE TABLE` 更新统计信息，再考虑 `FORCE INDEX`；强制索引是临时手段，不是常规方案。

### 区分度

区分度 = 不重复值数量 / 总行数。性别、状态这类字段区分度很低，单独建索引意义不大；但它们放在联合索引里作为过滤条件，仍然有价值。

判断一个字段适不适合单独建索引，可以先跑：

```sql
SELECT COUNT(DISTINCT status) / COUNT(*) FROM bid;
```

结果接近 1 说明区分度高，接近 0 说明低。不过这不绝对，还要结合查询频率和实际数据分布。

## 事务

### ACID 和隔离级别

| 特性 | 含义 | InnoDB 靠什么实现 |
|---|---|---|
| 原子性 A | 要么全成功，要么全失败 | undo log |
| 一致性 C | 约束和业务规则不被破坏 | 应用 + 数据库约束共同保证 |
| 隔离性 I | 并发事务互不干扰 | 锁 + MVCC |
| 持久性 D | 提交后不丢 | redo log |

四种隔离级别：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不会 | 可能 | 可能 |
| REPEATABLE READ（默认） | 不会 | 不会 | InnoDB 下基本不会 |
| SERIALIZABLE | 不会 | 不会 | 不会 |

「幻读」指同一事务内两次查询，第二次多出了第一次没看到的行。InnoDB 在 RR 级别下用 MVCC 保证快照读结果一致，用 next-key lock 保证当前读不出现幻读，所以跟标准 SQL 的定义略有差异。

### MVCC 是怎么工作的

每行数据有两个隐藏字段：`DB_TRX_ID`（最后修改它的事务 id）和 `DB_ROLL_PTR`（指向 undo log 里的旧版本）。更新时旧版本写进 undo log，形成一条版本链。

事务做快照读时，会生成一个 **Read View**，里面记录当前活跃事务 id 列表、最小活跃事务 id、下一个事务 id 等信息。读取时沿着版本链往前找，找到第一个对当前事务可见的版本。

关键区别：

- **RC**：每条语句生成一个新的 Read View，所以同一事务内两次查询可能看到不同结果。
- **RR**：事务第一次快照读时生成 Read View，之后一直复用，所以两次查询结果一致。

这也是为什么 RR 下「事务里读到的数据和外面不一致」不是 bug，而是快照读的正常行为。要看最新数据，得用 `SELECT ... FOR UPDATE` 或 `LOCK IN SHARE MODE` 这类当前读。

### 锁

InnoDB 的锁按粒度分：

| 锁 | 作用范围 | 说明 |
|---|---|---|
| 记录锁 Record Lock | 单行索引记录 | 锁定具体行 |
| 间隙锁 Gap Lock | 索引记录之间的间隙 | 防止其他事务插入 |
| Next-Key Lock | 记录锁 + 间隙锁 | RR 下默认加锁方式 |
| 插入意向锁 | 插入位置 | 插入前设置，等待间隙锁释放 |
| 意向锁 IS / IX | 表级 | 表示事务准备给某些行加锁 |
| 元数据锁 MDL | 表结构 | DDL 和 DML 冲突的来源 |

几个容易踩的点：

- **锁是加在索引上的。** 如果查询没走索引，可能锁住大量行甚至整张表。
- **RC 级别下基本没有间隙锁**，所以并发插入更好，但会出现幻读。
- **DDL 会拿 MDL 写锁。** 一个长事务没提交，后面的 `ALTER TABLE` 就会被阻塞，再后面的查询也会被排队。
- **间隙锁主要出现在 RR 及以上隔离级别**，用于防止其他事务在间隙里插入；RC 下基本不加。

### 死锁

死锁是两个事务互相等待对方持有的锁。常见原因是加锁顺序不一致，或者两个事务都先锁一批数据再锁另一批。

排查：

```sql
SHOW ENGINE INNODB STATUS;
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

避免方式：

- 固定加锁顺序，比如按主键排序后再批量更新。
- 事务尽量短，别在事务里做远程调用、发消息、等用户输入。
- 更新和删除走索引，避免锁范围扩大。
- 业务允许时降低隔离级别到 RC，减少间隙锁。
- 捕获死锁异常并重试，数据库已经帮你回滚了其中一个事务。

## 日志与持久化

InnoDB 有三类关键日志：

| 日志 | 层级 | 内容 | 用途 |
|---|---|---|---|
| redo log | InnoDB | 物理页修改 | 崩溃恢复、WAL |
| undo log | InnoDB | 行记录的旧版本 | 回滚、MVCC |
| binlog | Server | 逻辑变更 | 主从复制、数据恢复 |

### redo log 和 WAL

修改数据时，InnoDB 先改 Buffer Pool，再把修改记录写进 redo log，事务提交时按 `innodb_flush_log_at_trx_commit` 决定是否刷盘。真正的数据页由后台异步刷盘。

这就是 **WAL（Write-Ahead Logging）**：先写日志再写数据，把随机写变成顺序写，同时保证崩溃后能恢复。`innodb_flush_log_at_trx_commit = 1` 是最安全的配置，每次提交都刷盘；调成 0 或 2 性能更好，但可能丢最近的事务。

### binlog 和两阶段提交

binlog 是 Server 层的逻辑日志，记录的是「做了什么变更」，主要给主从复制和按时间点恢复用。

一个事务提交时，要同时保证 redo log 和 binlog 一致，所以 InnoDB 用**两阶段提交**：

1. 写 redo log，标记 prepare。
2. 写 binlog。
3. 写 redo log，标记 commit。

崩溃恢复时，如果 redo log 是 prepare 状态，就去检查对应 binlog 是否完整：完整就提交，不完整就回滚。这样主库和从库不会出现「主库有、从库没有」的不一致。

### 长事务为什么危险

- undo log 不能及时清理，版本链越来越长，快照读越来越慢。
- 占用锁时间长，阻塞 DDL 和其他事务。
- 可能导致主从延迟。
- 回滚成本高。

监控 `information_schema.innodb_trx` 里运行时间过长的事务，基本是每个 DBA 都会做的事。

## 优化

### 先定位，再动手

优化最忌讳上来就加索引。合理的顺序是：

1. **确认慢在哪。** 是数据库、网络、应用序列化，还是接口本身逻辑。
2. **开慢查询日志。** 设置 `long_query_time`，用 `mysqldumpslow` 或 `pt-query-digest` 聚合。
3. **看执行计划。** `EXPLAIN` 看访问类型、扫描行数、是否排序、是否临时表。
4. **改索引或改 SQL。**
5. **回归验证。** 对比执行时间和扫描行数，别只看「感觉快了」。

### EXPLAIN 看什么

| 字段 | 关注点 |
|---|---|
| `type` | 访问类型，性能从好到差：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `key` | 实际使用的索引，`NULL` 表示没走索引 |
| `key_len` | 索引使用了几列，可判断联合索引用到哪 |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤后剩余比例 |
| `Extra` | `Using index` 覆盖索引；`Using filesort` 额外排序；`Using temporary` 临时表；`Using index condition` 索引下推 |

`type = index` 容易误判：它表示扫描整棵索引树，不是走索引定位。数据量大时一样很慢。

MySQL 8.0.18 之后可以用 `EXPLAIN ANALYZE` 看实际执行时间和行数，比估算更可靠。

### 常见优化手段

**深分页。** `LIMIT 100000, 20` 会先扫描 100020 行再丢弃前 100000 行。两种改法：

```sql
-- 延迟关联：先用覆盖索引拿主键，再回表
SELECT b.*
FROM bid b
JOIN (
  SELECT id FROM bid
  WHERE tenant_id = 42
  ORDER BY created_at DESC
  LIMIT 100000, 20
) t ON b.id = t.id;

-- 游标分页：记住上一页最后一条
SELECT *
FROM bid
WHERE tenant_id = 42 AND id < 100000
ORDER BY id DESC
LIMIT 20;
```

游标分页最快，但只适合「上一页/下一页」，不适合跳页。

**COUNT 优化。** InnoDB 不保存精确行数，`COUNT(*)` 需要实际统计。`COUNT(*)` 和 `COUNT(1)` 性能基本一样，`COUNT(column)` 会排除 NULL。大表计数可以考虑近似值、单独计数表或缓存，不要每次都全表 count。

**JOIN 优化。** 给小表加索引、让驱动表结果集尽量小、关联字段类型一致、避免过多表 join。MySQL 8.0.18 之后有 hash join，但嵌套循环仍是大头。

**批量操作。** 批量插入比逐条插入快很多；批量更新注意单次事务大小，几千行一批比较稳。

**避免 SELECT \*。** 减少网络传输，增加覆盖索引机会，也避免表结构变更带来的意外。

**连接池。** 连接不是越多越好，连接数超过数据库处理能力后，等待和上下文切换会让整体更慢。池大小要结合 QPS、单查询耗时和数据库核数来定。

### 表设计上的优化

- 用最小够用的类型：能 `INT` 不 `BIGINT`，能 `TINYINT` 不 `INT`。
- 金额用 `DECIMAL`，不要用 `FLOAT` / `DOUBLE`。
- 时间用 `DATETIME` 或 `TIMESTAMP`，注意 `TIMESTAMP` 的时区和 2038 问题。
- 字符集统一 `utf8mb4`，别再混用 `utf8`。
- 尽量 `NOT NULL + DEFAULT`。NULL 参与索引、比较、聚合时行为更复杂，唯一索引里多个 NULL 也不冲突。
- 大字段（TEXT、BLOB）拆到单独表，避免主表页变宽。
- 单表字段不要太多，适当垂直拆分。
- JSON 适合结构不固定、查询不复杂的场景；需要频繁按某个字段过滤时，考虑生成列加索引。

### 大表变更

给大表加索引、加字段、改类型，都可能锁表。MySQL 8.0 支持 Online DDL，但并不是所有操作都真的 Online：

- 加索引通常可以在线进行，但会占用 I/O。
- 加字段在 8.0.12 之后支持 INSTANT，8.0.29 之后任意位置也能 INSTANT。
- 改列类型、改字符集往往需要重建表。
- 大表变更建议用 `gh-ost` 或 `pt-online-schema-change`，配合低峰期执行和监控。

## 架构层面

### 主从复制与读写分离

主从复制是异步的，从库可能落后于主库。常见的延迟原因：大事务、从库单线程回放、从库压力大、网络问题。

读写分离后，「刚写完立刻读」可能读到旧数据。解决办法：

- 写后短时间强制读主库。
- 重要业务用半同步复制。
- 用 GTID 和延迟监控，把延迟控制在可接受范围。
- 业务上接受最终一致，读路径做好兜底。

### 什么时候考虑分库分表

先优化索引、SQL、表结构、缓存、读写分离。这些做完还不够，再考虑分片。判断信号通常是：单表数据量过大导致即使走索引也慢、写入成为瓶颈、单库连接或磁盘撑不住。

分片一旦引入，跨分片查询、分布式事务、扩容、全局唯一 ID 都会变成新问题。**能晚点分就晚点分，能垂直拆就先垂直拆。**

## 常见答疑

**1. 为什么 MySQL 用 B+Tree，不用 B-Tree 或哈希？**

B+Tree 非叶子节点不存数据，同样大小的页能放更多 key，树更矮，磁盘 I/O 更少；叶子节点用链表连接，范围查询和排序效率高。哈希只适合等值查询，不支持范围和排序，所以 InnoDB 只在自适应哈希索引这种内部优化里用。

**2. 联合索引 (a, b, c)，查询 WHERE b = 1 能用索引吗？**

不能用于定位。索引按 a 排序，b 在全局不是有序的。但 MySQL 可能做全索引扫描（`type = index`），比全表扫描略快，但数据量大时仍然慢。要让 b 生效，得建以 b 开头的索引。

**3. 回表是什么？怎么避免？**

二级索引叶子只存索引列和主键，查其他列要回聚簇索引取，这就是回表。避免方式是覆盖索引：把查询需要的列都放进索引。但索引列越多，索引越大、写入越慢，要权衡。

**4. 为什么加了索引还是不生效？**

先看 `EXPLAIN` 的 `key` 和 `type`。常见原因：列上有函数、隐式类型转换、前导模糊、不满足最左前缀、区分度太低、统计信息过期。也可能是优化器算出来全表扫描更便宜，这时先 `ANALYZE TABLE`，别急着 `FORCE INDEX`。

**5. 索引是不是越多越好？**

不是。每个索引都占空间、拖慢写入、增加优化器选择成本。一张表通常控制在 5 个以内比较合理，具体看查询模式。定期清理从未被使用的索引。

**6. 为什么建议用自增主键？**

自增主键有序，插入时新页基本在末尾，减少页分裂和随机 I/O；主键短，二级索引叶子存的也短，索引更小。UUID 做主键会导致随机插入、页分裂和索引膨胀，非要用的话考虑有序 UUID 或单独的业务唯一键。

**7. RR 和 RC 怎么选？**

RR 是默认值，快照读一致性更好，但间隙锁更多、并发插入更差。RC 没有间隙锁，并发更好，但同一事务内可能读到不同结果，需要应用层接受。互联网业务用 RC 的不少，金融类更偏向 RR 或更严格的控制。选哪个要看业务对一致性和并发的要求。

**8. MVCC 能解决幻读吗？**

快照读可以，因为 Read View 固定了可见版本，新插入的行看不到。当前读不行，需要 next-key lock 来锁住间隙。所以「MVCC 解决幻读」这句话只对快照读成立。

**9. 事务里读不到刚更新的数据，为什么？**

如果事务用的是快照读，Read View 在第一次查询时就固定了，之后看不到其他事务的新提交。要读最新数据，用当前读 `SELECT ... FOR UPDATE`，或者把事务拆开。也要检查隔离级别和自动提交设置。

**10. 死锁怎么排查？**

先看 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`，看两个事务分别持有什么锁、等待什么锁。再看 `performance_schema.data_locks` 和 `data_lock_waits`。常见原因是加锁顺序不一致、缺索引导致锁范围过大、事务太长。解决靠固定顺序、缩短事务、补索引，最后才是重试。

**11. redo log 和 binlog 有什么区别？**

redo log 是 InnoDB 的物理日志，记录页修改，循环写，用于崩溃恢复；binlog 是 Server 层的逻辑日志，记录变更语句或行变更，追加写，用于复制和恢复。两者通过两阶段提交保证一致。

**12. 为什么事务要尽量短？**

长事务会持有锁、阻止 DDL、让 undo log 无法清理、导致版本链变长和主从延迟。事务里不要做远程调用、发消息、等用户输入，能挪到事务外的都挪出去。

**13. NULL 有什么坑？**

`NULL = NULL` 结果是 NULL 不是 true；`COUNT(column)` 不统计 NULL；`NOT IN` 遇到 NULL 可能返回空结果；唯一索引允许多个 NULL；索引统计和优化器估算也会受影响。业务上「未知」和「空字符串/0」含义不同，但大多数字段建议 `NOT NULL + DEFAULT`。

**14. 为什么 COUNT(*) 在大表上很慢？**

InnoDB 不保存精确行数，需要扫描索引统计。表越大越慢。可以接受近似值时用 `SHOW TABLE STATUS` 的 `Rows`，或者维护计数表、用缓存。业务上真要精确总数，就要接受这个成本。

**15. 读写分离后读到旧数据怎么办？**

先确认延迟来源：大事务、从库压力、单线程回放。业务上对一致性要求高的读走主库，或者写后一段时间内强制读主；技术上可以用半同步复制、并行复制、GTID 监控。不要假设主从复制是实时的。

**16. 什么时候该分库分表？**

单表优化到极限仍然慢、写入成为瓶颈、单库容量或连接数撑不住时才考虑。优先垂直拆分和读写分离，最后才是水平分片。分片会带来跨片查询、分布式事务、扩容和 ID 生成问题，代价很高。

## 小结

MySQL 的优化不是一堆技巧，而是一条链路：

- 先理解存储和索引，知道查询为什么快、为什么慢；
- 再理解事务和锁，知道并发下数据为什么不对、为什么阻塞；
- 然后用慢查询日志和 `EXPLAIN` 定位，按「索引 → SQL → 表设计 → 架构」的顺序解决；
- 最后接受一个事实：没有银弹，每个优化都有代价。

把「这条查询扫了多少行、锁了哪些记录、事务持有了多久」这三个问题问清楚，大部分问题都能找到方向。
