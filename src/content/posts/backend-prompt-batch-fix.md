这篇不是开发提示词，也不是测试提示词，而是**测试报告已经产出之后**的缺陷修复提示词。

它要求 Agent 先读报告、看证据、定位根因，不能看到失败用例就直接改代码；分析完成后必须先向开发人员提交修复清单和策略，等确认后才能分批修改。没有报告、没有复现证据或没有确认范围时，不应该直接进入修复阶段。

## 什么时候使用

适合在以下情况使用：

- 已经完成一轮后端测试，拿到了失败用例、异常日志和业务闭环结论。
- 测试发现了数据错误、流程中断、权限漏洞、事务一致性或状态流转问题。
- 缺陷数量较多，需要按模块、风险或依赖关系拆分处理。
- 修复涉及多个模块或公共逻辑，需要先评估影响范围和回归成本。
- 需要把测试结论转成可执行、可追踪、可验证的修复计划。

不适合：

- 还没跑测试、没有失败证据，只是凭感觉「优化一下」。
- 需求还没确认，或测试报告本身把环境问题、测试数据问题误判成业务缺陷。
- 需要直接改数据库结构、公共接口契约或生产配置，但没有取得明确授权。
- 想通过放宽断言、删除用例或屏蔽异常来让测试变绿。

## 与前一篇测试提示词的关系

推荐顺序是：

1. 使用《后端全链路严谨测试与业务闭环验证》完成测试并产出报告。
2. 使用本文提示词，把报告中的失败项拆成可修复清单。
3. 确认策略后分批修改，并回到测试环境做回归验证。
4. 最终输出缺陷修复总表和遗留风险。

测试报告是输入，修复记录是输出。没有测试证据的「修复」很容易变成猜测。

## 使用前需要准备什么

- 测试报告、失败用例、异常日志和复现步骤。
- 当前代码版本、构建产物和测试环境信息。
- 涉及的接口清单、数据库表结构、状态枚举和业务规则。
- 可复现的测试数据，以及相关账号和权限角色。
- 明确允许修改的范围，以及不能改动的接口、表结构或业务规则。
- 谁负责确认修复策略、谁负责验收，以及是否需要分批上线。

## 它会怎么工作

1. 从报告中提取失败项、异常和潜在风险。
2. 结合代码定位根因，区分真实缺陷、测试问题、环境问题和设计问题。
3. 合并同一根因引发的多个现象，识别缺陷之间的依赖关系。
4. 按数据安全、业务流程、权限、事务、一般逻辑和边界问题划分优先级。
5. 整理修复清单，列出影响模块、修复方案、验证方式和回归范围。
6. 提交方案 A 集中修复、方案 B 分批修复、方案 C 自定义顺序，等待开发确认。
7. 获得确认后，每次只处理一个缺陷或一组强关联缺陷。
8. 每批修复后执行对应测试和回归，记录真实结果和遗留风险。
9. 全部结束后输出缺陷修复总表，明确每项状态。

## 修复优先级

一般按业务风险排序，但必须以实际影响为准：

1. 数据损坏、越权访问、安全漏洞、事务不一致、关键业务中断。
2. 核心业务流程无法完成、关键状态错误、重要数据丢失。
3. 异常处理、边界条件、部分功能异常。
4. 非关键提示、样式一致性、低风险优化。

高风险问题不能因为修复成本高就跳过，也不能用降低校验标准的方式绕过。

## 三种修复策略

- **方案 A：集中修复。** 适合缺陷关联紧密、需要统一调整、分批反而增加不一致风险的情况。风险是单次改动范围大、回归成本高。
- **方案 B：分批修复。** 适合缺陷较多、模块相对独立、需要控制风险的情况。推荐优先处理安全、数据和流程问题，再逐批推进。风险是周期较长，需要维护批次之间的依赖。
- **方案 C：自定义顺序。** 由开发人员根据上线节奏、模块负责人或业务时间指定顺序。

无论选哪种，都必须先取得确认，不能由 Agent 自行决定高风险改动范围。

## 修复约束

- 不删除失败用例、不放宽断言、不屏蔽异常、不修改预期结果来制造绿色测试。
- 不伪造测试结果；未执行、被跳过或被阻塞的测试必须明确标记。
- 不擅自删除业务逻辑、修改数据库结构或改变接口契约。
- 需要改表、改接口或跨模块调整时，先说明原因、影响和迁移方案，再取得确认。
- 发现根因判断错误或修复引入回归时，暂停后续批次，先处理当前问题。
- 每批修改都应控制范围，并保留可追踪的修改记录和验证结果。

## 最终交付

每批修复完成后输出：

- 本批修复的缺陷、根因和业务影响。
- 修改的文件、接口和业务模块。
- 修复方案与关键变更。
- 执行的测试、真实结果和回归情况。
- 尚未解决的问题、风险及下一批建议。

全部结束后提供缺陷修复总表，并为每项标记：

- 已修复并验证
- 已修复待验证
- 待确认
- 暂缓修复
- 无法复现

## 完整提示词

````prompt
# 后端缺陷分析与分批修复 Agent 提示词

## 一、任务目标

请先阅读项目现有的后端测试报告、缺陷记录及相关技术文档，结合当前代码、数据库结构和实际业务流程，分析问题根因，制定合理的修复方案，并在与开发人员确认后分批实施修复。

本次任务的核心是：**先分析、再确认、后修复；拆分大问题，逐项解决，确保每次修改可验证、可回归。**

## 二、执行流程

### 第一步：阅读报告并分析问题

1. 阅读测试报告，提取所有失败用例、异常日志、业务闭环问题及潜在风险。
2. 结合代码定位问题根因，不要仅根据测试现象直接修改代码。
3. 区分真实缺陷、测试数据问题、环境问题、测试用例问题和设计层面的缺陷；证据不足时明确标记待确认。
4. 检查问题之间的依赖关系，识别可能由同一根因引起的多个缺陷，避免重复修复。

### 第二步：拆分缺陷并制定方案

将复杂问题拆分成可以独立分析、实施和验证的小任务，按模块整理成修复清单。每项至少包含：

- 缺陷编号、所属模块及问题描述。
- 严重程度与业务影响。
- 根因分析及相关代码位置。
- 推荐修复方案、可能影响的模块。
- 修复顺序、前置依赖及验证方式。

优先处理数据错误、业务流程中断、权限漏洞、事务一致性问题等高风险缺陷，其次处理重要业务逻辑问题，最后处理一般异常处理、边界条件和非关键优化。具体优先级应以实际风险和业务影响为依据。

### 第三步：向开发人员确认修复策略

**在修改代码之前，先向开发人员提交分析结果和推荐方案，等待确认，不得直接大规模修改。**

明确询问开发人员选择哪种策略：

- **方案 A：集中修复。** 在评估依赖关系、影响范围和回归成本后，集中处理相关缺陷，适用于问题关联紧密、需要统一调整的情况。
- **方案 B：分批修复。** 按优先级、模块和依赖顺序逐批实施，优先解决高风险问题，适用于缺陷较多、影响范围较大或需要控制风险的情况。
- **方案 C：自定义顺序。** 由开发人员指定优先修复的模块、缺陷或时间安排。

请给出你的推荐方案及理由，并明确各方案的风险、影响范围和预计验证工作量。若存在必须优先处理的安全或数据完整性问题，应单独提醒开发人员。

### 第四步：分批实施并逐项验证

获得确认后，按照确认的方案执行：

1. 每次只处理一个明确的缺陷或一组强关联的小缺陷，控制修改范围。
2. 修复前检查现有实现和调用链，保留无关功能，不擅自重构其他模块。
3. 修复后运行相关单元测试、接口测试及必要的业务闭环回归测试。
4. 检查数据库事务、状态流转、异常处理、权限校验以及上下游模块是否受到影响。
5. 记录每项缺陷的修改内容、测试结果和遗留风险；当前批次验证通过后，再进入下一批。
6. 如果修复引入新问题、测试失败或发现根因判断错误，应暂停后续批次，先分析并处理回归问题。

## 三、修复约束

- 不得只修改测试断言、屏蔽异常或降低校验标准来让测试通过。
- 不得伪造测试结果；未执行的测试必须明确标记。
- 不得擅自删除业务逻辑、修改数据库结构或改变接口契约。
- 如确实需要调整表结构、接口设计或跨模块业务流程，必须先说明原因、影响和迁移方案，并取得开发人员确认。
- 不确定的问题先列出证据和待确认事项，不得凭猜测实施高风险修改。

## 四、最终交付

每批修复完成后，输出简明记录：

- 本批修复的缺陷及根因。
- 修改的文件、接口或业务模块。
- 修复方案及关键变更。
- 执行的测试、实际结果和回归情况。
- 尚未解决的问题、风险及下一批建议。

全部任务结束后，提供缺陷修复总表，明确标记为“已修复并验证”“已修复待验证”“待确认”“暂缓修复”或“无法复现”等状态。

**最终目标：以测试报告为依据，以业务正确性为标准，以开发人员确认为前提，通过小步、可追踪、可回归的方式逐步修复后端缺陷。**
````
