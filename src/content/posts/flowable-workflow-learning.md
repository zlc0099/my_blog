审批流、工单流转、请假、报销、合同会签，这类需求一开始很容易写成“状态字段 + 一串 if-else”。流程简单时没问题，等到分支变多、节点要动态指定、还要查历史记录，代码就会慢慢缠成一团。

Flowable 做的事情，是把流程定义从业务代码里拿出来，用 BPMN 2.0 描述，引擎负责推进流程、保存运行时状态、分配任务和记录历史。它不是万能的，但对“有人工节点、流程较长、需要审计”的场景很合适。

这篇整理我对 Flowable 的理解：先看核心对象，再看 BPMN 元素和 Spring Boot 接入，最后集中回答实际使用中最容易卡住的问题。

## 先理解几个核心对象

| 对象 | 含义 | 你可以把它想成 |
|---|---|---|
| Deployment | 一次部署记录 | 把流程文件发布到引擎 |
| ProcessDefinition | 流程定义 | 流程模板，按 key 和 version 区分 |
| ProcessInstance | 流程实例 | 按模板发起的一次具体流程 |
| Execution | 执行路径/令牌 | 流程当前走到哪、分支怎么走 |
| Task | 人工任务 | 需要某个人或某组人处理的工作 |
| Job / TimerJob | 异步或定时作业 | 引擎稍后要执行的动作 |
| HistoricProcessInstance / HistoricTask | 历史记录 | 流程和任务走完之后的归档 |
| Variable | 流程变量 | 在流程中传递的业务数据 |

最容易混的是 `ProcessDefinition` 和 `ProcessInstance`：前者是模板，后者是按模板跑起来的一次流程。同一个流程定义可以启动很多实例，每个实例有自己的变量、任务和状态。

`Execution` 是流程的运行路径。有一条主线时它和流程实例很像；遇到并行网关分叉后，会出现多个执行令牌，最后再汇合。

`Task` 是给人做的任务。服务任务、脚本任务不产生待办，它们由引擎直接执行；用户任务才会出现在某人的待办列表里。

## BPMN 常用元素

BPMN 的图元很多，实际项目常用的其实就几类。

### 事件

- **开始 / 结束事件**：流程的起点和终点。
- **定时事件**：按时间触发，支持持续时间、具体时间点和 cron 表达式。
- **消息事件**：等待某条消息，通常是一对一的。
- **信号事件**：广播式事件，可以被多个流程或任务接收。
- **错误事件**：捕获业务异常，走异常处理路径。
- **边界事件**：挂在任务或子流程上，比如超时提醒、超时自动通过。
- **补偿事件**：为已经完成的操作定义补偿逻辑。

事件最容易出错的是“中断”和“非中断”：中断边界事件会取消当前任务，非中断边界事件则让原任务继续，同时走另一条路径。

### 任务

| 类型 | 用途 |
|---|---|
| 用户任务 | 需要人处理，产生待办 |
| 服务任务 | 调用 Java 委托、表达式或外部服务 |
| 脚本任务 | 执行脚本，适合很轻的逻辑 |
| 业务规则任务 | 调用 DMN 决策表 |
| 接收任务 | 等待外部消息后继续 |

服务任务不等于“写一个很大的 Java 类”。复杂业务应该放在领域服务里，Delegate 只做流程和业务之间的适配。

### 网关

- **排他网关**：只走一条满足条件的分支；要设置默认分支，防止条件全部不满足。
- **并行网关**：所有分支都会走，汇合时要等所有进入的分支都到达。
- **包容网关**：满足条件的分支都走，汇合时等已经激活的分支。
- **事件网关**：等待多个事件中的某一个发生。
- **复杂网关**：更复杂的汇合条件，实际项目用得不多。

排他网关的条件写成表达式，比如 `${days > 3}`；条件要覆盖所有情况，或者配置默认流。并行网关卡住时，第一反应应该是“是不是有一条分支没走到汇合点”。

### 子流程

- **嵌入式子流程**：画在同一个流程里，适合把一组节点收起来。
- **调用活动**：调用另一个独立的流程定义，适合复用审批模板。
- **事件子流程**：由事件触发，不依赖主流程的正常顺序。

流程图不是越细越好。节点太多、网关太密，后续维护会比代码更难。

## 一条审批流怎么跑

以请假审批为例，可以简化成：

```text
开始 → 员工提交（用户任务）→ 天数 > 3？
  ├─ 是 → 主管审批 → HR 审批 → 结束
  └─ 否 → 主管审批 → 结束
```

Spring Boot 里启动流程、查任务、完成任务的基本代码：

```java
ProcessInstance instance = runtimeService.startProcessInstanceByKey(
    "leave",
    "LEAVE-1001",
    Map.of("days", 5, "applicant", "user-1")
);

Task task = taskService.createTaskQuery()
    .processInstanceId(instance.getId())
    .taskAssignee("user-1")
    .singleResult();

taskService.complete(task.getId(), Map.of("approved", true));
```

几个细节：

- `businessKey` 通常放业务系统的唯一标识，比如请假单号；后面查流程、对账都靠它。
- 启动时的变量会进入流程作用域，后续网关、任务和执行都能读。
- 完成用户任务时可以传新变量，比如审批结果、审批意见。
- 任务有候选人时，通常先 `claim` 再 `complete`；已经指定 assignee 的任务不需要再 claim。

## Spring Boot 接入

流程引擎的 starter 通常是 `flowable-spring-boot-starter-process`。BPMN 文件放在 `src/main/resources/processes/` 下，Spring Boot 启动时会自动部署。

常用配置：

```yaml
flowable:
  async-executor-activate: true
  history-level: audit
  database-schema-update: true
```

`database-schema-update` 适合开发和测试，生产环境通常由 DBA 按版本执行建表脚本，不建议让应用自动改表。

服务任务可以绑定一个 Spring Bean：

```java
@Service("notifyDelegate")
public class NotifyDelegate implements JavaDelegate {
    @Override
    public void execute(DelegateExecution execution) {
        String applicant = (String) execution.getVariable("applicant");
        // 发通知、写审计日志等，注意幂等
    }
}
```

BPMN 里写 `flowable:delegateExpression="${notifyDelegate}"`。Delegate 里不要做特别耗时的外部调用；如果一定要做，考虑异步任务、重试和幂等，别把整个流程事务拖住。

任务分配常见有三种：

- `assignee`：直接指定一个人。
- `candidateUsers`：一组候选人，谁先 claim 谁处理。
- `candidateGroups`：按角色或部门分配，适合和现有权限系统对接。

候选人组不要硬编码在 BPMN 里。可以用表达式从变量取，或者在任务创建监听器里动态计算；具体人选最好来自业务系统的用户和组织数据，而不是在 Flowable 里再维护一份。

## 变量、异步和事务

### 变量

流程变量分几种作用域：流程实例级、执行级、任务本地。跨节点共享的用流程变量；只属于某个任务的临时数据用任务本地变量；不需要持久化的用 transient 变量。

变量会参与序列化，不要把大对象、文件内容、完整日志塞进流程变量。存业务主键、状态、少量金额和审批意见就够了，详情回业务库查。

### 异步与定时

服务任务可以配置异步执行，避免长事务。异步作业会进入 Job 表，由 async executor 执行；失败后会重试，超过次数进入死信。

定时事件和异步作业依赖 async executor。如果定时器不触发，先确认 executor 是否开启，再看 `ACT_RU_JOB` / `ACT_RU_TIMER_JOB` 里有没有作业，最后看时钟、时区和 cron 表达式。

### 事务与副作用

Flowable 通常和 Spring 事务一起工作。Delegate 抛异常，流程事务会回滚；但这不代表外部副作用也能回滚。发邮件、调 HTTP 接口、写消息队列这些操作，要么幂等，要么放在事务提交后做，要么用 outbox/补偿。

异步重试会把同一个 Delegate 再执行一遍，所以 Delegate 本身要能承受重复执行。

## 历史、版本和多租户

**历史级别**一般有 none、activity、audit、full。级别越高，记录越全，写入和存储成本也越高。审批类系统通常至少开 audit，方便查谁在什么时候做了什么。

历史数据要定期清理，否则 `ACT_HI_*` 表会越来越大。但清理策略要跟审计要求对齐，不能为了省空间把关键记录删掉。

**版本管理**：同一个流程 key 重新部署会生成新版本，已经运行的实例默认继续使用旧版本。修改流程后要确认：旧实例怎么办？要不要迁移？迁移前先备份，迁移后验证任务、变量和历史是否正常。

**多租户**：Flowable 支持 tenantId。查询流程定义、启动实例、查任务时都要带上租户条件，否则容易串数据。租户和现有系统的组织隔离要保持一致，不要一边用租户、一边又靠业务字段过滤。

## 常见答疑

**1. Flowable、Activiti、Camunda 是什么关系？**

Flowable 是从 Activiti 分出来的流程引擎，API 和概念有很多相似之处；Camunda 也是同一 lineage 的引擎，但产品和生态不同。选型不要只看名字，重点看版本维护、Spring Boot 兼容、团队经验和社区资料。

**2. 流程定义、流程实例、执行、任务怎么区分？**

流程定义是模板；流程实例是按模板跑起来的一次流程；执行是流程里的运行路径/令牌；任务是其中需要人处理的工作。一个实例可以有多个执行和多个任务。

**3. assignee 和 candidate 有什么区别？**

assignee 是已经指定给某个人；candidateUsers / candidateGroups 是候选人/候选组，需要先 claim 才能变成自己的任务。用组分配时，记得在查询待办时同时查 candidateGroup。

**4. 并行网关为什么卡住不往下走？**

并行网关的汇合要等所有进入分支都到达。常见原因是有分支没走到、被条件拦住、抛异常回滚，或者流程被挂起。先查当前执行令牌和活动节点。

**5. 排他网关条件全部不满足怎么办？**

会报错或卡住。给网关设置默认流，或者保证条件覆盖所有情况。条件表达式要写在流程变量存在的前提下，变量缺失也可能导致表达式求值失败。

**6. 定时器为什么没有触发？**

先确认 async executor 是否开启，再看定时作业是否创建、时间是否到了、时区和 cron 是否正确。还要确认流程实例没有挂起、作业没有被删除。

**7. 服务任务没有执行，怎么排查？**

看 Delegate 的 bean 名和 `delegateExpression` 是否一致，类是否在容器里，表达式有没有拼错；再看流程事务是否回滚、异步作业是否进入重试/死信。日志里通常能看到异常，不要只看流程图。

**8. 审批驳回应该怎么建模？**

可以走一条回到上一节点的流，也可以用网关结束当前流程。关键是明确业务语义：驳回是回到申请人、回到上一级，还是直接终止。不要用删除流程实例来代替业务上的驳回。

**9. 会签/多人审批怎么做？**

用多实例用户任务，配置 collection、elementVariable 和 completionCondition，选择并行或串行。不要在代码里给每个审批人创建一个任务再手动计数，引擎已经提供了这类能力。

**10. 历史表里查不到数据？**

先看 history level 是不是 none，或者只开了 activity；再看流程是否真的执行过、历史异步写入是否还没落库。不同级别的历史记录范围不一样，不要默认 full。

**11. 流程改了，旧实例怎么办？**

重新部署同一个 key 会生成新版本，旧实例默认留在旧版本。需要迁移时用流程实例迁移能力，先小范围验证，再批量迁移；迁移前备份，迁移后检查任务、变量和历史。

**12. 什么时候不该用 Flowable？**

只有两三个状态、没有人工节点、流程不会长期运行时，用状态机或普通代码更简单。把简单状态流转硬塞进 BPMN，最后只会多一层 XML 和一套引擎运维成本。

**13. Flowable 7 + Spring Boot 3 要注意什么？**

注意版本对应关系和 `jakarta` 命名空间，旧项目里的 `javax` 依赖、过滤器、安全配置可能都要一起升级。升级前先看官方迁移说明，不要只换 starter 版本。

**14. 怎么测试流程？**

用 Spring Boot 测试 + 内存数据库启动引擎，部署测试流程，启动实例，查询并完成任务，最后断言任务、变量和历史。外部 Delegate 用 mock 或测试实现替换，测试之间清理数据库，避免流程实例互相污染。

## 小结

Flowable 的核心不是“会画 BPMN”，而是理解它管理的几个层次：

- 流程定义是模板，流程实例是运行中的一次业务；
- 执行是路径，任务是人的操作；
- 变量是流程和业务之间的数据契约；
- 异步、定时、历史和版本管理，是长期运行必须面对的成本。

建模时尽量让流程图表达业务节点和分支，不要把复杂规则全塞进网关和表达式；Delegate 只做适配，业务逻辑留在领域服务里。流程简单时别急着上引擎，流程复杂时也别把它当万能胶水。
