这是一份后端性能测试与优化分析提示词，不是「猜一个性能问题然后加缓存」的模板。

它要求先做项目分析、制定测试计划，再用真实环境与数据执行基准、负载、压力、稳定性和核心链路测试，采集接口、资源、JVM、数据库与中间件指标，最后根据证据给出按 P0–P3 排序的优化方案。阶段重点是**测试、分析和建议**；未经确认，不直接修改业务代码或数据库结构。

## 什么时候使用

- 功能已经基本稳定，准备上线前做性能基线或容量评估。
- 核心接口、复杂查询、大数据量处理或跨模块链路出现响应变慢。
- 需要验证高并发、持续运行、连接池、缓存或消息积压场景。
- 线上出现超时、GC 抖动、慢 SQL、线程阻塞或资源瓶颈，需要定位证据。
- 重构或架构调整后，需要对比优化前后的指标。

不适合：

- 功能还没跑通、没有稳定测试环境或测试数据。
- 没有授权就压测生产环境或执行破坏性操作。
- 只想看理论分析，不准备执行测试；这种情况应明确标记为方案而不是结果。
- 企图通过关闭安全校验、降低业务校验或改测试断言来「提升性能」。

## 与前两篇后端提示词的关系

推荐顺序：

1. 《后端全链路严谨测试与业务闭环验证》先证明功能、数据、事务和权限正确。
2. 本文做性能测试与瓶颈分析，产出测试报告和优化方案。
3. 《缺陷分析与分批修复》按确认后的优先级分批实施修复或优化。
4. 优化后重新执行回归与相同的性能指标对比。

性能优化不应建立在功能未验证或数据不一致的基础上。

## 使用前需要准备什么

- 项目架构、技术栈、接口清单和核心业务流程。
- 测试环境、机器配置、数据规模，以及和生产环境的差异说明。
- 现有测试工具、脚本、监控、日志和数据库执行计划能力。
- 测试目标：响应时间、吞吐量、错误率、稳定性或容量上限。
- 测试数据初始化与清理策略，以及外部依赖的处理方式。
- 明确允许的测试范围；生产压测必须单独确认。

## 它会产出什么

- 可复核的性能测试计划和执行记录。
- 真实指标：平均响应时间、P50/P95/P99、RPS/TPS、成功率、错误率、CPU、内存、磁盘 I/O、网络、GC、线程、连接池、慢 SQL 和中间件状态。
- 瓶颈证据：具体接口、方法、SQL、执行计划、监控曲线或调用链。
- 按 P0–P3 排序的优化方案：问题、根因、方案/备选、收益、成本、风险、依赖和验证指标。
- 测试限制、未执行项和待确认问题。

如果环境无法实际压测，应完成分析、脚本和执行方案，并明确说明未执行原因，不能把理论分析包装成测试结果。

## 如何判断输出是否合格

- 每个结论是否能追溯到测试场景、真实指标和执行记录？
- 是否区分了测试环境与生产环境，避免夸大系统极限？
- 是否同时检查接口、资源、JVM、数据库和中间件，而不是只看平均响应时间？
- 是否说明数据规模、并发模型、持续时间和清理策略？
- 优化建议是否按优先级排列，并说明验证指标和回归范围？
- 未执行、被阻塞或无法验证的内容是否明确列出？

## 安全与边界

- 测试环境与生产环境隔离；未经授权不压测生产、不访问未授权资源。
- 不发送真实外部通知、支付、短信或设备控制请求。
- 不使用真实生产密钥，不把敏感数据写入报告或脚本。
- 测试数据必须有初始化与清理机制，避免脏数据和重复业务副作用。
- 优化方案先评审再实施；涉及表结构、接口契约或高风险改动必须单独确认。

## 完整提示词

````prompt
# 后端项目性能测试与优化分析 Agent 提示词

## 一、任务目标

请全面分析当前后端项目，结合项目实际技术栈、接口设计、业务流程、数据库结构及部署环境，制定并执行合理的性能测试，评估系统在不同负载下的表现，发现性能瓶颈，并输出正式的《后端性能测试报告》和《性能优化方案》。

**本阶段以测试、分析和提出优化建议为主，未经开发人员确认，不得直接修改业务代码或数据库结构。**

## 二、执行流程

### 1. 项目分析与测试准备

- 分析项目架构、技术栈、接口清单、核心业务流程及数据库设计。
- 识别高频接口、复杂查询、大数据量处理、跨模块业务链路、文件处理、异步任务等重点测试对象。
- 检查数据库索引、SQL 查询、事务、连接池、缓存、线程池及外部服务调用等潜在瓶颈。
- 确认测试环境、机器配置、数据规模及环境限制；区分测试环境与生产环境。
- 制定测试计划，明确测试范围、测试数据、并发量、测试时长和验收指标。

### 2. 执行性能测试

根据项目实际情况，选择合适的工具，例如 JMeter、Gatling、k6 或其他已有测试工具，至少覆盖以下测试类型：

1. **基准测试：** 测量正常负载下的响应时间、吞吐量和资源消耗。
2. **负载测试：** 逐步增加并发用户或请求量，观察系统性能变化。
3. **压力测试：** 找出系统性能明显下降、错误率上升或资源耗尽的临界点。
4. **稳定性测试：** 在持续负载下检查内存增长、连接泄漏、线程阻塞和性能衰减。
5. **核心业务链路测试：** 验证完整业务流程在并发情况下的性能与数据正确性。
6. **数据库专项测试：** 分析慢 SQL、索引使用、锁等待、连接池耗尽及事务竞争等问题。

具体测试类型和强度应结合项目规模与环境能力确定，不必机械执行所有项目。测试前应准备可靠的初始化与清理机制，避免重复请求造成脏数据或重复业务操作。

### 3. 采集指标并定位瓶颈

至少记录以下指标：

- **接口性能：** 平均响应时间、P50、P95、P99 响应时间、吞吐量（RPS/TPS）、请求成功率及错误率。
- **系统资源：** CPU、内存、磁盘 I/O、网络流量及资源使用趋势。
- **JVM（如适用）：** 堆内存、GC 次数与耗时、线程数量、线程阻塞及死锁情况。
- **数据库：** 慢 SQL、查询耗时、连接池使用率、锁等待、索引命中及事务耗时。
- **中间件：** 缓存命中率、消息积压、线程池队列及连接池状态（如项目使用相关组件）。
- **业务正确性：** 并发操作后的数据一致性、状态流转正确性和重复执行风险。

将测试结果与日志、监控、SQL 执行计划及代码调用链结合，尽可能定位到具体接口、方法、SQL 或资源瓶颈。不能仅凭单一指标直接断定根因。

### 4. 输出优化方案

根据实际测试证据，按照优先级提出优化建议：

- **P0：** 严重影响系统可用性、数据正确性或安全性的性能问题。
- **P1：** 明显影响核心业务吞吐量或响应时间的问题。
- **P2：** 一般性能问题及可通过合理改进获得收益的项目。
- **P3：** 低收益优化或长期架构改进建议。

每项优化建议必须说明：

- 对应的测试现象和证据。
- 瓶颈根因及影响范围。
- 推荐优化方式及备选方案。
- 预计收益、实施成本、风险和依赖条件。
- 优化后应验证的指标及回归测试范围。

可评估 SQL 与索引优化、分页策略、批量处理、缓存策略、异步化、连接池参数、线程池配置、对象创建与 GC、接口重复查询、N+1 查询等方向，但必须根据实际项目证据决定是否适用，禁止为了追求性能盲目引入缓存、异步处理或复杂架构。

## 三、性能测试报告要求

生成完整的 Markdown 报告，建议保存为 `docs/performance/performance-test-report.md`；优化方案保存为 `docs/performance/performance-optimization-plan.md`。

性能测试报告应包含：

1. 测试目的、范围、环境配置及工具版本。
2. 测试场景、数据规模、并发模型、持续时间和测试条件。
3. 测试指标定义、测试结果及关键数据表。
4. 各核心接口的响应时间、吞吐量、成功率及资源消耗。
5. 性能曲线、异常现象、瓶颈分析及证据。
6. 压力边界、稳定性表现及已知限制。
7. 结论、风险等级和优化优先级。

优化方案应包含：

1. 问题清单与优先级。
2. 根因分析和证据。
3. 推荐方案、备选方案及实施步骤。
4. 风险、影响模块和预估工作量。
5. 优化前后的对比指标及验收标准。
6. 建议的分阶段实施顺序和回归测试计划。

## 四、执行约束

- 不得伪造测试数据、监控数据或测试结果。
- 未执行的测试必须标记为“未执行”，无法验证的结论必须标明限制。
- 不得将单次测试结果直接视为系统极限或生产环境的真实性能。
- 必须说明测试环境与生产环境的差异，避免夸大结论。
- 测试时不得擅自压测生产环境、访问未授权资源或执行破坏性操作。
- 对可能产生大量数据、发送外部请求、触发真实业务操作的场景，必须先确认测试环境与数据清理策略。
- 不得仅为提升测试成绩而关闭安全校验、降低业务校验标准或修改测试断言。
- 发现明显缺陷时，记录问题及复现条件，纳入优化建议；未经确认不直接实施高风险改动。

## 五、最终验收标准

任务完成时，必须提供：

1. 可复核的性能测试方案与实际执行记录。
2. 包含真实测试数据和指标分析的性能测试报告。
3. 按优先级排列、具有明确实施步骤的性能优化方案。
4. 关键瓶颈对应的代码位置、SQL 或监控证据（能够定位时）。
5. 未完成的测试、测试限制及尚未确认的问题清单。

**注意：如果当前环境无法实际运行压测，应先完成项目分析、测试脚本和执行方案，并明确说明未执行原因；不得将理论分析包装成真实测试结果。完成报告后，向开发人员说明最值得优先处理的优化项，等待确认后再进入优化实施阶段。**
````
